## 简介
本文件系统性梳理 OpenWAF 的处理阶段实现，覆盖当前主引擎链路的 **11 个处理阶段**的设计理念、执行顺序、匹配逻辑、动作决策与短路机制。按 [internal/core/engine/engine.go:465-548] 实测入链顺序，阶段链为：`ip_reputation → anti_replay → acl → lua_pre → owasp_default → cve_detection → bot_detection → browser_sign → rate_limit → signature → custom`，容量按 11 预分配（engine.go:467）。各阶段按防护配置与站点规则是否启用条件入链，未启用的阶段不入链，因此单个请求实际经过的阶段数可少于 11。文档还提供阶段配置的最佳实践、性能调优指南，以及阶段扩展开发方法。TLS 指纹不是独立流水线阶段，而是数据面采集到 RequestCtx 后供 Bot 检测、审计日志和 `tls_*` 规则匹配器使用；Lua 后置策略（`lua_post`）同样不在阶段链内，而是在管道返回后由引擎执行（engine.go:369-371）。

## 项目结构
OpenWAF 将请求处理抽象为"流水线（Pipeline）"，每个处理阶段封装为独立的 Phase 实现，按固定顺序串联执行。核心模块分布如下：
- 引擎层：负责站点解析、维护模式检查、规则编译与流水线组装
- 流水线层：定义统一的 `Phase` 接口（`Name()` + `Execute()`）与执行模型
- 规则阶段层：`internal/core/rules/phases.go` 具体实现各处理阶段（IP 信誉、AntiReplay、ACL、OWASP、CVE、机器人、浏览器签名、速率限制、签名、自定义），`lua_phase.go` 实现 Lua 前置阶段，`phase_skip.go` 提供按路径跳过的装饰器
- WAF 核心算法层：IP 信誉、机器人检测、OWASP 检测、速率限制、CVE 检测、TLS 指纹元数据采集与匹配输入等

## 架构总览
OpenWAF 的处理流程以 Engine 为中心，`getOrBuildPhases` 按以下顺序条件入链阶段（engine.go:465-548）。下表为 **11 阶段全序表**，列出口径以代码实测为准：

| 序 | 阶段名 | 注册位置 | 前置条件 | 短路行为 |
|:--:|---|---|---|---|
| 1 | `ip_reputation` | [engine.go:479](file://internal/core/engine/engine.go#L479) | `e.ipRep != nil` | 全局白/黑名单命中 `stop=true`；站点白名单返回 Allow 不短路 |
| 2 | `anti_replay` | [engine.go:482](file://internal/core/engine/engine.go#L482) | `deps.antiReplay != nil` 且 `rt.AntiReplayEnabled` | 非法/重放 nonce → Intercept 短路 |
| 3 | `acl` | [engine.go:486](file://internal/core/engine/engine.go#L486) | `len(cr.ACL) > 0` | 终端动作短路；**Allow 不短路** |
| 4 | `lua_pre` | [engine.go:492](file://internal/core/engine/engine.go#L492) | Lua 引擎存在且有 StagePre 脚本 | 非 tag/observe 动作短路 |
| 5 | `owasp_default` | [engine.go:496](file://internal/core/engine/engine.go#L496) | `prot.OWASPEnabled` | 命中终端动作短路；Challenge 延迟 |
| 6 | `cve_detection` | [engine.go:499](file://internal/core/engine/engine.go#L499) | `prot.CVEEnabled` 且 detector 非空 | 命中终端动作短路 |
| 7 | `bot_detection` | [engine.go:503](file://internal/core/engine/engine.go#L503) | `prot.BotDetectionEnabled` | Drop/Intercept/Challenge 短路；Observe 继续 |
| 8 | `browser_sign` | [engine.go:513](file://internal/core/engine/engine.go#L513) | `prot.BrowserSignEnabled` | 校验失败按配置动作短路（Observe 除外） |
| 9 | `rate_limit` | [engine.go:517](file://internal/core/engine/engine.go#L517) | `prot.RequestRateLimitEnabled` 且 limiter 非空 | 超限按动作短路（RateLimit 429） |

| 11 | `custom` | [engine.go:527](file://internal/core/engine/engine.go#L527) | `len(cr.Custom) > 0` | 终端动作短路；Observe 命中收集后继续 |

## 详细组件分析

### ACL 访问控制阶段
- 输入：客户端 IP、方法、路径、查询、头部映射（经 `MatchCtx` 构造）
- 输出：命中动作结果与 `stop` 布尔；未命中返回 `Pass(), false`
- 决策机制：`executeCompiledPhase` 顺序遍历已编译 ACL 规则，命中**首条**即返回该规则结果，返回值为 `(hit(rule), hit(rule).IsTerminal())`
- 短路订正：`executeCompiledPhase` 的 `allowShortCircuit` 形参在函数体内**未被使用**（phases.go:112-129）。因此 ACL 的 `allow` 动作 `IsTerminal()` 为假，返回 `stop=false`，**不短路**后续阶段——请求继续经过 OWASP、CVE 等检测；只有拦截/丢弃/挑战等终端动作才短路。切勿理解为"ACL 命中 allow 即终止整条链"

| 符号 | 位置 | 签名 | 职责 |
|---|---|---|---|
| `aclPhase.Execute` | [phases.go:148](file://internal/core/rules/phases.go#L148) | `Execute(ctx) (action.Result, bool)` | 调用 `executeCompiledPhase`，`allowShortCircuit=true` 但未生效 |
| `executeCompiledPhase` | [phases.go:112](file://internal/core/rules/phases.go#L112) | `(ctx, rules, allowShortCircuit, needsDerived)` | 命中首条即返回 `(r, r.IsTerminal())` |
| `Compiled.Match` | [compiler.go:32](file://internal/core/rules/compiler.go#L32) | `Match(ctx MatchCtx) bool` | 委托预构建匹配器 |

### IP 信誉检查阶段
- 输入：客户端 IP、站点级黑白名单（`rt.SiteIPWhitelist/Blacklist`）、全局 IP 信誉与自动封禁
- 输出：`action.Result`（类型 Allow/Intercept/Drop）与 `stop` 布尔
- 决策机制（phases.go:368-433）：
  - 先匹配**站点白名单**：命中返回 `Allow, false`（不短路，继续后续阶段）
  - 再匹配**站点黑名单**：命中返回 Intercept/Drop，`stop=true`
  - 最后调用全局 `rep.Check`：白名单命中返回 `Allow, true`（短路）；黑名单/自动封禁命中返回 Intercept/Drop，`stop=true`
- 自动封禁默认参数（iprep.go:44-47）：阈值 10、窗口 60 秒、持续 3600 秒、动作 `intercept`

| 触发来源 | 命中动作 | stop | 分类 Category |
|---|---|:--:|---|
| 站点白名单 `SiteIPWhitelist` | Allow | 否 | `whitelist` |
| 站点黑名单 `SiteIPBlacklist` | Intercept/Drop | 是 | `site_blacklist` |
| 全局白名单 `rep.Check.Allowed` | Allow | 是 | `whitelist` |
| 全局黑名单/自动封禁 | Intercept/Drop | 是 | `blacklist`/`auto_ban` |

### 机器人检测阶段（两阶段：预筛选 + 深度评分）
- 输入：方法、路径、头部、UA、Cookie、连接方式、ClientIP
- 输出：BotVerdict（是否机器人、分数、类别、原因、规则 ID），以及 BotScore（深度评分明细）
- 预筛选（PreScreen）快速判定高风险：
  - 已知恶意工具 UA
  - 黑名单/自动封禁 IP
  - 高风险 GeoIP（数据中心/VPN/高危国家）
- 深度评分（DeepScore）综合评估：
  - GeoIP 风险评分与信息
  - UA/头部指纹评分
  - TLS/HTTP2 指纹评分
  - IP 信誉评分
- 决策机制：阈值决定拦截级别，恶意工具直接拦截，可疑行为仅记录观察

### 请求速率限制阶段（请求级）
- 输入：客户端 IP，与 `bind`、`siteID`、归一化 `Host` 组成计数键 `RateLimitKey = bind|siteID|host|clientIP`（phases.go:63-70），保证限流按站点隔离

- 决策机制：固定窗口计数，超过阈值即返回终端动作；支持运行时重配置与禁用
- 关键点：Bot 行为分使用同窗口但带 `|bot` 后缀的独立键，避免与限流计数相互干扰（phases.go:490-512）

## 性能考虑
- 并发与锁：IP 信誉与速率限制均采用互斥锁保护状态，注意在高并发下的竞争
- 计数与清理：IP 信誉与速率限制均有后台清理任务，避免内存无限增长
- 归一化成本：OWASP 归一化涉及多次解码与正则扫描，建议：
  - 控制目标长度（maxTargetLen）
  - 使用快速过滤跳过明显安全的目标
  - 限制正文扫描大小（如 multipart 字段值限制）
- GeoIP 查询：使用哈希集合进行 O(1) 快速判定，建议热更新配置而非频繁重载数据库
- 两阶段机器人检测：预筛选快速过滤，仅对高风险 IP 进行深度评分，降低 CPU 开销
- CVE 检测：先做可疑内容预筛选，再按固定检测器顺序查找首个命中，避免每个请求产生 goroutine 开销
- TLS 指纹：数据面缓存 JA3、JA4、TLS 版本、SNI、ALPN 和 cipher suites 到 RequestCtx，规则匹配时按需构造派生 MatchCtx 字段
- 规则匹配优化：签名与自定义阶段使用正则缓存，复合规则实现短路逻辑，减少不必要的匹配成本

## 故障排查指南
- IP 信誉
  - 症状：白名单未生效、封禁未解除
  - 排查：确认列表格式（CIDR/单 IP）、备注字段、过期时间；检查自动封禁阈值与窗口设置
- 机器人检测
  - 症状：误判正常浏览器、漏判已知恶意工具
  - 排查：检查 UA 模式、GeoIP 配置、阈值设置；确认两阶段流程是否启用
- 速率限制
  - 症状：限流不生效或过度拦截
  - 排查：确认启用状态、窗口秒数与最大请求数；检查键生成 `bind|siteID|host|clientIP`（phases.go:63-70）
- OWASP 检测
  - 症状：误报/漏报
  - 排查：调整敏感度档位（off/low/mid/high/very_high/strict 六档）、检查误报抑制逻辑、确认头部跳过列表，详见 [安全防护功能/OWASP 检测/OWASP 检测.md](file://docs/安全防护功能/OWASP 检测/OWASP 检测.md)
- TLS 指纹识别
  - 症状：指纹未识别、误报高风险
  - 排查：确认上游代理正确传递 X-JA3-Hash、X-JA4-Hash、X-TLS-Version 等头部；检查浏览器指纹数据库完整性
- CVE 检测
  - 症状：未触发或动作不当
  - 排查：确认 CVE 开关、检测器初始化、严重程度与动作映射；检查自定义规则正则表达式有效性
- 签名与自定义规则
  - 症状：规则不生效、正则异常、复合规则结构错误
  - 排查：检查规则阶段、启用状态、优先级设置；使用测试接口验证模式解析与匹配
- 动作系统
  - 症状：动作未生效、短路异常
  - 排查：检查动作类型规范化、终端优先级、短路策略

## 结论
OpenWAF 的处理阶段以流水线为核心，通过严格的阶段顺序与动作短路机制实现高效的安全防护。IP 信誉、AntiReplay 与 ACL 提供基础准入控制，OWASP 与 CVE 检测覆盖主流攻击面，机器人检测结合 GeoIP 与指纹技术提升识别精度，速率限制保障服务稳定性。TLS 指纹由数据面采集并作为 Bot 检测、审计日志和 `tls_*` 规则匹配输入，不作为独立流水线阶段。签名与自定义规则阶段提供了灵活的扩展能力，支持复杂的业务场景。阻断机制提供了灵活的响应策略，既能在用户体验和性能之间取得平衡，又能应对高风险攻击场景。合理配置阈值与动作、优化归一化与扫描策略，可在准确性与性能之间取得最佳平衡。
