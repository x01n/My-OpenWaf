## 简介
本文件系统解析 My-OpenWaf 的请求速率限制阶段（`rate_limit`）。它是全 11 阶段链的第 9 位（`... → bot_detection → browser_sign → rate_limit → signature → custom`，engine.go:465-548），位于浏览器签名校验之后、签名/自定义自建规则之前。文档围绕固定窗口算法的实现与并发安全展开，涵盖：`RateLimitKey` 如何按站点隔离、`reqRateLimitPhase.Execute` 如何判定超限并映射动作、`RateLimiter` 的互斥锁与原子计数、`Allow`/`Increment`/`IsOverLimit` 语义、`cleaner` 过期回收，以及配置项与默认值。

> 订正：限流计数键并非旧文档所述"客户端IP + Host"，而是 `RateLimitKey = bind|siteID|归一化Host|clientIP`（phases.go:63-70），确保不同监听器、不同站点互不挤占配额。

## 详细组件分析

### RateLimiter 结构体与并发安全
- 字段说明（ratelimit.go:20-34）：
  - `mu`：互斥锁，保护 `windows` 映射的读写。
  - `configMu`：`RWMutex`，保护配置读取与 `Reconfigure`。
  - `windows`：键（`RateLimitKey` 生成的不透明串）到 `window` 的内存映射。
  - `windowS` / `maxReqs`：窗口长度（秒）与窗口内最大请求数。
  - `enabled`：`atomic.Bool` 启用标志。
- 并发安全：`Allow`/`Increment` 先以 `configMu` 读配置，再用 `mu` 取/建窗口后立即解锁，最后 `atomic.Int64` 递增，临界区最小（ratelimit.go:96-141）。
- 构造防护：`NewRateLimiter` 在 `windowSec<=0 || maxReqs<=0` 时强制 `enabled=false`，避免 max=0 让首请求即 429（ratelimit.go:36-51）。

| 字段 | 类型 | 位置 | 说明 |
|---|---|---|---|
| `windows` | `map[string]*window` | [ratelimit.go:23](file://internal/waf/ratelimit/ratelimit.go#L23) | 键→窗口 |
| `enabled` | `atomic.Bool` | [ratelimit.go:26](file://internal/waf/ratelimit/ratelimit.go#L26) | 原子启用标志 |
| `window` | struct{atomic.Int64,int64} | [ratelimit.go:31-34](file://internal/waf/ratelimit/ratelimit.go#L31-L34) | 计数+过期 |

### Allow 方法决策逻辑
`Allow` 流程（ratelimit.go:96-118）：
1) `rl==nil` 或未启用或 `windowS/maxReqs<=0` → 返回允许。
2) 取当前 unix 秒，加锁查找窗口；不存在或 `expiry<=now` 则新建 `window{expiry:now+windowS}`。
3) 解锁后 `count.Add(1)`，返回 `n <= maxReqs`。

键由 `reqRateLimitPhase.Execute` 用 `RateLimitKey(ctx.Bind, ctx.SiteID, ctx.Host, ctx.ClientIP)` 生成，形如 `bind|siteID|归一化Host|clientIP`（phases.go:320）。

```mermaid
flowchart TD
Start(["进入 Allow"]) --> Enabled{"启用且参数有效?"}
Enabled --> |否| ReturnTrue["返回允许"]
Enabled --> |是| Lock["加锁查找 windows"]
Lock --> FindWin{"窗口存在且未过期?"}
FindWin --> |否| CreateWin["新建窗口 expiry=now+windowS"]
FindWin --> |是| Unlock["解锁"]
CreateWin --> Unlock
Unlock --> AtomicInc["atomic count.Add(1)"]
AtomicInc --> Compare["n <= maxReqs ?"]
Compare --> ReturnBool["返回是否允许"]
```

### Increment / IsOverLimit / Reconfigure
- `Increment`（ratelimit.go:121-141）：与 `Allow` 同窗口逻辑，返回当前计数，用于错误率统计与 bot 行为分。

- `Reconfigure`（ratelimit.go:80-94）：原子更新 windowS/maxReqs/enabled，非法参数强制禁用。

### cleaner 协程与过期清理机制

### 配置项与后端契约
- `RateLimiterBackend` 接口由本地固定窗口与 Redis 滑动窗口两套实现共享：`Enabled/Reconfigure/Allow/Increment/IsOverLimit/Close`（ratelimit.go:10-17）。本地实现适合单机、延迟更低；Redis 实现适合分布式共享状态（属概念说明，本库以本地实现为准）。

## 性能考虑
- 原子计数：`count.Add(1)` 无锁递增，降低竞争（ratelimit.go:116-117）。
- 最小临界区：仅在取/建窗口时加 `mu`，解锁后再原子操作（ratelimit.go:109-117）。
- 清理策略：30 秒周期回收过期窗口，平衡内存与 CPU（ratelimit.go:176）。
- 键隔离：`RateLimitKey` 含 bind 与 siteID，避免跨站点/跨监听器共享计数导致误限（phases.go:63-70）。
- 可扩展：`RateLimiterBackend` 抽象使本地与 Redis 实现可互换（ratelimit.go:10-17）。

## 故障排查指南
- 限流未生效：确认 `enabled`、`windowS/maxReqs>0`、键构造 `bind|siteID|host|clientIP`（phases.go:63-70）。
- 瞬时峰值误判：固定窗口在边界存在"桶破裂"，可增大窗口或结合其它策略。
- 内存增长：确认 `cleaner` 运行、`stopCh` 未提前关闭（ratelimit.go:164-196）。
- 调试：`IsOverLimit` 只读检查，`Reconfigure` 动态调参验证（ratelimit.go:80-162）。

| 症状 | 原因 | 排查点 |
|---|---|---|
| 首请求即 429 | maxReqs≤0 未拦住 | `NewRateLimiter` 强制禁用逻辑 |
| 限流跨站点串扰 | 键缺 siteID/bind | `RateLimitKey` 组装 |
| bot 阈值疑似减半 | 行为分共用限流键 | `|bot` 后缀独立键 |

## 结论
请求速率限制采用固定窗口算法，以 `RateLimitKey` 实现站点隔离，用原子计数与最小临界区保证高并发稳定。`RateLimiterBackend` 抽象兼容本地与分布式实现，`Reconfigure` 支持热重配。作为链上第 9 位，它在浏览器签名之后、自建规则之前控制频率，并向 bot 行为分供数。
