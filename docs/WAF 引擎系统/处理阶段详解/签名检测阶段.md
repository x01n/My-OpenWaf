## 简介
本文件聚焦 My-OpenWaf 的 `signature` 阶段。它是全 11 阶段链的第 10 位（`ip_reputation → anti_replay → acl → lua_pre → owasp_default → cve_detection → bot_detection → browser_sign → rate_limit → signature → custom`，engine.go:465-548），属于"用户自建规则"类阶段，与末位的 `custom` 阶段共用同一套编译与匹配机制。签名阶段命中后依据动作是否为终端动作决定短路；与 OWASP/CVE 等内置检测阶段相比，它位于其后，用于对已放行的检测流量再做一层特征匹配。

> 订正：OWASP、CVE、Bot、限流均在签名阶段**之前**执行；签名与自定义是链上最后两个阶段。ACL 与签名都走 `executeCompiledPhase`，其 `allowShortCircuit` 形参未被使用，Allow 不短路。签名阶段的规则由 `cr.Signature` 预分区供给，运行期不再按 Phase 过滤。

## 核心组件
- 编译器：`Compile` 过滤启用规则、`ParsePattern` 解析 kind/arg、`buildMatcher` 构建匹配器，按优先级升序、ID 升序排序（compiler.go:39-78）。
- 匹配器：统一实现 `Matcher.Match(ctx MatchCtx) bool`，非法模式回落 `neverMatcher`（matcher.go:21-23、1772-1773）。
- 签名阶段：`executeCompiledPhase(ctx, rules, false, ...)` 顺序遍历，命中首条即返回 `(hit, hit.IsTerminal())`（phases.go:169-171）。
- 引擎：`getOrBuildPhases` 在 `len(cr.Signature) > 0` 时把签名阶段**直接 append** 入链，不包跳过装饰器（engine.go:522-526）。

## 详细组件分析

### 签名阶段执行流程
`Execute` 委托 `executeCompiledPhase`：规则为空返回 `Pass(), false`；否则构造 `MatchCtx` 并顺序匹配，命中首条即返回该规则结果与 `IsTerminal()`（phases.go:112-129）。`allowShortCircuit` 形参在函数体内未被引用（phases.go:112），因此 Allow 命中不短路，请求继续进入 `custom` 阶段。

```mermaid

Ctx --> Loop["顺序遍历已编译规则"]
Loop --> Match{"命中首条?"}
Match --> |否| Pass["返回 Pass(),false"]
Match --> |是| Term{"动作 IsTerminal()?"}
Term --> |是| Stop["返回结果,stop=true 短路"]
Term --> |否 allow/observe| Cont["返回结果,stop=false"]
```

### 与其它检测阶段的区别与协作
- 与 `custom`：两者都用 `Compiled`，但 `custom` 走 `executeCustomPhase` 会内部累积 Observe 命中（phases.go:194-225），`signature` 走 `executeCompiledPhase` 单条命中即返回，Observe 命中由 `pipeline.Run` 统一收集（pipeline.go:523）。
- 与内置检测：OWASP/CVE/Bot/限流在签名之前执行；签名不参与按路径跳过装饰（engine.go:522-526），停用规则本身即可关停。

| 对比维度 | signature | custom |
|---|---|---|
| 链上位置 | 第 10 | 第 11（末位） |
| 执行函数 | executeCompiledPhase | executeCustomPhase |
| Observe 累积 | 由 pipeline 收集 | 阶段内累积多条 |
| 跳过装饰 | 不适用 | 不适用 |

### 规则来源与编译缓存
签名规则与 ACL、custom 同源：引擎 `getCompiledRules` 把快照里的 `CompiledRule` 经 `convertAndCompile` 转为 `rules.Compiled`，并按 `Phase` 预分区到 `cr.Signature`（engine.go:399-410、623-645）。编译结果按 `{siteID,policyID}` 键缓存于 `compiledSnapshot`，同一快照 revision 内每站点至多编译一次（engine.go:34-42、386-431）。

`Compiled` 结构承载运行期所需的全部字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| ID | uint | 规则 ID，排序次键 |
| Phase | string | `signature` 分区依据 |
| Action | action.Type | 命中动作 |
| Priority | int | 排序主键（升序） |
| Kind/Arg | string | 解析后的匹配类型与参数 |
| StatusCode | int | 自定义状态码（0 用默认） |
| RedirectTo | string | 重定向目标 |
| CaptchaType | string | 规则级验证码类型（空继承全局） |
| matcher | Matcher（私有） | 预构建匹配器 |

> `convertAndCompile` 对复合规则把原始 JSON 存于 `Arg` 并以 `{` 前缀识别，非复合规则拼成 `kind:arg` 交 `ParsePattern` 解析（engine.go:625-644、compiler.go:146-170）。

### 与 ACL 阶段的异同
签名与 ACL 都经 `executeCompiledPhase` 顺序命中首条，唯一入参差异是 `allowShortCircuit`（ACL 传 `true`、签名传 `false`），但该形参未被使用，因此两者短路语义完全一致——只有终端动作短路（phases.go:148-150、169-171）。

| 命中策略 | 首条命中即返回 | 首条命中即返回 |

## 性能考虑
- 编译期排序：优先级与 ID 升序，使高优先级规则先匹配、命中即停（compiler.go:71-76）。
- 正则缓存：`cachedCompile` 用全局 `RWMutex` 缓存复用已编译正则，非法模式回落永不匹配（matcher.go:1785-1808）。
- 匹配器短路：AND/OR 在匹配器内部短路（matcher.go:281-307），避免无关子条件继续计算。
- 派生头部按需：仅当含 `tls_alpn`/`header_order_*` 等 kind 时才构造派生字段（phases.go:227-249）。
- 编译缓存复用：签名规则按 `{siteID,policyID}` 缓存，同 revision 每站点至多编译一次，避免热路径重复编译（engine.go:386-431）。
- 分区预置：引擎在缓存阶段即把规则按 `Phase` 分入 `cr.Signature`，运行期 `NewSignaturePhasePrecompiled` 无需再过滤（engine.go:405-406、phases.go:163-165）。

## 故障排查指南
- 规则不生效：确认 `Phase=="signature"`、启用、kind 在 `knownPrefixes` 内（compiler.go:119-142）。
- Allow 未绕过后续：这是预期——签名 Allow 不短路，但签名在链尾，其后仅 `custom`；如需绕过内置检测应在前置阶段处理。
- 正则异常：非法正则回落 `neverMatcher`，检查语法（matcher.go:1791-1808）。
- Observe 记录缺失：签名阶段的 Observe 命中由 pipeline 收集，而非阶段内累积（pipeline.go:523）。
- 规则分区错配：确认规则 `Phase` 为 `signature`；分区在 `getCompiledRules` 完成，错配将导致规则根本不入本阶段链（engine.go:405-406）。

## 结论
签名阶段通过"编译期排序 + 运行期单条命中短路"实现用户自建特征匹配，位于内置检测之后、自定义之前（链上第 10 位）。它与自定义阶段共用编译链路，差异在 Observe 命中收集方式；`allowShortCircuit` 形参已废弃，短路语义统一由 `IsTerminal()` 决定。作为链尾倒数第二站，签名对已放行检测流量做最终特征过滤，命中终端动作即结束整条链。
