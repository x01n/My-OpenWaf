## 简介
动作与结果系统是规则判定与客户端响应之间的唯一契约层，承载三件事：

- **动作建模**：`action.Type` 定义 12 个可用动作加 2 个历史别名，`action.Result` 打包一次判定的全部归因信息
- **终态裁决**：`TerminalPriority` 决定多阶段并发命中时谁胜出，`pipeline.Run` 据此实现"终端立即返回、挑战延迟保留"
- **动作落地**：数据面把最终判定路由到五类出口——TCP 丢弃、拦截页、挑战页、重定向、放行上游

本篇必须强调的项目约定：**挑战类动作是 WAF action，不是状态码页面**。`captcha_challenge` 展示站点/全局配置的验证码类型，`shield_challenge` 走 5 秒盾（PoW + 环境指纹）流程，`chain_challenge` 展示链式步骤，`challenge` 才是不指定形态的 JS 挑战。四者都不得用通用 403 页面代替。

两条常被写错的事实：

- `allow` 与 `observe` **都不是终端动作**，不会短路后续阶段（action.go:168-179）
- 四类挑战动作的优先级**同为 60**，同档取链上先出现者，不存在"验证码比 5 秒盾高"之类的排序（action.go:96-97、pipeline.go:533）

阶段全序见 [处理阶段详解](处理阶段详解/处理阶段详解.md)，匹配器如何产出结果见 [规则匹配器](规则匹配器/规则匹配器.md)。

### Drop 执行与协议级降级
`drop` 的语义是"立即断开 TCP 且不发送任何 HTTP 响应"，但落地路径有四种，且**必须失败可见**：

| 步 | 动作 | 执行位置 | 输入 | 输出 | 失败分支 | 可观测点 |
|:--:|---|---|---|---|---|---|
| 1 | 执行器缺失检查 | [handler.go:664-668](file://internal/dataplane/handler.go#L664-L668) | `dropEnabled(eng)` | 否 → 动作改写为 `intercept` | 403 拦截页 | 事件 `action=intercept` |
| 2 | h2 流重置 | [handler.go:743-745](file://internal/dataplane/handler.go#L743-L745) | `InboundProtocolGuard` | `RST_STREAM(CANCEL)` | 落到下一级 | 响应头无 `X-OWAF-Drop-Degraded` |
| 3 | h3 流重置 | [handler.go:746-748](file://internal/dataplane/handler.go#L746-L748) | 请求上下文 | 流重置 | 落到下一级 | 同上 |
| 4 | 连接关闭 | [handler.go:749-753](file://internal/dataplane/handler.go#L749-L753) | `DropExecutor` 或 `CloseForDrop` | `SetLinger(0)` + `Close` | `dropApplied=false` | 降级分支 |
| 5 | 成功记账 | [handler.go:755-795](file://internal/dataplane/handler.go#L755-L795) | 判定结果 | 事件 `StatusCode:0`、访问日志 `drop`、drop 事件 | 无 | `drop-events` 页面 |
| 6 | 失败降级 | [handler.go:796-849](file://internal/dataplane/handler.go#L796-L849) | 无可关闭连接 | 403 拦截页 + `X-OWAF-Drop-Degraded` | 事件 `MatchDesc` 追加降级原因 | 响应头与事件字段 |

降级原因写在注释里并被固化为响应头：历史行为此处写 502，会让客户端误判为上游故障；当前 fork 未提供 h2 流级重置方法，因此 h2 请求实际恒走降级分支。

`DropExecutor` 侧的三项实现细节：

- 统计按 `DropReason.Source` 分桶，日志限频为"前 16 条 + 每 1024 条一次"（drop.go:61-76）
- `GetStats()` 返回**深拷贝**，`ResetStats()` 清零全部计数与最后时间（drop.go:93-113）
- 分桶 case 是 `"bot"`/`"cve"`/`"rule"`/`"ip_reputation"`，而数据面传入的 `Source` 是**阶段名**（`bot_detection`/`cve_detection`/`acl`/`custom`），因此 `DroppedByBot`、`DroppedByCVE`、`DroppedByRule` 在当前主路径下不会被累加，实际都落进 `DroppedOther`——只有 `ip_reputation` 阶段能对上桶名（drop.go:78-91、handler.go:733-741）

## 性能考虑
- 优先级比较是整数比较，`TerminalPriority` 两次 `switch`（含归一后重算）不构成热点（action.go:88-119）
- 挑战延迟保留让后续更严动作有机会覆盖，代价是该请求多跑若干阶段——这是正确性优先于单次延迟的取舍
- `Result` 的可选输出（`SetHeaders`/`ResponseBody`/`Tags`）用指针表达，避免未启用时的分配
- Drop 日志限频（前 16 条 + 每 1024 条）避免高频丢弃把日志变成瓶颈（drop.go:61-76）
- 分级升级的 Redis 调用带 50ms 超时，失败即回落实数，不会拖慢判定路径（escalation.go:120、164）
- 页面渲染的模板解析在请求期发生（`renderTemplatePage` 对站点自定义 HTML 每次 `template.Parse`），是自定义页面场景下已知的固定成本

## 故障排查指南
- "配置了验证码，出来的却是 403 页"
  - 检查动作是否写成 `intercept` 而非 `captcha_challenge`；`CaptchaManager` 未挂载时会回落 JS 挑战页
  - 检查规则是否显式选了 `captcha_challenge`：泛化 `challenge` 才会被站点/全局 `challenge_action` 覆盖，显式类型不会被顶替（handler.go:889-898）
- "5 秒盾没出现，出现的是普通挑战"
  - `ShieldManager` 未启用时回落 JS 挑战页；确认站点级 `shield_enabled` 与挑战参数已配置
- "drop 之后客户端收到 403"
  - 说明进入了协议级降级分支（h2 无流重置方法或多路复用场景）；看响应头 `X-OWAF-Drop-Degraded` 与事件 `match_desc` 中的 `drop degraded to 403`
  - 若动作直接被改成 `intercept` 且无降级头，则是执行器未启用（`dropEnabled` 为假）
- "drop 统计里 ByBot/ByCVE 一直是 0"
  - 成因是桶名与阶段名不一致：`recordStats` 按 `"bot"`/`"cve"`/`"rule"` 匹配，而传入的是 `bot_detection`/`cve_detection`/`acl`，全部落进 `DroppedOther`（drop.go:78-91、handler.go:734）
  - 需要按来源统计时，应查安全事件的 `phase` 字段而非 `DropStats`
- "ACL 放行没生效"
  - `allow` 不短路是设计行为：ACL 放行只表示该阶段不拦，OWASP/CVE/Bot 仍会判定；要真正终止请求需 `observe` 之外的放行语义请配合阶段跳过配置
- "挑战通过后又弹挑战"
  - 通行 cookie 绑定 IP/UA/Host/SiteID/Bind 五元组，任一项变化（如经不同 CDN 出口）即失效
- "拦截页显示成英文默认页"
  - 站点与全局 HTML 均为空时走 `sn.BlockPage` 配置渲染，配置解析失败会回落 `DefaultBlockPageConfig`
- 验证命令
  - `go test ./internal/core/action/...`：优先级与判定谓词
  - `go test ./internal/core/pipeline/...`：终端/挑战延迟与观察收集
  - `go test ./internal/waf/escalation/...`：档位比较与计数降级

## 结论
动作系统用一套 `Result` 与一组整数优先级，把"多阶段并发命中"这件本质上含糊的事变成了可判定的规则：终端立即返回、挑战延迟比较、同档保留先者、`allow`/`observe` 永不短路。落地层按出口分派并保持三级兜底（自定义 → 全局 → 内嵌），且对页面注入面做了显式净化。两个管道外的修改机制（分级升级、Lua post）都被约束为"只能变严或只能放行误报"，避免了绕过优先级的第二条判定通道。已知需要读者警惕的是三点：挑战类动作必须按具体形态而非通用状态码呈现；`DropStats` 的来源桶名与阶段名不一致导致按来源统计不可用；站点自定义 HTML 每次请求重新解析模板。
