## 简介
本文档解析 My-OpenWaf 的站点解析器实现，涵盖 `Resolver` 结构体设计、`MatchSite`/`MatchSitePtr` 的工作机制、绑定地址与主机头匹配策略、精确/通配/catch-all 三级优先级、多站点与多监听器场景处理、路由冲突的构建期判定、与快照系统的集成方式以及解析结果的实时性保证。

需要先纠正一个常见误解：**站点解析不使用任何前缀树（Trie）**。全库不存在 trie 实现，站点匹配是「哈希表 + 至多三次固定键查找」，键由 `bind + NUL + 规范化 host` 拼成（`snapshot.go:293-296`、`337-362`）。本文所有描述均以 `internal/core/sites/resolver.go` 与 `internal/snapshot/snapshot.go` 的实际实现为准。

### Snapshot.MatchSite 匹配算法
匹配是**至多三次哈希查找**，不做任何树遍历：

| 级 | 构造的键 | 前置条件 | 位置 |
|:--:|---|---|---|
| 1 | `siteMapKeyNorm(bind, host)` | `host` 规范化后非空 | `snapshot.go:343-346` |
| 2 | `siteMapKeyNorm(bind, "*." + 父域)` | `host` 不是 IP 且首个点号不在位置 0 | `snapshot.go:348-355` |
| 3 | `siteMapKeyNorm(bind, "*")` | 站点显式把 `Host` 配成 `*` | `snapshot.go:357-359` |

- 父域取自 `strings.Index(host, ".")`，即只把**第一级标签**替换为 `*`：`a.b.example.com` → `*.b.example.com`，不会继续尝试 `*.example.com`（`snapshot.go:349-351`）。
- 值拷贝 vs 指针：`MatchSite` 返回 `*rt` 的拷贝（`snapshot.go:345`），`MatchSitePtr` 直接返回 map 里的指针（`snapshot.go:381`），后者要求调用方在请求期内不改写指向内容（`snapshot.go:364-372`）。

#### 匹配优先级规则
1. **精确匹配**优先：第一级键命中即返回，不再尝试通配（`snapshot.go:343-346`）。
2. **单级通配**次之：仅替换第一级标签，且 IP 字面量主机不参与通配（`snapshot.go:348-355`）。
3. **catch-all** 最后：`Host` 配成 `*` 的站点在第三级命中（`snapshot.go:357-359`）。
4. 三级查找**始终限定在同一 `bind` 前缀内**，不存在跨监听地址回退。
5. `TLSCertificateStateForSNI` 使用同一优先级顺序，保证「站点命中」与「证书取值」一致（`snapshot.go:302-335`）。

### 多站点场景处理
系统支持复杂的多站点场景，键空间全部在构建期展开：

#### 多绑定地址场景
- 站点可配置多个监听器，`Build` 为每个**启用的** listener 生成一条独立的 `SiteRuntime`，并把 `rt.Bind` 覆写为该 listener 的 bind（`build.go:309-330`）。
- 没有 listener 行且站点 `Bind` 非空时，会用站点自身的 bind 合成一条默认监听记录（`build.go:310-319`）。
- 匹配时 bind 是键的前缀，因此天然限定在同一监听地址内。

#### 多主机头场景
- `Site.Host` 按逗号切分，每个非空 host 生成一个独立映射键（`build.go:787-794`、`splitHosts` 于 `build.go:812-822`）。
- 每个 host 在写入前都会过一遍 `NormalizeMatchHost`（`build.go:790`）。
- 上游地址为空的站点会被整体跳过，不进入键空间（`build.go:261-264`）。

#### 域名冲突处理
| 情形 | 判定 | 结果 | 位置 |
|---|---|---|---|
| 同站点重复声明同一键 | `existing.Site.ID == rt.Site.ID` | 幂等跳过 `continue` | `build.go:795-797` |
| 不同站点争用同一键 | 两个不同 `Site.ID` | 返回 `duplicate site route` 错误 | `build.go:798-799` |
| 本次 reload 的后续处理 | `Build` 返回 error | 重载失败，**旧快照继续生效** | `runtime.go:246-249` |

- 与「first-come-first-served」不同：冲突不是被静默忽略，而是让整次快照构建失败，从而强制配置唯一性。

#### 实时性保证机制
- **原子切换**：`Holder.StoreIfNewer` 用 CAS 循环发布新快照，只接受更高代次（`snapshot.go:474-487`）。
- **每次调用重取**：`Resolver.Match` 与 `MatchPtr` 都在函数内 `holder.Load()`，不缓存快照指针，因此不存在「解析器还看到旧映射」的窗口（`resolver.go:25`、`34`）。
- **不可变性**：`Snapshot` 一次构建全程只读，请求期不改写任何字段（`snapshot.go:207-212`）。
- **键空间稳定**：`siteMapKeyNorm` 只做字符串拼接，不做分配以外的规范化处理，规范化在写入与查找两侧各由 `NormalizeMatchHost` 保证（`snapshot.go:293-296`、`409-439`）。

- **低耦合**：`Resolver` 只持有 `*snapshot.Holder` 一个具体类型指针，`resolver.go` 的 import 段只有 `My-OpenWaf/internal/snapshot` 一项（`resolver.go:3-5`）。

## 结论
My-OpenWaf 的站点解析器由 44 行的 `Resolver` 薄封装与快照内约 60 行的查找实现组成：哈希键、至多三级回退、每次调用重取快照。它不依赖前缀树，也不需要前缀树——键空间大小由站点与监听器数量界定，三级固定查找把开销压到常数。精确优先于通配、通配优先于 catch-all，跨 bind 永不回退，路由冲突在构建期直接失败而非静默覆盖，这些取舍共同保证了虚拟主机解析的确定性与可运维性。
