## 简介
本文件系统性阐述快照系统的理念、实现与工程实践，覆盖以下关键主题：
- 快照模式的设计与不可变性保障
- 快照版本管理与 `Revision` 字段的作用
- 快照构建流程：从原始配置到最终运行时配置的转换
- 变更检测与热重载：代次递增、进程内缓存命中与两级引擎缓存失效
- 引擎中的作用：如何确保配置更新的原子性与一致性
- 构建期配置诊断的分流策略
- 提供代码位置，帮助定位实现细节

### 快照结构与不可变性
`Snapshot` 的关键字段与语义：

| 字段 | 类型 | 位置 | 语义 |
|---|---|---|---|
| `Revision` | `uint64` | `snapshot.go:214` | 代次守卫，驱动引擎两级缓存失效 |
| `Sites` | `map[string]*SiteRuntime` | `snapshot.go:216` | 键为 `bind + NUL + 规范化 host` |
| `Protection` | `store.ProtectionConfig` | `snapshot.go:230` | 从 `SystemSettings` 加载的全局防护配置 |
| `SiteTLSCertBySNI` | `map[string]tls.Certificate` | `snapshot.go:226` | 键由 `SNICertKey` 生成 |
| `SiteTLSCertStateBySNI` | `map[string]TLSCertificateState` | `snapshot.go:227` | `valid`/`unconfigured`/`invalid` |
| `LuaPlugins` / `LuaPluginErrors` | `[]*Script` / `map` | `snapshot.go:238-240` | 构建期编译，单脚本失败不影响整体 |
| `ConfigDiagnostics` | `[]SnapshotConfigDiagnostic` | `snapshot.go:248` | 构建期跳过的无效配置，随快照原子发布 |

- 不可变性保障：一次构建、全程只读，请求期不改写任何字段，reload 只是换指针（`snapshot.go:207-212`）。
- 读取入口：`Holder.Load()` 单次原子加载（`snapshot.go:489`）；`Resolver` 只在该 holder 上做薄封装（`resolver.go:14-44`）。
- 发布入口：`StoreIfNewer` 用 CAS 循环保证不会用旧代次覆盖新代次（`snapshot.go:474-487`）；`Store` 是无条件发布，仅供初始化使用（`snapshot.go:456-464`）。

### 版本管理与变更检测
- 配置修订号：单行表 `config_revisions`（`store.ConfigRevision`，`system.go:30-34`），`BumpRevision` 递增（`migrate.go:141-150`）；读取路径用 `FirstOrCreate` 保证首次也有行（`runtime.go:283-289`）。
- 缓存命中：`ReloadSnapshotWithPrePublish` 先 `GetSnapshot(rev)`，命中后仍会**再次核对** `currentRevision` 未变才发布（`runtime.go:223-245`）。
- 竞态处理：整个重载过程包在 `for` 循环里，任何一次核对发现代次被并发推进就 `continue` 重来（`runtime.go:218-273`）。
- 前置发布钩子：`prePublish` 在新一代对请求处理器可见之前执行，返回错误时当前已发布快照保持不变（`runtime.go:205-211`、`231-235`）。
- Redis 同步：频道固定为 `openwaf:config:reload`，消息体带 `source_id` 用于回环抑制（`pubsub.go:16-22`、`64-82`）。

| 机制 | 取值/位置 | 说明 |
|---|---|---|
| 修订号表 | `config_revisions`，`system.go:30-34` | 单行 `ID=1`，`Revision` 单调递增 |
| 递增入口 | `migrate.go:141-150` | 由 `reloadRuntime(propagate=true)` 调用 |
| 读取入口 | `runtime.go:283-289` | `FirstOrCreate` 兜底建行 |
| 重载互斥 | `reloadMu`，`runtime.go:33`、`212` | 同进程串行化 reload |
| 发布判据 | `StoreIfNewer`，`snapshot.go:474-487` | 只接受更高代次 |
| 缓存键 | `snapshot:{rev}`，`layer.go:41-48` | 进程内 ristretto |
| 同步频道 | `openwaf:config:reload`，`pubsub.go:16` | 跨节点广播 |
| 回环抑制 | `event.SourceID == cs.sourceID`，`pubsub.go:114-116` | 自身发起的广播不再重载 |
| 发布超时 | 2 秒，`pubsub.go:77` | 失败仅告警不阻塞 |

## 性能考虑
- 快照与原子指针：读路径只有一次 `atomic.Pointer.Load()`，写路径仅在重载时持有 `reloadMu`，适合读多写极少（`snapshot.go:489`、`runtime.go:212`）。
- 进程内缓存：同代次快照命中 `cache.Layer`，省掉全表读取与编译（`runtime.go:223-245`、`layer.go:54-62`）。
- 缓存参数：`NumCounters=1e4`、`MaxCost=1<<20`、`BufferItems=64`，写入后 `Wait()` 保证立即可读（`layer.go:30-34`、`50`）。
- 监听器隔离：只重启指纹漂移的 bind，其余实例保持（`server.go:771-777`）。
- 上游连接池收敛：仅当上游端点集合变化时才关闭空闲传输（`server.go:890-895`）。
- Redis 通知降级：发布带 2 秒超时且失败仅告警，不阻塞主流程；客户端为 nil 时 `PublishReload` 直接返回（`pubsub.go:65-82`）。

## 结论
快照系统通过不可变视图与原子指针实现了配置更新的原子性与一致性：`Build` 是配置生效的唯一入口，`Holder.StoreIfNewer` 保证只接受更高代次，`cache.Layer` 让同代次重载免于重复构建，`reconcileListeners` 把影响面收敛到指纹漂移的 bind。构建期的致命错误与可跳过项分流，使单个可选能力的配置错误不会拖垮整个控制面。
