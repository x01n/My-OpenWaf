## 简介

规则编译缓存是 My-OpenWaf WAF 引擎中的关键性能组件，用于避免每个请求重复执行「规则 DSL 解析 + 匹配器构建 + 排序」这一昂贵开销。本文档说明其真实实现：`compiledRules` 的三分区结构、`compiledSnapshot` 的不可变快照形态、`getCompiledRules` 的无锁读与写时复制、缓存键的实际构成，以及与阶段链缓存、快照代次之间的协同关系。

需要澄清的一点：引擎侧的规则缓存**没有 LRU、没有淘汰参数、没有命中率指标**，它靠「快照代次整体切换」来失效；带 `NumCounters`/`MaxCost`/`BufferItems` 的是另一层——进程内快照缓存 `cache.Layer`（`layer.go:29-39`）。两者常被混为一谈，本文分节说明。

### compiledRules 三分区结构

`getCompiledRules` 把编译结果按 `Compiled.Phase` 分到三个桶，供阶段链直接构造阶段：

| 分区 | 字段 | 来源 Phase | 消费的构造函数 | 位置 |
|---|---|---|---|---|
| ACL | `cr.ACL` | `"acl"` | `rules.NewACLPhasePrecompiled` | `engine.go:402-404`、`486-488` |
| Signature | `cr.Signature` | `"signature"` | `rules.NewSignaturePhasePrecompiled` | `engine.go:405-406`、`524-526` |
| Custom | `cr.Custom` | `"custom"` | `rules.NewCustomPhasePrecompiled` | `engine.go:407-408`、`527-529` |

- 其余 `Phase` 取值（`rate_limit`、`owasp_default`）不来自用户规则，因此 `switch` 分支不落入这三桶（`engine.go:401-410`、`policy.go:29-35`）。

### getCompiledRules 方法实现

| 步 | 动作 | 执行位置 | 输入 | 输出 | 说明 |
|:--:|---|---|---|---|---|
| 1 | 读代次 | `engine.go:387` | `sn.Revision` | `rev` | 缓存代次守卫 |
| 2 | 组装键 | `engine.go:388` | `rt.Site.ID`、`rt.PolicyID` | `compiledRulesKey` | 结构体键，非位运算 |
| 3 | 无锁快路径 | `engine.go:391-396` | `compiledPtr.Load()` | 命中返回 `*compiledRules` | 代次相符才认命中 |
| 4 | 编译 | `engine.go:399` | `rt.Rules` | `[]rules.Compiled` | 每站点每代至多一次 |
| 5 | 分区 | `engine.go:400-410` | `Phase` 字段 | `compiledRules` | 三分桶 |
| 6 | 写锁 | `engine.go:413` | — | 临界区 | 串行化发布 |

#### 缓存键生成机制

| 要素 | 取值 | 位置 |
|---|---|---|
| 键类型 | `compiledRulesKey` 结构体 | `engine.go:34-37` |
| 字段一 | `siteID uint`，来自 `rt.Site.ID` | `engine.go:388` |
| 字段二 | `policyID uint`，来自 `rt.PolicyID` | `engine.go:388` |
| 代次 | 不在键内，置于快照的 `revision` 字段 | `engine.go:40` |
| map 类型 | `map[compiledRulesKey]*compiledRules` | `engine.go:41` |

按站点分键的原因：同一策略在不同站点可能配套不同的站点级 CC 规则，构建期会把 `siteCCRules` 追加进该站点的规则集合（`build.go:275`），因此不能只按策略缓存。

#### 版本检查与失效机制

| 检查项 | 判据 | 不满足时 | 位置 |
|---|---|---|---|
| 快路径代次 | `snap.revision == rev` | 视为未命中，走编译 | `engine.go:392` |
| 写侧代次 | `current.revision != rev` | 整表重建而非清理单条 | `engine.go:416-418` |
| 阶段链保护配置 | `entry.prot == prot` | 重建链 | `engine.go:461` |
| 阶段链 Lua 代次 | `entry.luaRevision == luaRevision` | 重建链 | `engine.go:461` |
| 阶段链依赖体 | `entry.deps == deps` | 重建链 | `engine.go:461` |

- 失效策略是「整代替换」：新代次的第一次访问会建立一张只含自身条目的新 map，旧代条目随旧快照一起被垃圾回收，不存在逐条淘汰（`engine.go:416-427`）。
- 之所以阶段链要额外比 Lua 代次：脚本增删改时快照 `revision` 可能不变，只比代次会让缓存留下过期链（`engine.go:44-51`）。

### 规则编译器工作流程

`rules.Compile` 的每步都是可核对的（`compiler.go:40-78`）：

| 步 | 动作 | 执行位置 | 失败处理 |
|:--:|---|---|---|
| 1 | 过滤停用规则 | `compiler.go:43-45` | 直接跳过 |
| 2 | 解析 pattern | `compiler.go:46` | `kind` 为空则跳过 |
| 3 | 校验 kind/arg | `compiler.go:51` | 有错误则降级 `neverMatcher` |
| 4 | 构建匹配器 | `compiler.go:52` | 见 `buildMatcher` |
| 5 | 填充元数据 | `compiler.go:54-69` | `ruleIDStr`、`matchDesc`、`runtimeAction` |
| 6 | 排序 | `compiler.go:71-76` | `Priority` 升序，同优先级按 `ID` 升序 |

- `ParsePattern` 把以 `{` 开头的 pattern 判为 `compound`，其余按首个冒号切分并校验前缀是否在 `knownPrefixes` 白名单内（`compiler.go:119-142`、`146-170`）。
- `neverMatcher` 保证坏规则「保留但不命中」，而不是让整条链失效（`compiler.go:50-53`、`matcher.go:504-508`）。
- `ensureCompiledMetadata` 只在缓存来的条目缺元数据时才复制切片补齐，避免热路径无谓分配（`compiler.go:87-115`）。

#### 复合条件与频次限制

复合规则以 JSON 表达式树承载，`parseCompoundJSON` 递归构造 `and`/`or`/`not`/`if_else`/`cc_rate` 匹配器（`matcher.go:1810-1825`、`1878`）。规则级频次限制在**快照构建期**就被包装成 `cc_rate` 节点：`WindowSeconds` 与 `RequestCount` 同时大于 0 时生效，已是复合 JSON 的 pattern 不重复嵌套（`build.go:927`、`938-950`）。

### 与快照系统的协同

快照层与引擎层各编译一次，职责不同：

| 阶段 | 执行位置 | 产物 | 是否含匹配器 |
|---|---|---|:--:|
| 构建期编译 | `build.go:920-936` | `snapshot.CompiledRule`（`Kind`/`Arg` 文本） | 否 |
| 引擎期编译 | `engine.go:625`、`compiler.go:40` | `rules.Compiled`（含 `matcher`） | 是 |

- 引擎入口 `convertAndCompile` 会用 `Kind + ":" + Arg` 还原 pattern；`compound` 规则例外，直接把原始 JSON 当 pattern 返回（以 `{` 开头）（`engine.go:623-646`、`compiler.go:152-154`）。
- 重载时 `Runtime.ReloadSnapshotWithPrePublish` 先读 `currentRevision`，再 `cache.Layer.GetSnapshot(rev)`；命中则直接 `StoreIfNewer`，未命中才 `snapshot.Build` 并回写缓存（`runtime.go:211-274`）。
- 每次重载都会用新 `Revision` 构造新快照对象，因此引擎两级缓存的代次守卫会同时失效（`snapshot.go:214`、`engine.go:392`、`engine.go:460`）。

## 性能考虑

### 缓存收益与代价

| 机制 | 收益 | 代价 | 位置 |
|---|---|---|---|
| 代次守卫 | 热路径单次 `Load()` | 代次变更后首请求要重建整表 | `engine.go:391-396` |
| 按站点分键 | 站点级规则差异可缓存 | 站点数放大条目数 | `engine.go:34-37`、`388` |
| 三分区 | 构造阶段免过滤 | 需 `ensureCompiledMetadata` 补元数据 | `engine.go:400-410`、`compiler.go:87-115` |
| 构建期正则编译 | 请求期零正则解析 | 正则内存常驻至代次结束 | `matcher.go:1785-1808` |
| 写时复制发布 | 读者永远看到一致快照 | 每次未命中复制整张 map | `engine.go:413-428` |
| 阶段链预分配 | 免扩容 | 容量常量需与最大链长同步 | `engine.go:467` |

- 编译成本只在「每个站点、每个快照代次」至多发生一次（`engine.go:398` 注释）；稳态下所有请求走快路径。
- 规则缓存本身无淘汰与容量参数：map 大小由「站点数 × 策略数」界定，代次切换即整体丢弃，因此不需要 LRU（`engine.go:416-427`）。
- 只有进程内**快照**缓存带 ristretto 参数（`NumCounters=1e4`、`MaxCost=1<<20`、`BufferItems=64`，`layer.go:30-34`），其容量是「快照对象个数」而非规则数。

### 调优建议

1. 控制站点差异化配置的数量：同一策略被尽量多站点共用，可让 `policyID` 相同的站点复用同一条目结构（键仍按站点区分，见 `engine.go:388`）。
2. 避免高频 reload：每次 `store.BumpRevision` 都会使两级缓存整体作废（`migrate.go:141-150`、`runtime.go:219-270`）。
3. 保持规则 `Enabled` 与 `Priority` 稳定：`Compile` 每次全量重排（`compiler.go:71-76`）。
4. 谨慎使用复合规则嵌套层数：`buildCompound` 为递归构造，深度直接影响单次编译耗时（`matcher.go:1878`）。

## 故障排查指南

| 症状 | 可能原因 | 诊断步骤 | 解决方案 |
|---|---|---|---|
| 规则改动不生效 | 快照代次未变，缓存仍命中 | 核对 `sn.Revision` 是否变化（`engine.go:387`） | 确认 `BumpRevision` 被调用并重载 |
| 阶段链是旧的 | 保护配置指针未变 | 检查 `rt.EffectiveProtection` 是否重建（`engine.go:354-357`） | 让构建期产出新的 `ProtectionConfig` |
| Lua 改动不生效 | 只比代次不够 | 打印 `lp.Revision()`（`engine.go:452-455`） | 确认脚本重载会推进 Lua 代次 |
| 编译耗时异常升高 | 大量站点同时首次访问 | 观察未命中是否集中在 reload 后 | 预热关键站点或降低 reload 频率 |
| 规则永不命中 | pattern 校验失败被降级 | `validateParsedPattern` 返回值（`validate.go:36`、`compiler.go:51-53`） | 修正 kind/arg 组合 |
| 规则被静默丢弃 | `Enabled=false` 或 `ParsePattern` 返回空 kind | `compiler.go:43-49` | 启用规则或修正 pattern 前缀 |
| 内存不回落 | 旧代快照被在途请求持有 | 检查 reload 是否在高峰期密集发生 | 降低 reload 频率，复用同代配置 |

## 结论

规则编译缓存用「结构体键 + 代次守卫 + 无锁读 + 写时复制发布」四个手段，把昂贵的 DSL 解析与匹配器构造压缩到「每站点每代至多一次」。它与阶段链缓存共享同一失效语义，差别在于阶段链条目额外携带保护配置指针、Lua 引擎与 Lua 代次、依赖打包体指针四项判据，以覆盖「快照代次不变但插件已更新」这一场景。规则缓存不设淘汰策略，容量由站点与策略的组合数天然界定；带容量参数的是进程内快照缓存 `cache.Layer`，二者不应混淆。
