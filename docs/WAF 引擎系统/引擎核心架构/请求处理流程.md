## 简介
本文面向请求处理流程，系统性阐述引擎如何处理单个 HTTP 请求的完整生命周期：从站点解析、上下文构造、阶段链执行到最终动作分派的每个步骤；深入解释 `Engine.Process` 与 `Engine.ProcessResolved` 的实现差异；阐明 `RequestCtx` 上下文的作用与传递机制、`ProcessResult` 的构成；给出关键路径的代码位置，覆盖维护模式、无站点匹配、降级与上游失败等异常场景，并总结缓存与对象池带来的性能收益。

## 详细组件分析

### 请求匹配站点配置（虚拟主机与绑定地址）
- 匹配策略：站点映射是哈希表，键由 `bind + "\x00" + 规范化 host` 组成（`snapshot.go:294-296`）。查找固定尝试三把键，不做任何树形遍历：

| 级 | 尝试键 | 条件 | 位置 |
|:--:|---|---|---|
| 1 | `bind + NUL + host` | 精确命中 | `snapshot.go:343-346` |
| 2 | `bind + NUL + "*." + 父域` | host 非 IP 且含点号 | `snapshot.go:348-355` |
| 3 | `bind + NUL + "*"` | 站点显式配置 `Host` 为 `*` 的 catch-all | `snapshot.go:357-359` |

- 归一化：`NormalizeMatchHost` 做小写化、去首尾空白、剥离纯数字端口；已规范化的输入走零分配快路径（`snapshot.go:409-439`）。
- 键空间来源：构建期按逗号拆分站点 `Host`，为每个 (bind, host) 写入映射；不同站点争用同一键时 `registerSiteKeys` 直接返回错误使本次快照构建失败（`build.go:787-804`）。
- 与 TLS 的一致性：`TLSCertificateStateForSNI` 采用与站点匹配相同的精确 → 通配 → catch-all 优先级，避免「站点命中 A、证书取到 B」（`snapshot.go:312-335`）。
- 绑定地址：每个站点可有多个监听器，构建期为每个启用的 listener 生成独立站点条目，因此匹配严格限定在同一 bind 内，不会跨 bind 回退（`build.go:309-330`）。

### 动作分派与响应渲染
数据面拿到 `ProcessResult` 后按动作类型分派，全部判定谓词来自 `action.Result`（`action.go:168-203`）：

| 序 | 判定 | 执行位置 | 渲染/动作 | 状态码 | 短路 |
|:--:|---|---|---|---|:--:|
| 1 | `Maintenance` | `handler.go:632-643` | `WriteMaintenanceResponse` | 站点/全局配置，缺省 503 | 是 |
| 2 | 质询 cookie 已有效 | `handler.go:646-657` | 降级为 `Pass` | — | 否 |
| 3 | `IsDrop()` 且执行器可用 | `handler.go:713-820` | 关闭 TCP | 0 | 是 |
| 4 | `IsDrop()` 但执行器不可用 | `handler.go:664-668` | 降级为 `intercept` | 403 | 是 |
| 5 | `IsChallenge()` | `handler.go:852-931` | 按渲染动作分派验证码/5 秒盾/链式/JS | 403 或自定义 | 是 |
| 6 | `IsRedirect()` | `handler.go:934-973` | `c.Redirect` | 302 或自定义 | 是 |
| 7 | 其余终端动作 | `handler.go:976-1024` | `WriteBlockResponse` | `ResponseStatusCode()` | 是 |
| 8 | 非终端 | `handler.go:1027-1220` | 代理转发上游 | 上游返回码 | 否 |

- 质询渲染只允许站点/全局 `challenge_action` 覆盖泛化 `challenge`，规则显式选择的 `captcha_challenge`/`shield_challenge`/`chain_challenge` 不被顶替（`handler.go:889-927`）。

## 性能考虑
- 对象池与内存：`RequestCtx` 来自 `sync.Pool`，请求结束成对归还（`handler.go:340`、`handler.go:387`）；归还时按容量上限重建 map/slice，避免峰值后 RSS 不回落（`pool.go:10-17`）。
- 扫描上限：请求体进入上下文时截断到 48 KB，与快照常量 `WAFBodyScanLimit` 一致（`handler.go:377-385`、`snapshot.go:493`）。
- 每请求缓存：`BodyTargets`、JSON 主体、查询值、匹配器请求头、派生 ALPN/头顺序/密码套件均带 Done 标记，跨阶段只算一次（`pipeline.go:53-100`）。
- 缓存复用：规则与阶段链各一次 `atomic.Pointer.Load()` 即命中，热路径无锁（`engine.go:391`、`engine.go:459`）。
- 零拷贝匹配：`MatchSitePtr` 直接返回 map 中的指针；数据面复用已解析结果，避免第二次匹配与值拷贝（`snapshot.go:364-398`、`engine.go:564-572`）。
- 快路径归一化：`NormalizeMatchHost` 在输入已规范化时原样返回，不产生分配（`snapshot.go:409-421`）。

## 结论
My-OpenWaf 的请求处理以“站点级监听 + 数据面中间件 + WAF 引擎 + 阶段链”为核心，具备完善的站点匹配、维护与阻断页面、异步事件记录、指标采集与上游转发能力。通过不可变快照、两级无锁缓存、上下文对象池与严格的短路策略，既能保障性能，又能灵活扩展防护能力。关键取舍是把「已解析的站点」沿调用链透传（`ProcessResolved`），使每请求只做一次哈希查找。
