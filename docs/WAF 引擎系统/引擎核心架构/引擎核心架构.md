## 简介
本文件面向引擎核心架构，系统化阐述 WAF 引擎 Engine 的设计与实现，重点覆盖以下方面：
- 站点解析器：基于快照的站点匹配与路由
- 规则编译器：规则 DSL 到可执行匹配器的转换
- 管道执行器：阶段链的构建、执行顺序与短路机制
- 快照系统：配置不可变性与热重载
- 请求处理全流程：从站点匹配到最终动作决策
- 性能优化策略与故障排查

目标是帮助读者在不深入源码细节的前提下，理解引擎如何以“快照 + 缓存 + 管道”的方式实现高吞吐、低延迟、可热重载的 WAF 处理。

## 架构总览
引擎以“快照 + 缓存 + 管道”为核心设计，分层与依赖方向如下：

| 层 | 组成 | 核心职责 | 允许依赖 | 禁止依赖 | 代表位置 |
|---|---|---|---|---|---|
| 接入层 | 数据面监听器与中间件 | 协议解析、请求上下文构造 | 引擎层 | 直接读数据库 | `internal/dataplane/handler.go:39` |
| 编排层 | `Engine` | 解析站点、取缓存、跑管道 | 快照层、规则层 | 接入层对象 | `internal/core/engine/engine.go:551` |
| 执行层 | `pipeline` + 各 `Phase` | 顺序判定与短路 | 动作层、WAF 能力包 | 快照写路径 | `internal/core/pipeline/pipeline.go:517` |
| 配置层 | `Snapshot`/`Holder`/`Layer` | 不可变视图与原子切换 | `store` 模型 | 请求期反查 DB | `internal/snapshot/snapshot.go:453` |
| 构建层 | `Build`/`Runtime.ReloadSnapshot` | DB→快照一次性解析编译 | `store`、`cache` | 请求热路径 | `internal/snapshot/build.go:47` |

- 快照：从数据库构建不可变配置视图，通过 `Holder.StoreIfNewer` 原子替换（`snapshot.go:474-487`）
- 编译缓存：键为 `{siteID, policyID}`，以快照 `Revision` 为代次守卫（`engine.go:34-42`）
- 阶段缓存：键为 `{policyID, siteID, antiReplayEnabled}`，另需匹配防护配置指针、Lua 引擎与 Lua 代次（`engine.go:60-64`、`461`）
- 管道执行：严格顺序执行，终端动作短路、挑战类延迟比较（`pipeline.go:517-560`）

## 详细组件分析

### 引擎 Engine 设计与职责
- 职责边界
  - 站点解析：`Process` 内部经 `resolver.Snapshot()` 取快照，再调 `MatchSitePtr`（`engine.go:551-562`）
  - 规则编译：`getCompiledRules` 按 `{siteID, policyID}` 缓存 `*compiledRules`（`engine.go:386-431`）
  - 阶段构建：`getOrBuildPhases` 按站点有效保护配置动态组装阶段链（`engine.go:441-548`）
  - 管道执行：调用 `pipeline.Run` 执行阶段链，返回最终动作（`engine.go:363`）
  - 辅助能力：IP 信誉、GeoIP 阈值、CVE 检测器、防重放、分级升级挂载点（`engine.go:161-215`、`603-621`）

- 关键数据结构

| 符号 | 定义位置 | 签名/字段 | 职责 |
|---|---|---|---|
| `Engine` | `engine.go:83-113` | `struct{resolver; phaseDeps atomic.Pointer; compiledPtr; phasesPtr; luaPlugins; jsPlugins}` | 编排入口与缓存宿主 |
| `compiledRules` | `engine.go:26-30` | `ACL / Signature / Custom []rules.Compiled` | 按阶段分区的已编译规则 |
| `compiledRulesKey` | `engine.go:34-37` | `{siteID, policyID uint}` | 编译缓存键 |
| `phasesCacheKey` | `engine.go:60-64` | `{policyID, siteID uint; antiReplayEnabled bool}` | 阶段链缓存键 |
| `phasesEntry` | `engine.go:52-58` | `{prot, lua, luaRevision, deps, phases}` | 缓存条目与有效性判据 |
| `phaseRuntimeConfig` | `engine.go:75-80` | `{reqRateLimiter, antiReplay, geoResolver, botThreshold}` | 阶段链依赖的不可变打包体 |
| `ProcessResult` | `engine.go:324-329` | `{Action, Site, ObserveHits, Maintenance}` | 单次请求最终输出 |

- 并发模型：读侧一律 `atomic.Pointer.Load()`，无锁；写侧由 `compiledWriteMu`/`phasesWriteMu` 串行化后做写时复制再 `Store`（`engine.go:98-103`、`413-428`、`532-545`）。运行时依赖（限流后端、防重放、GeoIP、bot 阈值）通过 `updatePhaseDeps` 的 CAS 循环整体原子替换（`engine.go:146-158`）。

- 维护模式与短路：全局 `Protection.MaintenanceGlobalEnabled` 或站点 `rt.MaintenanceEnabled` 命中时，直接返回 `intercept` 且 `Maintenance=true`，不进入管道（`engine.go:337-348`）。

### 管道执行器 Pipeline
- 接口与数据结构
  - `Phase` 接口：`Name() string` 与 `Execute(ctx *RequestCtx) (action.Result, bool)`（`pipeline.go:277-280`）
  - `RunResult`：`{Action, ObserveHits}`（`pipeline.go:494-497`）
  - `RequestCtx`：承载请求解码数据与各类每请求缓存（`pipeline.go:15-100`）

- 执行语义（`pipeline.go:517-560`）

| 情形 | 阶段返回 | 管道行为 |
|---|---|---|
| 未命中 | `stop=false`，`Matched=false` | 进入下一阶段 |
| 观察命中 | `stop=false`，需记日志且非终端 | 追加进 `ObserveHits`，继续 |
| 非终端短路 | `stop=true` 且非挑战 | 立即返回该结果 |
| 挑战短路 | `stop=true` 且为挑战 | 暂存，继续执行后续阶段 |
| Drop | `Matched && IsDrop()` | 立即返回，不再评估 |
| 其他终端 | `IsTerminal()` 且非挑战 | 立即返回 |

- 终端优先级取自 `action.TerminalPriority`（`action.go:88-119`）：`drop=90 > intercept=80 > rate_limit=70 > 挑战族=60 > redirect=50 > observe=10`，仅当更高优先级时才替换已暂存的挑战。
- 热路径优化：`Run` 直接遍历阶段切片，不额外分配 `Pipeline` 包装（`pipeline.go:508-517`）；观察命中复用 `ctx.observeHitsBuf`，避免每请求分配（`pipeline.go:518`、`pool.go:25`）。管道本身无锁，阶段链为每请求只读切片。

## 性能考虑
- 编译与缓存
  - 规则编译昂贵，按 `{siteID, policyID}` 与快照代次缓存；revision 变化时整表重建（`engine.go:386-431`）
  - 阶段链同样缓存，命中判据含保护配置指针、Lua 引擎、Lua 代次与依赖打包体指针（`engine.go:461`）
- 管道执行
  - `Run` 直接遍历切片、复用观察缓冲，避免每请求分配（`pipeline.go:517-518`）
  - 终端优先级比较与挑战延迟在热路径内完成，无额外数据结构（`pipeline.go:533-552`）
- 匹配器优化
  - 全局正则编译缓存（`matcher.go:1791-1808`）
  - `MatchCtx` 的派生请求头（ALPN、密码套件、头顺序）按 `needsDerivedHeaders` 惰性计算并缓存（`phases.go:72-104`、`pipeline.go:232-257`）
- 上下文复用
  - `RequestCtx` 经 `sync.Pool` 复用，超过容量上限时重建，避免峰值后 RSS 不回落（`pool.go:12-17`、`37-113`）
- 快照与热重载
  - 快照不可变、原子替换，读路径零锁（`snapshot.go:453-489`）
  - 同修订号快照命中 ristretto 缓存，避免重复构建（`layer.go:44-62`、`runtime.go:223-245`）

## 结论
引擎通过“快照 + 编译缓存 + 阶段缓存 + 管道执行”的组合，实现了高吞吐、低延迟、可热重载的 WAF 处理框架。其关键优势在于：
- 不可变快照与 `StoreIfNewer` 保证一致性与原子切换
- 两级缓存以原子指针读取、写时复制发布，热路径无锁
- 管道短路与挑战延迟机制兼顾安全强度与用户体验
- 阶段链按站点有效配置动态装配，能力开关互不影响
