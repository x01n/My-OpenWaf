## 简介
本篇是复合匹配器的**唯一**实现文档，逐 kind 的内置匹配器篇目不再单独承载复合条件。它覆盖三件事：

- **逻辑组合**：`and` / `or` / `not` 三种布尔组合如何递归构建成匹配器树
- **条件分支与取反**：`if` / `if_else` / `ifelse` 三分支语义，以及 UI `ne` 映射专用的 `exactNotMatcher`
- **频次限制**：`cc_rate` 的窗口累计、阈值触发、阻断持续期与跨请求共享状态

复合条件是规则 DSL 的第二种形态：`Pattern` 以 `{` 开头即判为 `kind="compound"`，`arg` 保留原始 JSON（compiler.go:152-154）。运行期求值发生在**构造期的同一棵树上**，因此不存在解释器或 AST 二次解析。

必须与旧描述区分的三点：

- `Matcher` 签名是 `Match(MatchCtx) bool`（matcher.go:21-23）
- `cc_rate` 的计数键是 `bind|siteID|host|clientIP`（`RateLimitKey`，phases.go:63-70），**不是** "IP + Host"
- 非法结构一律回落 `neverMatcher`，没有 `alwaysMatcher`

## 详细组件分析

### AND / OR / NOT 的短路真值
三种布尔节点的求值语义与真值边界：

| 节点 | 求值实现 | 空集合结果 | 短路点 | 位置 |
|---|---|:--:|---|---|
| `andMatcher` | 顺序遍历，任一 false 立即 false | **false**（`len(children) > 0` 是必要条件） | 首个 false 子节点 | matcher.go:283-290 |
| `orMatcher` | 顺序遍历，任一 true 立即 true | false | 首个 true 子节点 | matcher.go:294-301 |
| `notMatcher` | 对唯一子节点取反 | 不可能为空（构建期已要求恰好 1 个） | 无 | matcher.go:305-307 |
| `exactNotMatcher` | 对唯一**精确**子节点取反 | 同上 | 无 | matcher.go:313-315 |

`andMatcher` 的空集合返回 false 是一个刻意的边界：若返回 true，则 `"op":"and","children":[]` 会退化为"恒不命中"之外的"恒真"，与 `neverMatcher` 的 fail-closed 方向相反。

`exactNotMatcher` 与 `notMatcher` 的实现体相同，区分存在的原因是语义注释（matcher.go:309-311）：UI 的 `ne`（不等于）必须表达为"精确相等的取反"，而不是"不包含"。当前六个 kind 走这条路：

| kind | 被取反的精确匹配器 | 位置 |
|---|---|---|
| `block_header_not_exact` | `headerExactMatcher` | matcher.go:1517-1519 |
| `path_not_exact` | `exactPathMatcher` | matcher.go:1540-1541 |
| `full_url_not_exact` | `fullURLExactMatcher` | matcher.go:1543-1544 |
| `host_not_exact` | `hostMatcher` | matcher.go:1546-1547 |
| `body_not_exact` | `bodyExactMatcher` | matcher.go:1622-1623 |
| `query_param_not_exact` | `queryParamExactMatcher` | matcher.go:1636-1638 |

### if / else 条件分支
`ifElseMatcher` 持有三个可选子节点，求值规则：

- `condition` 为 nil → 直接 false（matcher.go:495-497）
- `condition` 为 true → 结果为 `thenMatch != nil && thenMatch.Match(ctx)`
- `condition` 为 false → 结果为 `elseMatch != nil && elseMatch.Match(ctx)`；即**未写 `else` 时分支不命中**

三个 `op` 别名 `if`、`if_else`、`ifelse` 走同一分支（matcher.go:1898），但校验侧 `validateCompoundNode` 同样接受这三个值（validate.go:67）。

典型用法是"除某来源外的全部 POST /login 请求"：

```json
{"op":"if","if":{"kind":"block_method","arg":"POST"},"then":{"kind":"block_path","arg":"/login"},"else":{"kind":"block_ip","arg":"10.0.0.0/8"}}
```

### cc_rate 的窗口状态机
`cc_rate` 是复合体系里唯一带跨请求状态的节点。其判定路径：

```mermaid
stateDiagram-v2
  state "子条件未命中" as MISS
  state "窗口累计中" as WIN
  state "达阈值触发" as HIT
  state "阻断期内" as BLK
  state "条目被清扫" as GC
  [*] --> MISS
  MISS --> MISS: child.Match 为 false
  MISS --> WIN: child 命中且 window/threshold 有效
  WIN --> WIN: count++ 且 count < threshold
  WIN --> HIT: count >= threshold
  HIT --> BLK: duration 大于 0，置 blockedTill
  HIT --> MISS: duration 为 0，不设阻断
  BLK --> BLK: 后续请求 child 命中，直接返回 true
  BLK --> GC: now 超过 blockedTill 与 windowUntil
  GC --> MISS: 下一次清扫后重建条目
```

- [matcher.go:47-91](file://internal/core/rules/matcher.go#L47-L91)

| 参数 | 类型 | 取值约束 | 语义 | 缺省/非法行为 |
|---|---|---|---|---|
| `window` | int64 秒 | 必须 > 0 | 计数窗口长度 | ≤0 → `neverMatcher` |
| `threshold` | int64 次 | 必须 > 0 | 窗口内命中次数阈值 | ≤0 → `neverMatcher` |
| `duration` | int64 | 必须 ≥ 0 | 阻断时长，按 `duration_unit` 解释 | <0 → `neverMatcher` |
| `duration_unit` | string | `""` / `seconds` / `minutes` | 时长单位 | 非法 → `neverMatcher` |
| `duration_seconds` | int64 | 必须 ≥ 0 | 已换算的秒数，**优先于** `duration`+`duration_unit` | 为 0 时回落到 `ccDurationSeconds` |

单位换算规则（matcher.go:1844-1856）：`seconds/second/sec/s` → 原值；`""`/`minutes/minute/min/m` → 乘 60；其余 → 也乘 60（兜底按分钟）。因此 **`duration` 单独写而不带单位时，语义是分钟**。

三条易被误读的实现细节：

- 计数键不是 "IP + Host"：`ccRateKey` 复用 `RateLimitKey(bind, siteID, host, clientIP)`，即 `bind|siteID|归一化 Host|clientIP`（matcher.go:107-109、phases.go:63-70）。同一 `bind` 下 `*` 兜底站点与显式 host 站点因此不会互抢配额。
- 状态表**按条件指纹共享**：`ccRateStateKey` 对 `{child, window, threshold, duration_seconds}` 序列化后取 MD5（matcher.go:1858-1876），再经 `ccRateStates.LoadOrStore` 落到进程级 `sync.Map`（matcher.go:45、1912）。两条规则若条件与参数完全相同，会共享同一份计数。
- 清扫周期固定 60 秒，且只清"窗口与阻断都已过期"的条目（matcher.go:67-74）；因此条目数上界是"60 秒内活跃过的客户端数"，没有容量上限。

`window <= 0 || threshold <= 0` 在 `Match` 内也有一道防御性短路（matcher.go:51-53，直接返回 true），但正常路径不可能到达——`buildCompound` 已在建树时把这些参数挡成 `neverMatcher`。

### JSON 解析的双次反序列化
`parseCompoundJSON` 刻意做两次 `json.Unmarshal`（matcher.go:1825-1835）：

| 步 | 动作 | 执行位置 | 输入 | 输出 | 失败分支 | 可观测点 |
|:--:|---|---|---|---|---|---|
| 1 | 反序列化为运行期结构 | [matcher.go:1826-1829](file://internal/core/rules/matcher.go#L1826-L1829) | `arg` 原文 | `compoundCondition` | 解析失败 → `neverMatcher` | 规则"配了不生效" |
| 2 | 反序列化为校验结构 | [matcher.go:1830-1833](file://internal/core/rules/matcher.go#L1830-L1833) | 同一原文 | `compoundPattern` | 失败或有 errs → `neverMatcher` | 同上 |
| 3 | 递归校验 | [validate.go:54-104](file://internal/core/rules/validate.go#L54-L104) | `compoundPattern` | `errs` | 非空即视为非法 | `ValidateRule` 返回中文错误串 |
| 4 | 建树 | [matcher.go:1878-1928](file://internal/core/rules/matcher.go#L1878-L1928) | `compoundCondition` | `Matcher` 树 | 叶子非法 → 该子树 `neverMatcher` | `MatchDesc` 显示 `compound:{...}` |

两个结构体字段集完全一致，分开定义的原因是把校验模型与运行期模型解耦：`validateParsedPattern` 在编译期也会被调用（compiler.go:51），若校验依赖运行期结构，任何字段新增都会同时改变校验面。

### 复合条件的两个生产入口
除手写 DSL 外，复合树还有两个自动来源，理解它们才能判断"这条 compound 规则从哪来"。

| 入口 | 位置 | 触发条件 | 生成的结构 | 优先级/阶段 |
|---|---|---|---|---|
| 规则级频次限制 | [build.go:955-969](file://internal/snapshot/build.go#L955-L969) | `store.Rule.WindowSeconds > 0` 且 `RequestCount > 0` 且原 `kind != "compound"` | `{"op":"cc_rate","children":[{kind,arg}],"window":W,"threshold":N}`（**不含 duration**） | 规则自身 Phase；`Priority` 不变 |
| CC 防护页 cc_rules | [build.go:1051-1116](file://internal/snapshot/build.go#L1051-L1116) | 站点/全局 `cc_rules` JSON 且 `Window>0 && Threshold>0` | `cc_rate` 信封，内含单条件或 `and` 树，带 `duration`/`duration_unit`/`duration_seconds` | 固定 `Phase=custom`、`Priority=10000`、ID 由 `ccRuleIDCounter` 递增 |

规则级包装明确**不叠加**已是 compound 的 pattern（`kind == "compound"` 直接原样返回），以免生成 `cc_rate` 套 `cc_rate` 这种无法从表单还原的结构；`cc_rules` 的多条件在 `len(children) > 1` 时先包一层 `and`（build.go:1079-1081），无频次参数时同样落为 `compound`。

`store.Rule` 的对应字段语义写在模型注释里：`WindowSeconds`/`RequestCount` 任一为 0 表示不做频次限制（policy.go:88-96）。

## 性能考虑
- 建树一次性、求值零解析：`arg` 只在 `Compile` 时被解析，请求路径只走 `Match`；每代次每 `{siteID,policyID}` 只编译一次（engine.go:34-37、386-431）
- 短路顺序即成本顺序：`and` 把廉价条件放前面（`block_method`、`block_path_exact`），`or` 把高命中条件放前面
- 深度嵌套的代价在构造期而非请求期，但递归 `Match` 会增加调用栈与分支预测压力，建议层级 ≤3
- `cc_rate` 的锁粒度是**每条件指纹一把 `sync.Mutex`**（matcher.go:33-37），高并发下同一条件的所有客户端共用一把锁；需要更细粒度时应拆成多条不同条件的规则，而不是加锁分级
- `cc_rate` 的 `child.Match` 在锁**外**执行（matcher.go:48-50），因此子条件的昂贵正则不会长时间持锁
- 观察命中不受影响：`cc_rate` 未达阈值返回 false，不产生 observe 记录

## 故障排查指南
- 规则保存时报中文错误
  - 症状：`valid:false`，`errors` 含"复合条件至少需要一个子条件"等
  - 原因：结构不满足 `validateCompoundNode` 约束
  - 排查：对照本文 op 取值表逐项核对 `children` 数量、`if/then` 是否成对、`cc_rate` 参数范围
  - 方案：修正 JSON；`duration_unit` 只能留空、`seconds` 或 `minutes`
- 保存通过但规则永不命中
  - 原因：编译期二次校验失败或被降级为 `neverMatcher`（compiler.go:50-53）
  - 排查：确认叶子 `kind` 在 `knownPrefixes` 内；确认 `arg` 里没有多余空白（`ParsePattern` 对 `*_wildcard` 保留首个冒号后的空白）
  - 方案：用 `ValidateRule` 入口复现，再逐层拆树定位到出错叶子
- `cc_rate` 看起来"没有按 IP 限"
  - 原因：计数键包含 `bind` 与 `siteID`，跨监听器或跨站点的同一 IP 是**不同**计数
  - 排查：核对请求命中的站点与 `bind`
  - 方案：这是隔离设计，不应用它做"全局单 IP 限流"；全局口径应走请求速率限制阶段
- `cc_rate` 阻断时长与预期差 60 倍
  - 原因：`duration` 未带 `duration_unit` 时按分钟解释（matcher.go:1851-1854）
  - 方案：显式写 `duration_unit:"seconds"`，或直接由快照层生成 `duration_seconds`
- 两条相同规则互相稀释配额
  - 原因：条件与参数完全相同的两条 `cc_rate` 共享同一状态表（`ccRateStateKey`）
  - 方案：若需要独立计数，改变条件中任一字段（含 `arg` 文本）即可自然分裂状态键
- 复合规则在界面上不可回显
  - 原因：`rule-pattern-mapper.ts` 的反向解析（`backendToRow`/`notLeafToRow`）未覆盖该叶子
  - 方案：补映射分支，不要手改 `pattern` 字段绕过编辑器

## 结论
复合匹配器的设计核心是"构造期把 JSON 变成对象树，运行期只走多态调用"。布尔三类节点实现极简且方向一致（空集合非恒真）；`cc_rate` 是体系中唯一带跨请求状态的节点，其状态共享粒度由条件指纹决定，计数键与限流、bot 行为窗口同源，从而保证站点与监听器维度的隔离。校验侧与构建侧使用两套同构结构体，是为了让"能否保存"与"能否生效"这两个判据始终一致——这也是本篇反复出现的 fail-closed 方向的来源。已知代价有二：`cc_rate` 状态表无容量上限，`cc_rate` 共享锁按条件而非按客户端划分，两者都应在规则规模与并发量增长时纳入评估。
