## 简介
规则编译器负责把持久化的规则行变成"拿来即用"的匹配器对象。它的职责边界很窄但很关键：

- 解析 DSL 文本或 JSON 复合条件，得到 `(kind, arg)`
- 校验参数是否可用，不可用即降级为永不匹配的匹配器
- 构造具体 `Matcher` 实例并挂到 `Compiled` 上
- 按 `Priority` 升序、`ID` 升序排序，确定运行期遍历顺序

设计取向有三条必须在读代码前知道：

- **fail-closed**：语法错误的规则不生效，而不是拦下所有流量；因此本库不存在 `alwaysMatcher`，只有 `neverMatcher`（matcher.go:504-508）
- **成本前置**：正则/CIDR/glob 的解析全部发生在构造期，请求路径只调 `Match(MatchCtx)`（matcher.go:21-23）
- **两段白名单**：引擎侧 `knownPrefixes` 有 57 项（compiler.go:119-142），快照构建侧只有 30 项（build.go:1197-1222），差集 27 项的裸 DSL 规则进不了快照

阶段链的 11 阶段全序、匹配器逐 kind 参数、复合条件树语义分别由 [处理阶段详解](处理阶段详解/处理阶段详解.md)、[内置匹配器](内置匹配器/内置匹配器.md)、[复合匹配器](规则匹配器/复合匹配器.md) 承载，本篇不重复它们的表格。

### 规则 DSL 与字段映射表
`Pattern` 有两种合法形态，其余一律解析失败：

| 形态 | 文法 | 解析结果 | 关键规则 |
|---|---|---|---|
| 简单 DSL | `<kind>:<arg>` | `kind` = 前缀，`arg` = 冒号后内容 | 第一个冒号位置必须 `> 0`；前缀必须命中 `knownPrefixes` |
| 复合 JSON | `{...}` | `kind = "compound"`，`arg` = 整串 | 仅剥前导空白后判断首字符为 `{`；`arg` 做 `TrimSpace` |
| 通配符类 DSL | `<kind>_wildcard:<pattern>` | `arg` **保留首个冒号之后的空白** | compiler.go:164-167：通配符模式中空白是语义的一部分 |

### 匹配器构造与正则缓存
`buildMatcher` 是唯一的 kind 分派点，构造结果只有两类：具体匹配器或 `neverMatcher`。

| 构造类别 | 代表 kind | 使用的工具 | 缓存 |
|---|---|---|---|
| 网络类 | `allow_ip`、`block_ip` | `net.ParseCIDR` / `net.ParseIP`，单 IP 自动补 `/32`、`/128` | 无（构造期一次） |
| 字符串比较类 | `block_path`、`path_contains`、`block_header*`、`host*` | `strings` 与 `containsFoldASCII` | 无 |
| 正则类 | 全部 `*_regex`、`block_multipart`、`block_body_json_path` 的 pattern 段 | `cachedCompile`（matcher.go:1791-1808） | 进程级 `regexCache`，无淘汰 |
| 通配符类 | 全部 `*_wildcard` | `compileWildcard` → 形态选择，必要时回落 `cachedCompile` | 同上 |
| TLS 类 | `tls_*` | `tlsmeta.NormalizeRuntimeVersionToken`、套件 token 归一 | 无 |
| 组合类 | `compound` | `parseCompoundJSON` → `buildCompound` | 状态表 `ccRateStates` |

`regexCache` 是 `struct{ mu sync.RWMutex; cache map[string]*regexp.Regexp }`（matcher.go:1785-1788），非互斥锁；编译失败**不写缓存**，因此非法模式每次调用都会重走失败路径——这也是校验必须前置的原因。

`splitHeaderArg`（matcher.go:1778-1783）按**第一个**冒号切分，因此 `block_header_regex:User-Agent:a:b:c` 的 pattern 段是 `a:b:c`。`query_param_regex` 例外，用 `strings.Cut` 只切一次并在缺冒号时直接降级（matcher.go:1640-1649）。

## 性能考虑
- 每代次每 `{siteID,policyID}` 只编译一次：缓存命中路径是单次 `atomic.Pointer.Load()`（engine.go:386-396），未命中才付出 `convertAndCompile` + `Compile` 成本
- 排序是 `sort.Slice` 一次成型（compiler.go:71-76），运行期遍历为线性且命中首条即止
- 归一化前置：`runtimeAction`、`ruleIDStr`、`matchDesc` 在构造期算好，避免每请求重复字符串操作
- 通配符形态快路径：`*foo*` / `foo*` / `*foo` / `foo` 四类不进 RE2，成本口径见 [正则表达式优化](规则匹配器/正则表达式优化.md)
- 建议
  - 把高命中率、低成本的规则放在较小 `Priority` 上
  - 用 `path_contains` / `path_wildcard` 替代等价的正则
  - 复合条件收敛在少数几条规则内，减少遍历条数而非增加嵌套深度
  - 避免同一模式因大小写或空白差异产生多个缓存键

## 故障排查指南
- 规则在管理端可见、事件里从不出现
  - 先分清是"丢弃"还是"降级"：前者条目数为 0，后者条目存在但恒不命中
  - 检查 kind 是否落在快照侧 30 项白名单内（build.go:1205-1215）；不在则改用 `compound` 叶子写法
  - 检查 `Phase` 是否为 `acl`/`signature`/`custom`（engine.go:401-410）
- 规则命中顺序与预期不符
  - 核对 `Priority` 是否相同（同值按 `ID` 升序，默认 `Priority` 为 100）
  - 注意跨阶段优先级由 `pipeline.Run` 与 `TerminalPriority` 决定，编译期排序只管阶段内部
- 正则类规则报"非法正则"
  - 校验期用 `cachedCompile` 试编译（validate.go:147-238），因此保存被拒就是模式本身有问题
  - 常见坑：`\d` 写成 `d`、字符类未闭合、把 `(?i)` 依赖给匹配器默认行为
- 通配符规则保存被拒
  - 空串、非法 UTF-8、未转义星号超过 8、悬空 `\`、空字符类都会失败（validate.go:212-238）
  - `*_wildcard` 的 `arg` 保留首个冒号之后的空白，尾部多余空格会改变语义
- 频次限制不生效
  - `WindowSeconds` 与 `RequestCount` 必须同时大于 0，且原 kind 不是 `compound`（build.go:956）
  - `cc_rate` 的 `duration` 不带单位时按**分钟**解释（matcher.go:1844-1856）
- 动作与配置不符
  - `log` 被归一为 `observe`；不在白名单的动作串一律回落 `intercept`（phases.go:1301-1310）
- 验证命令
  - `go test ./internal/core/rules/... -run Compile`：编译与排序断言
  - `go test ./internal/snapshot/... -run CompileRules`：快照侧预解析与频次包装断言
  - `POST` 规则校验接口：对 `pattern` 做保存期等价校验

## 结论
规则编译器的价值在于它把"规则文本"到"可调用对象"的转换收敛成一条严格单向、方向一致退化的流水线：解析、校验、构造、归因、排序五步各有明确的失败落点，且所有落点都朝"不拦"退化。真正需要读者记住的是两点：**丢弃与降级是两种不同故障**（前者条目消失、后者条目恒假），以及**引擎侧与快照侧各有一份 kind 白名单**（57 项对 30 项），后者是"保存成功却毫不生效"这类缺陷最常见的成因。编译成本全部落在代次内的一次性路径上，运行期只承担多态调用，这是当前规则规模下性能稳定的根本原因。

### 规则编译最佳实践
- 优先级设计：小 `Priority` 给高命中低成本规则，让"命中首条即止"尽早生效
- 形态选择：能用前缀/包含/通配符就不要用正则；确需正则时保持模式串逐字稳定以命中缓存
- 动作选择：`allow` 只表示"本阶段放行"，**不短路**；需要真正终止请用 `intercept`/`drop`/挑战类动作
- 频次设计：单条规则用 `WindowSeconds`+`RequestCount`；跨条件的组合频次用 CC 防护页的 `cc_rules`
- 可观测性：`Category` 等于 kind，`MatchDesc` 等于 `kind:arg`，二者是事件检索的主键；长复合条件会被折叠成 `compound:{...}`，需要精确定位时查规则原文
