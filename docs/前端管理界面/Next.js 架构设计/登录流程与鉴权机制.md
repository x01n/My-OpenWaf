## 简介

My-OpenWaf 管理端采用**双令牌**模型：短时 HS256 JWT 作为访问令牌，长期不透明刷新令牌以 HttpOnly Cookie 承载。前端只持有访问令牌，刷新令牌的原文只在 Cookie 中往返，脚本无法读取。

本文只描述代码中实际存在的行为。以下几处与常见假设不同，属本次核对的订正：

1. 访问令牌存放在 **`localStorage` 的 `token` 键**，不是 `sessionStorage`，也不是 `owaf_access_token` 之类前缀键；到期时间单独存于 `token_expires_at`。
2. 登录页与闸门**不处理 `?reason=` 参数**。会话过期时的跳转是 `window.location.href = "/login"`，不带原因码。
3. 刷新不是"等 401 再补"。`use-auth.ts` 会在到期前 60 秒主动续期，401 重试只是兜底路径。
4. 刷新请求跨标签页串行化：优先使用 Web Locks API，不可用时退化为基于 `localStorage` 的租约锁。

### 令牌刷新链路

刷新是这套鉴权里最复杂的一条链路，因为要同时满足：一次性刷新令牌不可重复消费、多标签页不可并发刷新、旧响应不可覆盖新会话。

```mermaid
sequenceDiagram
  autonumber
  participant PG as 页面请求
  participant AQ as apiRequest
  participant RT as refreshToken
  participant LK as 跨标签页锁
  participant RH as RefreshHandler
  participant REPO as RefreshTokenRepo
  participant ST as localStorage
  PG->>AQ: GET /api/v1/xxx（Bearer 旧令牌）
  AQ->>AQ: 收到 401 且非认证端点
  AQ->>ST: 比对当前令牌是否已变化
  alt 已被其他标签页轮换
    AQ->>PG: 用新令牌直接重试，不消费刷新令牌
  else 未变化
    AQ->>RT: refreshToken
    RT->>RT: 命中在途 Promise 或 500 毫秒结果缓存则复用
    RT->>LK: 申请 exclusive 锁 my-openwaf-refresh
    alt Web Locks 可用
      LK->>RH: POST /auth/refresh（credentials include）
    else 不可用
      LK->>LK: 登记意图，取最小 owner 竞争租约
      LK->>RH: 拿到租约后 POST /auth/refresh
    end
    RH->>REPO: FindByJTI 与 HashToken 比对
    alt 校验失败
      RH-->>RT: 401
      RT-->>AQ: reason unauthorized
      AQ->>ST: 清除令牌
      AQ-->>PG: ApiError 并跳 /login
    else 仓储故障
      RH-->>RT: 503
      RT-->>AQ: reason unavailable
      AQ->>AQ: 保留令牌，标记 refresh_status unavailable
    else 校验通过
      RH->>REPO: Rotate 旧 JTI 到新 JTI
      RH->>RH: Set-Cookie 新刷新令牌
      RH-->>RT: 200 新 access_token
      RT->>ST: setToken 写入 token 与 token_expires_at
      RT-->>AQ: ok 与新令牌
      AQ->>PG: 用新令牌重试原请求
    end
  end
```

### 鉴权状态机

把"前端可观察的会话状态"独立建模，是理解 `AuthGate` 与错误处理的关键：

```mermaid
stateDiagram-v2
  state "无凭据" as NONE
  state "续期中" as REFRESHING
  state "有效会话" as ACTIVE
  state "服务暂不可用" as UNAVAILABLE
  state "令牌已过期" as EXPIRED
  state "登录页" as LOGIN
  [*] --> NONE: 无本地访问令牌
  NONE --> REFRESHING: 首屏探测携带 Cookie
  REFRESHING --> ACTIVE: 200 且形状校验通过
  REFRESHING --> UNAVAILABLE: 网络错误或 5xx
  REFRESHING --> EXPIRED: 401 明确失效
  ACTIVE --> REFRESHING: 距到期不足 60 秒
  ACTIVE --> REFRESHING: focus 或 visibility 恢复
  ACTIVE --> EXPIRED: 业务请求 401 且刷新 401

  note right of EXPIRED
```

### 跨标签页刷新的锁与竞态防护

| 机制 | 实现 | 解决的具体竞态 |
|------|------|----------------|
| `authEpoch` 代次与令牌比对 | 登录/清除时递增，返回后比对当前令牌 | 旧响应复活会话或重复写入 |
| 在途 Promise 复用 | `refreshPromise` 单例 | 同页多个 401 并发刷新 |
| 500 毫秒结果缓存 | 按代次与令牌命中 | 首屏无令牌时反复打同一 401 |
| Web Locks | `locks.request("my-openwaf-refresh", exclusive)` | 跨标签页串行刷新 |
| 意图登记 + 最小 owner | `localStorage` 前缀键与确定性比较 | 无 CAS 时的双写抢锁 |
| 租约续约 | 每 `TTL/3` 重写租约与意图 | 长请求期间租约被抢 |
| 等待上限 20 秒 | 超时返 `unavailable` | 死锁导致页面卡住 |
| 忽略 `StorageEvent.newValue` | 一律重读共享存储 | 滞后事件覆盖新会话 |

### 服务端令牌校验与吊销

`AuthMiddleware` 的判定顺序不可调换：

| 序 | 步骤 | 结果 |
|:--:|------|------|
| 1 | 白名单路径直接放行 | 健康检查与三个认证端点 |
| 2 | `Authorization` 缺失 | 401 `missing Authorization header` |
| 3 | 无 `Bearer ` 前缀 | 401 `invalid Authorization format, use Bearer <token>` |
| 4 | `VerifyAccessToken` 主密钥失败回退备用密钥 | 支持密钥轮换过渡期 |
| 5 | 黑名单未就绪则重试加载，仍失败返 503（fail closed） | 未就绪时拒绝认证 |
| 6 | JTI 命中黑名单 | 视为已吊销，落到回退分支 |
| 7 | 写入 `auth_user`、`auth_username`、`auth_method`、`auth_role`、`auth_jti` | 下游 handler 取用 |
| 8 | `SessionManager.UpdateLastActive` | 30 秒内只落库一次 |
| 9 | JWT 失败回退 API Key；归属账号已删除则 401 | 身份与角色取所属账号 |

吊销路径有三条：登出拉黑访问令牌 JTI（有效期取 `AccessTTL` 余量，原因 `logout`）、强制注销删除会话、改密后撤销该用户全部凭据（原因 `password_changed`）。登出会撤销**整条刷新令牌轮换链**，而不是仅撤销 Cookie 中的那个 JTI，否则重载页面仍可能被后继令牌恢复会话。

## 性能考虑

- **提前续期而非事后补救**：到期前 60 秒触发，避免业务请求集中撞 401 再排队刷新。
- **单点续期**：控制器在根布局，定时器与焦点监听全站共一份，不随页面数量线性增长。
- **请求合并**：同一令牌的 `/auth/me` 只保留一个在途 Promise；刷新结果 500 毫秒内复用。
- **锁等待有界**：租约等待 20 秒上限、50 毫秒轮询、`TTL/3` 续约，不会因某标签页崩溃而无限期阻塞。
- **会话活跃写库节流**：30 秒窗口内合并 `UPDATE`，避免每个管理请求一次写库。
- **黑名单内存化与周期回收**：`sync.Map` 查找加 10 分钟清理；会话与暴力破解各 5 分钟一轮（后者空闲超两倍锁定时长即删），`Close` 幂等。

## 结论

这套鉴权机制的工程价值集中在**失败语义的区分**上：`unauthorized` 与 `unavailable` 的分离让"凭据失效"与"服务抖动"不再共用一条登出路径，`authEpoch` 与令牌一致性比对让异步响应不会污染新会话，一次性轮换与整链撤销让刷新令牌被重放时立即失效。

前端侧符合单一职责：表单只提交、控制器只调度、`lib/api.ts` 只处理凭据与请求。服务端侧 `AuthDeps` 依赖注入使处理器可脱离 HTTP 上下文单测。

可改进项：`frontend/hooks/use-auth.ts` 中的 `useIsAuthenticated` 与 `AuthGate` + `useAuth` 职责重叠且无调用方，属可清理的冗余；`internal/admin/auth.go` 中 `username` 为空时回落到硬编码 `admin` 的兼容分支，值得在确认无历史数据后移除。

|------|:----:|------|
| `maxFailures` | 5 | 非正值回落默认 |
| `lockoutDur` | 15 分钟 | 非正值回落默认 |
| 计数维度 | 2 | 纯 IP 与 `IP\|username` |
| 判定顺序 | IP 优先 | 先 IP 级，再 IP+用户 |
| 剩余提示阈值 | ≤3 | 仅小值时返回 `remaining_attempts` |
| 成功后清理 | 是 | 只清 IP+用户维度记录 |
| 锁定过期 | 自动重置 | 下次失败重新给满额机会 |
| 记录回收 | 5 分钟一轮 | 空闲超两倍锁定时长即删 |
| 动态重配 | `Reconfigure` | 阈值下调时补打锁定时间戳 |
