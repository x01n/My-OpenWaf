## 简介

My-OpenWaf 前端导航由 **4 个协作组件 + 1 个路由元数据源** 构成：`AppSidebar`（菜单）、`TopBar`（标题与全局动作）、`BreadcrumbNav`（路径）、`TabWorkspaceProvider`（多标签工作区），元数据集中在 `lib/route-titles.ts`。

本篇同时订正旧稿中一批**并不存在**的名字。下列符号经对 `frontend/components/`、`frontend/lib/`、`frontend/app/` 全量核对，均无对应实现，凡引用它们的描述都已改写为实测实现：

| 旧稿说法 | 实测事实 |
|----------|----------|
| `lib/console.ts` 为导航配置中心 | 不存在。导航数据在 `components/sidebar-nav.tsx:192-334` 的 `useNavGroups()`，标题映射在 `lib/route-titles.ts` |
| `layout/sidebar.tsx`、`layout/topbar.tsx` | 不存在。`components/` 为扁平结构，无 `layout/` 子目录 |
| `components/dashboard-topbar.tsx` | 不存在。顶部栏是 `components/top-bar.tsx` 的 `TopBar` |
| `ConsoleNavItem` / `ConsoleNavGroup` / `consoleNavGroups` | 实际类型名为 `NavItem`（`:76-81`）与 `NavGroup`（`:83-87`） |
| `getNavMeta(pathname)` | 实际函数是 `getPageTitleKey(pathname)`（`lib/route-titles.ts:72-77`） |
| 面包屑由 `TopBar` 内部生成 | 面包屑由独立的 `BreadcrumbNav` 渲染，挂在 `main` 内（`(dashboard)/layout.tsx:28`） |
| 图标来自 Lucide | 图标全部来自 `@tabler/icons-react`（`sidebar-nav.tsx:10-38` 导入 27 个） |
| 导航项含 `enabled`、`exact` 字段 | 实际字段只有 `label`、`href`、`icon`、`children?`；分组有 `labelKey?` |

### 侧边栏：折叠、展开与活动态

`AppSidebar`（`sidebar-nav.tsx:339-382`）的结构是固定的三段式：`SidebarHeader`（`IconShieldCheck` + `OpenWAF` 字样，折叠时只留图标）、`SidebarContent`（6 个 `SidebarGroup`）、`SidebarFooter`（版本号文本，折叠时不渲染）。骨架由 `<Sidebar collapsible="icon">`（`:346`）提供整栏 icon 折叠能力。

活动态判定分两步，且两处都做了前缀匹配修正：

```mermaid

  P --> |否| NO["返回 false"]

  COLL --> LONG{"href 是否等于最长匹配？"}

  NO2 --> NOTE1
  YES --> NOTE1["附加 ACTIVE_ITEM_CLASS<br/>主色文字 + 左侧 3px 指示条"]
  NOTE1 --> END(["渲染完成"])
```

三个必须知道的实现细节：

1. **为什么需要「最长匹配」**：`/security-events` 既是父项 `href` 又是第一个子项 `href`，若只做前缀匹配，父项与子项会同时高亮。`isExactOrLongestActive()`（`:101-111`）把所有命中项按 `href.length` 取最长者，只有它标活。
2. **活动态样式是覆写的**：shadcn 默认 `SidebarMenuButton` 的活动底色与 hover 底色相同（都是 `bg-sidebar-accent`），鼠标划过时分不清哪个是当前页。`ACTIVE_ITEM_CLASS`（`:69-70`）与 `ACTIVE_SUB_ITEM_CLASS`（`:73-74`）叠加 `data-[active=true]:text-primary` 与 `before:` 伪元素指示条（父项 3px、子项 0.5px），注释见 `:62-68`。
3. **展开态由命中情况决定**：`CollapsibleNavItem` 用 `defaultOpen={groupActive}`（`:123`）让当前命中的分组默认展开；`groupActive` 来自对子项的递归判定（`:118-120`）。

分组标题只在 `labelKey` 非空时渲染（`:358-360`），因此前 3 组在视觉上是无标题块。

### 多标签工作区与尾斜杠适配

`TabWorkspaceProvider` 是「文档式」导航的载体：顶部标签条随路由自动新增/激活，关闭后回到相邻标签。它与 `trailingSlash: true`（`next.config.ts:6`）之间有硬耦合：

- 固定标签 `PINNED_PATH = "/dashboard/"` 显式带尾斜杠，注释写明原因（`tab-workspace.tsx:24-25`）。

- `tabIdentity()`（`:47-53`）为站点详情开了特例：只有 `/sites/detail` 会把 `?id=` 纳入身份，其余路径一律以 pathname 为身份——这意味着同一页面的不同页签（`?tab=`）不会各自占用一个标签。
- 持久化键 `owaf.workspace.tabs` 写在 `sessionStorage`（`:26`），`loadTabs()`（`:86-102`）用 try/catch 包裹 JSON 解析，坏数据回落为空数组。

- 由于内部使用 `useSearchParams()`，`(dashboard)/layout.tsx:25` 必须把它包在 `<Suspense>` 里——这在静态导出预渲染时是强制要求。

## 性能考虑

- 文案解析零成本：`getPageTitleKey()` 是对 26 条记录的线性前缀扫描（`route-titles.ts:72-77`），不在渲染热路径上引入查表结构是合理的规模判断。
- 最长匹配只遍历一次：`isExactOrLongestActive()`（`sidebar-nav.tsx:101-111`）用 `flatMap` + `reduce` 在单个条目渲染内完成，代价是每项一次小数组构造——由于导航总量固定在 30 项以内，实测不构成瓶颈。
- 子菜单不预渲染内容：`CollapsibleContent` 折叠时不展开子树（`:136-161`），移动端未打开抽屉时也不渲染。
- 状态集中在 Context：`SidebarContext`（`ui/sidebar.tsx:44`）避免逐层透传 `collapsed`，`useSidebar()` 只在需要的三个组件里订阅（`sidebar-nav.tsx:116`、`:170`、`:341`）。
- 标签持久化用 `sessionStorage` 而非 `localStorage`（`tab-workspace.tsx:26`），会话结束即释放，避免长期累积。
- 图标按需引用：27 个图标全部具名导入（`sidebar-nav.tsx:10-38`），配合 Tailwind v4 + Turbopack 的 tree-shaking 不引入整包。
- 断点监听单点：`useIsMobile()` 只在 `SidebarProvider` 内调用一次（`ui/sidebar.tsx:68`），子组件通过 Context 读 `isMobile`，不各自 `matchMedia`。

## 结论

My-OpenWaf 的导航系统由四个职责互不重叠的组件构成，靠一份路由元数据保持一致性：

1. **单一数据源**：标题与面包屑都从 `lib/route-titles.ts` 派生，不存在第二处路径—文案映射，符合 DRY。
2. **职责分离**：`AppSidebar` 只管「去哪」，`TopBar` 只管「在哪 + 全局动作」，`BreadcrumbNav` 只管「路径链」，`TabWorkspaceProvider` 只管「开过哪些页」，四者互不引用，可独立替换，符合 SRP。
3. **响应式内聚**：断点、抽屉、快捷键、偏好持久化全部收在 `ui/sidebar.tsx` 原语层，业务侧只需 `<Sidebar collapsible="icon">`，符合 KISS。
4. **与静态导出对齐**：用 `document.cookie` 与 `sessionStorage` 替代服务端 cookie 与路由级缓存能力，`useSearchParams` 的消费者显式包 `Suspense`，不依赖任何需要 Node 运行时的 Next 特性。

待改进项（如实记录，未擅自改代码）：`routeTitleKeyMap` 与 `segmentKeyMap` 均缺 `/tls-fingerprints`，导致该页标题回落、面包屑显示原始片段；`sidebar-nav.tsx:377` 的页脚版本号为硬编码；`tab-workspace.tsx:278` 的 `useTabWorkspace` 目前无调用方。
