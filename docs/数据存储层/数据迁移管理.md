## 简介

数据迁移管理解决两个问题：如何让旧库在不丢数据的前提下追上新的 struct tag，以及如何让这个过程在每次启动都重跑一次仍然安全。

实现方式是一套固定编排：**先数据修复，再结构迁移，最后补做依赖新表的数据修复**。结构本身永远由 `AutoMigrate` 依据 struct tag 生成，15 个具名 `Vn` 函数只处理「tag 无法表达的部分」——历史列改名、取值语义清洗、索引替换、引用完整性修复。没有 down migration，回滚依赖带时间戳的备份表与配置备份。

## 详细组件分析

### 执行顺序与编排

`AutoMigrate` 的顺序不是风格问题而是因果约束，代码注释逐条给出了理由。

| 序 | 步骤 | 位置 | 为什么必须在此 |
|:--:|------|------|----------------|
| 1 | V2 单站点合并 | `migrate.go:24` | 旧表存在时后续模型列才有归属 |
| 2 | V10 XFF 归一 | `migrate.go:27` | 先洗取值，避免快照读到非法模式 |
| 3 | V3 规则 phase 改写 | `migrate.go:30` | 旧 phase 不可执行，必须先落到 `custom` |
| 4 | V4 资源查询串 | `migrate.go:33` | 为 V8 的五列摘要准备列 |
| 5 | V5 去列默认值 | `migrate.go:36` | 默认值存在会掩盖继承语义 |
| 6 | V6 TLS 继承标记 | `migrate.go:39` | 需要 `system_settings`，旧库可能还没有 |
| 7 | V11 反重放继承 | `migrate.go:42` | 同上 |
| 8 | V8 摘要回填 | `migrate.go:47` | 必须在 `AutoMigrate` 之前，否则唯一索引因重复值创建失败 |
| 9 | 结构迁移 31 模型 | `migrate.go:52-89` | 依据 struct tag 建表加列 |
| 10 | V9 默认策略修复 | `migrate.go:92` | 需要 `default_slot` 列已存在 |
| 11 | V13 `cve_rules.references` | `migrate.go:99` | 启动期 CVE 目录对账早于日志迁移 |
| 12 | V7 访问控制建表 | `migrate.go:104` | 新表，幂等 |
| 13 | V15 令牌归属回填 | `migrate.go:110` | 需要 `admin_accounts` 已建 |
| 14 | V14 规则执行参数 | `migrate.go:113` | 兜底补列 |
| 15 | V6、V11 再跑 | `migrate.go:120-123` | 覆盖「表结构迁移前还没有 `system_settings`」的旧库 |

### 幂等守卫的四种写法

每个 `Vn` 函数都必须能在已迁移库上重复执行，项目里共四种守卫。

| 守卫类型 | 写法 | 代表 | 适用 |
|----------|------|------|------|
| 表存在性 | `if !db.Migrator().HasTable(...) { return nil }` | `single_site.go:12`、`rule_phase.go:14`、`access_log_fingerprint_key.go:42` | 首次启动或表已被改名 |
| 列存在性 | `if !db.Migrator().HasColumn(...) { return nil }` | `site_xff_mode.go:12`、`api_key_owner.go:25`、`site_antireplay_inheritance.go:17` | 依赖新列的取值修复 |
| 条件更新 | `WHERE` 只命中待修数据 | `rule_phase.go:20`、`site_xff_mode.go:17`、`api_key_owner.go:45` | 天然幂等，重复为无操作 |
| 标记行 | `system_settings` 有键即跳过 | `site_tls_min_version_inheritance.go:25-34`、`site_antireplay_inheritance.go:22-32` | 一次性语义，保护后续显式值 |

```go

var marker migrationSystemSetting
markerQuery := tx.Where(clause.Eq{
	Column: clause.Column{Name: "key"},
	Value:  siteTLSMinVersionInheritanceMigrationKey,

	return fmt.Errorf("failed to load site TLS min version migration marker: %w", markerQuery.Error)
}
if markerQuery.RowsAffected > 0 {
	return nil
}

	Where("min_tls_version = ?", "TLS12").
	Update("min_tls_version", "").Error; err != nil {
	return fmt.Errorf("failed to migrate sites.min_tls_version default: %w", err)
}
```

## 性能考虑

- **问题**：日志库回填需要扫全表，大库启动会卡住。
  **优化**：V12 采用 keyset 游标（`id > ?` + `LIMIT 1000`）而非 offset，且只回填空摘要且含 JA3/JA4 的行。
  **效果**：内存占用有界，历史无指纹行不被无谓重写。
- **问题**：重复行会让唯一索引创建失败。
  **优化**：V8 回填时用 `seen` 表识别同摘要行，保留最小 id 并删除其余。
  **效果**：索引创建一次成功，且结果与运行期 upsert 语义一致。
- **问题**：MySQL 的 DDL 不进事务，失败会留下中间态。
  **优化**：V5 把「列本无默认值」类错误白名单化；V6/V11 用标记行避免重复洗数据。
  **效果**：重复启动幂等，中间态可被下一次启动继续修复。
- **问题**：迁移全量跑一遍会拖慢重启。
  **优化**：所有 `Vn` 以存在性守卫短路，已迁移库几乎只付索引检查成本。
  **效果**：稳态启动的迁移阶段接近常数时间。

## 结论

迁移管理由「固定编排 + 四种守卫 + 一个修订号」构成：编排把因果关系写进顺序（V8 早于结构迁移、V9 晚于默认槽列），守卫让每次启动重跑都安全，`ConfigRevision` 把「数据变了」与「快照要重建」解耦。KISS 是不引入外部迁移工具与版本号表；YAGNI 是不做 down migration，改用备份表与配置导出；DRY 的例外是摘要算法与影子结构体的两份实现，二者由测试强制一致；SRP 是每个 `Vn` 只做一件事，因此可以任意组合重跑。

已知风险集中在 MySQL 的隐式提交：跨语句 DDL 无法整体回滚，生产变更前必须做数据库级备份。
