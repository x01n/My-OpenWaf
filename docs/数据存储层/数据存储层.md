## 简介

数据存储层承担 My-OpenWaf 全部持久化职责，向上为控制面（管理 API）与数据面（请求处理）提供统一的数据读写入口，向下屏蔽 SQLite、MySQL、PostgreSQL 三种方言差异。它由四个边界清晰的子域组成：连接与方言（`internal/core/database`）、领域模型与迁移（`internal/store` 及其 10 个领域子包与 `migrations`）、数据访问（`internal/store/repository`）、可选分布式状态（`internal/core/redis` 与 `internal/cache`）。

本层的设计目标是：**主库与日志库物理分离**、**表结构演进全程幂等**、**站点级配置以三态表达继承关系**、**Redis 完全可选且故障不阻断主链路**。本篇作为该域索引，给出表清单、模型关系与迁移全景，细节由六份子文档展开。

## 项目结构

存储层代码分布在四个目录，职责互不重叠：连接工厂不感知模型，模型不感知驱动，仓储不感知缓存实现，Redis 不感知 SQL。

| 模块 | 路径 | 非测试行数 | 职责 | 关键入口 |
|------|------|:----------:|------|----------|

| 领域子包 | `internal/store/{auth,access,approute,cve,owasp,iplist,luaplugin,threatintel,falsepositive,upstream}` | 742 | 按领域拆分的模型与常量 | 各包 `type Xxx struct` |

func BumpRevision(db *gorm.DB) error {
	seed := ConfigRevision{ID: 1, Revision: 0}
	if err := db.Clauses(clause.OnConflict{
		Columns:   []clause.Column{{Name: "id"}},
		DoNothing: true,
	}).Create(&seed).Error; err != nil {
		return err
	}
	result := db.Model(&ConfigRevision{}).
		Where("id = ?", seed.ID).
		UpdateColumn("revision", gorm.Expr("revision + ?", 1))
	if result.Error != nil {
		return result.Error
	}
	if result.RowsAffected != 1 {
		return fmt.Errorf("config revision row %d was not updated", seed.ID)
	}
	return nil
}

## 性能考虑

- **问题**：日志与配置同库时，`access_logs` 的高频追加会与站点配置读写争用同一把 SQLite 写锁。
  **优化**：主库与日志库拆成两个 `*gorm.DB`，日志库使用独立 PRAGMA 组合（`foreign_keys(OFF)`、`wal_autocheckpoint(2000)`）。
  **效果**：配置查询不受日志 WAL 膨胀影响，日志侧 checkpoint 频率提高换取 WAL 体积可控。
- **问题**：列表页每页都要 `COUNT(*)`，宽表上代价高。
  **优化**：`CountCache` 按命名空间缓存计数（`al_count:v2`、`se_count:v2`、`de_count`），写后按前缀失效。
  **效果**：翻页只付一次计数成本；命名空间失效避免误清无关缓存。
- **问题**：直接 `db.Create` 会把用户显式设置的 `false`/`0` 覆盖成 struct 默认值。
  **优化**：`CreateWithZeroDefaults` 先快照零值列，插入后显式 `UpdateColumns` 回写（`zero_defaults.go:90-146`）。
  **效果**：停用站点不会立刻对外服务，`priority = 0` 的规则保持抢跑位置。
- **问题**：五列复合唯一索引在 MySQL utf8mb4 下超过 3072 字节上限。
  **优化**：`recorded_resources` 改用 `char(64)` 的 SHA-256 摘要列建唯一索引，`access_logs` 同理使用 `fingerprint_key`。
  **效果**：三方言语义一致，分组查询不再扫描宽文本列。
- **问题**：Redis 抖动会把管理页请求拖成超时链。
  **优化**：`HotCache` 与 `RedisKV` 各自维护熔断窗口（故障后 5 秒内不再访问），所有命令带上下文超时。
  **效果**：Redis 不可用时读路径直接回源数据库，不产生级联等待。

## 结论

存储层用四个小接口把「怎么连、有几张表、表怎么变、谁能读」四件事彻底分开：`Options` 描述连接、struct tag 描述表、`Vn` 函数描述演进、`Repos` 描述访问。KISS 体现在没有第二个建表入口（一切走 `AutoMigrate` 清单）与第二个日志库打开函数（只有 `Options.LogDB` 一个开关）；YAGNI 体现在未引入通用迁移框架与外键约束，改以显式版本函数与幂等守卫；DRY 体现在零值默认回写被抽成 `CreateWithZeroDefaults`，替代此前散落在 5 个仓储中的同类补偿；SOLID 的接口隔离体现在 `WriteQueueBackend`、`HotCacheBackend`、`CountCache` 各自只有必要方法，并以此切断与 `observability`、`cache` 的导入环。

主要优势是降级路径完整、方言差异集中在两处（`gorm.go` 与 `V5`）；已知取舍是保留 `listener_id`、`forwarding_profile_id` 等 legacy 字段与带时间戳的备份表，以换取历史库可无损升级。
