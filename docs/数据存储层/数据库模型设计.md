## 简介

本篇描述数据存储层的模型设计：35 张表的清单与职责、字段与 struct tag 的逐条对应、索引策略、软删除与时间戳约定、枚举取值口径，以及本项目最具特色的**站点级三态覆盖**建模。

模型层遵循三条硬规则：其一，表结构只由 struct tag 表达，SQL 类型与索引名不写在迁移脚本里；其二，「未设置」与「显式关闭」必须可在数据库层面区分，因此可空标量指针是首选；其三，跨方言可移植性优先于单库便利性，凡 MySQL 无法建立的索引一律改为定长摘要。

## 性能考虑

- **索引与写入平衡**：`access_logs` 有 12 个索引、`security_events` 有 9 个，全部服务于列表过滤与聚合；写放大由统一写入器批量合并来抵消。
- **摘要列替代宽索引**：`fingerprint_key`、`dedup_key` 都是 `char(64)`，把跨列分组转成单列等值查询，同时绕开 MySQL 3072 字节索引上限。
- **默认值集中在 Go 侧**：TEXT 列一律不带 `DEFAULT`（MySQL Error 1101 会直接让 `AutoMigrate` 失败），空串与 `"{}"` 在读取侧等价处理。
- **软删除的成本**：`deleted_at` 索引让「只看未删」保持高效，但统计口径必须显式带条件；`Unscoped()` 仅在修复默认槽时使用。
- **派生字段不进表**：`IsDefault`、`TLSSNIPresence`、上游 mTLS 的 DER/指纹都是 `gorm:"-"`，读时由钩子派生，避免多份真相。

## 结论

模型层用 struct tag 作为唯一真相源，把 35 张表的类型、索引、默认值收敛到声明位置，使迁移脚本只需处理数据而非结构。三态指针、摘要列、键值配置容器三项设计分别解决了「继承语义无法表达」「跨方言索引上限」「配置字段频繁增减」三个具体矛盾；软删除与派生字段钩子则把一致性问题推到仓储事务与读取钩子中处理。

### 命名与约束规范

| 规范 | 写法 | 反例 |
|------|------|------|
| 列名 | snake_case，由字段名自动推出 | 手写 `column:` 只在摘要/覆盖列使用 |
| JSON 名 | 与列名一致的 snake_case | 对外驼峰会破坏前端契约 |
| 字符串长度 | `size:255` 以下，长文本 `type:text` | 长文本用 size 会撑爆索引 |
| TEXT 默认值 | 禁止 | MySQL Error 1101 使建表失败 |
| 布尔默认 | `default:true/false`，可空用 `default:null` | 用 `default:false` 表达继承 |
| 索引命名 | 显式 `index:idx_域_字段` | 依赖自动名会让迁移无法定位 |
| 派生字段 | `gorm:"-"` + `AfterFind` | 落库副本会产生第二真相 |
| 机密字段 | `json:"-"` 且管理面脱敏 | 直接序列化哈希或私钥 |
