## 简介

数据访问层是控制面与数据面通往持久化的唯一通道，由聚合根 `Repos`、12 个领域子包仓储、4 个日志类仓储与一组可选注入的缓存/写队列接口构成。它解决的问题很具体：让上层不必拼 SQL、不必关心连接归属哪条 `*gorm.DB`、不必在每处重复实现分页与计数缓存。

设计上有三个不可妥协点：**仓储不感知缓存实现**（只依赖本地声明的接口）、**日志与配置分属两条句柄**（由 `NewWithLogDB` 路由）、**类型别名保持调用点不变**（拆分到子包后外部零改动）。

### 聚合根与库路由

`Repos` 的 24 个字段就是访问层的能力边界，路由规则简单到只有一条：日志类走 `logDB`，其余走 `db`。

```go
// internal/store/repository/repository.go:60-90（节选）
func NewWithLogDB(db *gorm.DB, logDB *gorm.DB) *Repos {
	if logDB == nil {
		logDB = db
	}
	return &Repos{
		Site:               NewSiteRepo(db),
		SecurityEvent:      NewSecurityEventRepo(logDB),
		AccessLog:          NewAccessLogRepo(logDB),
		BotScore:           NewBotScoreRepo(logDB),
		DropEvent:          NewDropEventRepo(logDB),
		RecordedResource:   NewRecordedResourceRepo(db),
		// 其余 19 个仓储同样绑定 db
	}
}
```

`RecordedResource` 虽是数据面写入，但落在主库：它属于「站点画像」而非请求日志，随配置一起备份与恢复。

### 通用 CRUD 与流程约定

所有配置类仓储共享同一套方法语义，差异只在零值处理与事务边界。

| 序 | 步骤 | 实现约定 | 代表位置 |
|:--:|------|----------|----------|
| 1 | 归一化过滤器 | 先清洗再拼 WHERE，避免非法值进入 SQL | `tls_filter.go:5-29` |
| 2 | 试热缓存 | 仅日志大表列表使用，键含 offset/limit | `access_log.go:332-341` |
| 3 | 计数缓存判定 | 命中则跳过 `COUNT` | `access_log.go:361-376` |
| 4 | 真实计数 | `Model(T).Count(&total)` | `site/site.go:16` |
| 5 | 分页读取 | `Offset/Limit` + 稳定排序键 | `access_log.go:393` |
| 6 | 结果投影 | 列表用轻量列集合，详情全列 | `security_event.go:100-107` |

```go
// internal/store/repository/site/site.go:13-31：List(0,0) 会命中 LIMIT 0，
// 因此全量场景必须用 ListAll，这是本层唯一的显式陷阱说明
func (r *SiteRepo) List(offset, limit int) ([]store.Site, int64, error) {
	var items []store.Site
	var total int64
	if err := r.db.Model(&store.Site{}).Count(&total).Error; err != nil {
		return nil, 0, err
	}
	if err := r.db.Offset(offset).Limit(limit).Order("id ASC").Find(&items).Error; err != nil {
		return nil, 0, err
	}
	return items, total, nil
}

func (r *SiteRepo) ListAll() ([]store.Site, error) {
	var items []store.Site
	return items, r.db.Order("id ASC").Find(&items).Error
```

## 性能考虑

- **问题**：日志大表列表页每次都执行 `COUNT(*)` 与宽列扫描。
  **优化**：三级缓存（Redis 热缓存 5 秒、进程内计数与列表缓存、投影列集合）+ 三列复合索引。
  **效果**：翻页只付一次计数与一次窄列查询成本。
- **问题**：高频日志写入使 SQLite 写锁成为瓶颈。
  **优化**：写队列异步合并 + `CreateInBatches(items, 100)`。
  **效果**：单请求路径不等 DB，写入被批处理摊平。
- **问题**：缓存失效范围过大会连带清空无关列表。
  **优化**：命名空间前缀失效（`al_count:v2`、`al_list:v1`、`se_count:v2`、`de_count`），旧实现自动回落 `InvalidateAll`。
  **效果**：写后读一致性保持，且不产生缓存雪崩。
- **问题**：`SiteRepo.List(0,0)` 表达「取全部」会命中 `LIMIT 0`。
  **优化**：提供 `ListAll` 明确全量语义。
  **效果**：消除空结果类隐性缺陷。
- **问题**：指纹聚合每次刷新都重算。
  **优化**：进程内有界结果缓存 + singleflight + 代际递增。
  **效果**：管理页刷新不打穿数据库。

## 结论

访问层用「一个聚合根 + 一个门面 + 三个接口」把 24 个仓储组织成稳定结构：`Repos` 负责生命周期与库路由，`aliases.go` 负责拆分后的兼容，接口负责可选能力。KISS 体现在没有通用 BaseRepo 泛型——各仓储方法直白但差异清晰；YAGNI 体现在不引入 ORM 之上的查询语言与软开关；DRY 体现在计数缓存失效、TLS 版本归一、零值回写三处公共逻辑各只写一次；ISP 体现在三个注入接口都只声明仓储实际使用的方法，且失效能力通过第二个可选接口增量提供。

主要技术债是日志仓储体量偏大（`access_log.go` 1010 行、`security_event.go` 725 行），其中过滤器、投影列与聚合可继续按切面拆分。

### 仓储方法约定速查

| 约定 | 写法 | 例外 |
|------|------|------|
| 列表 | `List(offset, limit int, f Filter) ([]T, int64, error)` | `SiteRepo.List` 无过滤器 |
