## 简介

My-OpenWaf 支持 SQLite、MySQL、PostgreSQL 三种 SQL 方言，同一份 struct tag 与同一套仓储代码在三者之上运行。方言差异没有被抽象层掩盖，而是收敛到三类显式处理点：**连接参数**（DSN 校验与 PRAGMA）、**结构迁移**（按方言分支的 DDL）、**查询表达式**（时间分桶与标识符引用）。

本篇说明这三类处理点的实现位置与约束，并给出选型建议。核心结论有两条：一是 SQLite 为默认且唯一无需外部服务的部署形态，MySQL/PostgreSQL 面向多节点与集中运维；二是主库与日志库始终是两条独立句柄，可以指向不同方言后端。

### 连接与 DSN 规则

环境变量到方言的映射只有四个变量，DSN 形态决定校验分支。

| 配置项 | 类型 | 默认值 | 必填 | 作用域 | 生效方式 | 安全等级 | 说明 |
|--------|------|--------|:----:|--------|----------|----------|------|
| `MY_OPENWAF_DB_DRIVER` | string | `sqlite` | 否 | 进程 | 重启 | 普通 | 空串等价 sqlite |
| `MY_OPENWAF_DSN` | string | `{DataDir}/waf.db` | 非 sqlite 时必填 | 进程 | 重启 | 机密 | MySQL 必含 `parseTime=True` |
| `MY_OPENWAF_LOG_DSN` | string | `{DataDir}/waf_logs.db` | 否 | 进程 | 重启 | 机密 | 别名 `MY_OPENWAF_LOG_DB` |
| `MY_OPENWAF_DATA` | string | `./data` | 否 | 进程 | 重启 | 普通 | sqlite 落盘目录 |
| `pgbouncer=true` | DSN 参数 | 缺省 false | 否 | 连接 | 重启 | 普通 | 切简单协议，放弃预编译 |
| `charset=utf8mb4` | DSN 参数 | 建议显式 | 否 | 连接 | 重启 | 普通 | 影响索引键长上限判定 |

```bash
# SQLite（默认，无需外部服务）
export MY_OPENWAF_DB_DRIVER=sqlite
export MY_OPENWAF_DSN='{占位目录}/data/waf.db'
export MY_OPENWAF_LOG_DSN='{占位目录}/data/waf_logs.db'

# MySQL：三处缺一不可（charset、parseTime、loc）
export MY_OPENWAF_DB_DRIVER=mysql
export MY_OPENWAF_DSN='{user}:{password}@tcp({host}:3306)/{db}?charset=utf8mb4&parseTime=True&loc=Local'

# PostgreSQL：走 PgBouncer 事务池时必须加 pgbouncer=true
export MY_OPENWAF_DB_DRIVER=postgres
export MY_OPENWAF_DSN='postgres://{user}:{password}@{host}:5432/{db}?sslmode=disable&pgbouncer=true'

# 多方言迁移验证（未设置对应变量时测试自动跳过）
export MY_OPENWAF_TEST_MYSQL_DSN='{user}:{password}@tcp({host}:3306)/waf?charset=utf8mb4&parseTime=True&loc=Local'
export MY_OPENWAF_TEST_POSTGRES_DSN='postgres://{user}:{password}@{host}:5432/waf?sslmode=disable'
go test ./internal/store -run TestAutoMigrateOnExternalDialect -v
```

`Open` 之后的公共配置对三种方言完全一致：慢查询阈值 200 ms、日志级别 `Error`、忽略「记录未找到」、跳过默认事务、开启预编译语句。

	switch strings.ToLower(db.Dialector.Name()) {

	}

}

## 性能考虑

- **问题**：SQLite 下多条写连接互相争用文件锁。
  **优化**：`sqliteMaxOpenConns = 8`（`gorm.go:113`），配合 WAL 与 `busy_timeout(10000)`；日志库关闭外键检查并把自动 checkpoint 收紧到 2000 页。
  **效果**：读并发可用，写突发被 `busy_timeout` 吸收，WAL 不无限膨胀。
- **问题**：`COUNT(*)` 与时间轴聚合在日志大表上代价高。
  **优化**：日志库复合索引按查询形态声明（`site_id,created_at,id`），聚合列走定长摘要。
  **效果**：分页走覆盖索引，指纹分组不扫描 TEXT 列。
- **问题**：MySQL 上 `ALTER TABLE` 不进入事务，迁移半程失败会留下中间态。
  **优化**：V6/V11 用标记行保证一次性，V5 把可容忍错误白名单化。
  **效果**：重复启动不会重复洗数据。
- **问题**：PostgreSQL 走 PgBouncer 时服务端预编译语句会失效。
  **优化**：`pgbouncer=true` 切简单协议（`gorm.go:143`）。
  **效果**：牺牲 `PrepareStmt` 收益换取连接池可用，属显式取舍。

## 结论

多数据库支持被压缩成「一个分发点、两类分支、三处显式适配」：`Open` 是唯一分发点；连接参数与结构迁移是仅有的两类分支；查询侧只有时间分桶、标识符引用与摘要索引三处需要知道方言。KISS 体现在不引入自研迁移框架与 SQL 生成层；YAGNI 体现在不为每种方言维护独立仓储实现；DRY 体现在摘要列一次设计同时解决 MySQL 键长限制与三库分组一致性；SRP 体现在 `dialect` 判断只出现在迁移函数与两个查询辅助函数内。

选型建议：单机或边缘节点用 SQLite，多节点共享配置与集中运维用 MySQL/PostgreSQL；若必须跨方言，注意 TEXT 列默认值与长复合索引这两条硬约束。
