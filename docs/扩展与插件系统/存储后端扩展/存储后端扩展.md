## 简介

本篇是「存储后端扩展」子域的索引文档，面向需要**替换或新增存储后端**的开发者。它回答三个问题：存储侧到底有哪些可扩展的接缝（seam）、每类扩展要改动哪些文件、扩展时必须守住哪些边界。

必须先厘清一件事：本项目的存储后端**不是可插拔注册表**。SQL 侧只有一个分发点 `database.Open`，通过 `Options.Driver` 在编译期已确定的三种方言（sqlite、mysql、postgres）之间选择；KV / 限流 / 事件扇出侧只有一个可选客户端工厂 `redis.OptionalClient`。因此「扩展存储后端」在本仓库中的真实含义是两条：一是在 `database` 包内增加一条方言分支，二是为 `RedisKV`、`RateLimiterBackend`、`HotCacheBackend` 这类已有接口增加第二个实现。任何「插入一个 MongoDB 驱动」式的设想都没有代码依据，具体论证放在 [NoSQL 存储适配](NoSQL%20存储适配.md)。

与已完成的 [数据存储层](../../数据存储层/数据存储层.md) 7 篇的分工是明确的：那 7 篇描述**现状与模型**（表结构、字段、仓储路由、Redis 现有用途），本 5 篇描述**如何扩展与替换**，两侧不重复同一张表，只互相链接。

## 详细组件分析

### 新增一种关系型数据库后端（最小闭环）

真实约束是「四处一起改」，缺一个就会在运行时才暴露。`database.Open` 只认 `Options.Driver`，而 `core.Config.Validate` 有独立白名单，两者必须一致（`postgresql` 别名在两处都要认，`dialect_test.go:98-109` 就是为锁死这个一致性而写的）。

```go
// 文件：internal/core/database/gorm.go
// 目标：接入名为 mydb 的第四种方言（示意，gorm 官方 driver 存在时可直接用）

import (
    mydbdriver "gorm.io/driver/mydb" // 新增依赖，同时写进 go.mod
    "gorm.io/gorm"
)

// 1) Options.Driver 的取值集合扩大，结构本身不变（gorm.go:22-27）。
//    不新增字段即可承载新方言，是这里唯一的 KISS 约束。

// 2) 打开函数：DSN 必填校验 + 错误脱敏，与 openPostgres 保持同构（gorm.go:134-149）。
func openMyDB(opt Options, gcfg *gorm.Config) (*gorm.DB, error) {
    dsn := strings.TrimSpace(opt.DSN)
    if dsn == "" {
        return nil, fmt.Errorf("mydb requires MY_OPENWAF_DSN")
    }
    db, err := gorm.Open(mydbdriver.Open(dsn), gcfg)
    if err != nil {
        // 复用 maskDSN，避免把凭据写进启动日志（gorm.go:162-199）
        return nil, maskDatabaseOpenError(err, dsn)
    }
    return db, nil
}

// 3) Open 的 switch 加分支（gorm.go:45-54），并在 config_validate.go:15-20
//    的白名单里加同一个字符串，否则校验阶段就会拒绝启动。
// 4) gorm.go:60-68 的非 SQLite 池调优分支会自动覆盖新方言，
//    若该方言需要不同取值，在此按 opt.Driver 再分支。
```

围栏说明：`Options`、`Open` 的签名与 `maskDatabaseOpenError`、`preferSimpleProtocolFromDSN` 的写法均来自 `gorm.go` 原文；`mydbdriver` 只是占位名称，仓库中不存在该依赖，落地时必须换成真实存在的 `gorm.io/driver/*` 包。DSN 全部以 `{占位}` 形态出现在文档其余部分。

### 替换 KV / 限流类扩展存储

`RateLimiterBackend` 是本项目唯一「同一语义双实现」的存储接口：`ratelimit.RateLimiter`（进程内固定窗口）与 `ratelimit.RedisRateLimiter`（Redis 有序集合滑动窗口）。`buildRateLimiterBackend` 在 Redis 客户端为 nil 时静默回落本地实现，这就是新增第三种后端的标准接入形状。

```go
// 文件：internal/app/server.go:123-128 的现有形状（原文节选，未改动）
func buildRateLimiterBackend(client rueidis.Client, prefix string, windowSec, maxReqs int, enabled bool) ratelimit.RateLimiterBackend {
    if rl := ratelimit.NewRedisRateLimiter(client, prefix, windowSec, maxReqs, enabled); rl != nil {
        return rl
    }
    return ratelimit.NewRateLimiter(windowSec, maxReqs, enabled)
}

// 扩展方式：实现 ratelimit.RateLimiterBackend 的 6 个方法
// （Enabled / Reconfigure / Allow / Increment / IsOverLimit / Close，
//   见 ratelimit.go:11-17），然后在本函数里加一条优先级分支。
// 注意 Allow 的语义是「失败开路」：RedisRateLimiter.Allow 在脚本出错时
// 返回 true（redis.go:134-138），新实现必须保持一致，否则 Redis 抖动会
// 变成整站 429。
```

同样的接口化形状出现在仓储侧：`HotCacheBackend`（`repository.go:18-26`）与 `WriteQueueBackend`（`repository.go:11-14`）之所以定义在 repository 包内，是为了切断 repository → cache/observability 的反向依赖。替换这两类后端时不要把它们挪到实现包，否则导入环立刻出现。

### 连接池与迁移的扩展边界

两条边界必须由文档守住，否则改动会串台：

1. **DB 连接池 ≠ HTTP 上游连接池**。前者由 `database/sql` 管理（`gorm.go:63-66`、`gorm.go:103-105`），后者由 `net/http.Transport` 与 hertz、quic-go 客户端管理（`transport.go:157-177`、`transport.go:872-876`）。两者没有任何共享旋钮，取值也刻意不同量级。详见 [连接池管理](连接池管理.md)。
2. **结构迁移 ≠ 数据迁移**。`store.AutoMigrate` 内两类操作按固定顺序编排，`V8` 必须早于结构迁移、`V9` 必须晚于默认槽列，这类因果写在调用点注释里（`migrate.go:45-49`、`migrate.go:96-101`）。新增迁移不得重排既有顺序，详见 [存储迁移机制](存储迁移机制.md)。

### 存储后端可用性状态机

SQL 句柄与 Redis 客户端的状态迁移路径不同：前者只有「未装配 / 已装配 / 已关闭」三态且任一失败即终止启动，后者额外拥有「未配置」「降级」两态，并可在运行期被整颗换掉。新增后端必须声明自己落在哪一侧，否则会破坏 `/readyz` 的判定口径（就绪要求 DB Ping 成功）。

## 性能考虑

存储扩展的性能红线只有三条，都来自代码而非经验判断：

- **SQLite 是 8 连接而非单连接**。`sqliteMaxOpenConns = 8`（`gorm.go:113`），`SetMaxOpenConns`/`SetMaxIdleConns` 都用它（`gorm.go:103-104`），`SetConnMaxLifetime(0)` 表示本地文件连接不轮换（`gorm.go:105`）。把「单连接」当既成事实去优化会得出错误结论。
- **主库与日志库是两份独立句柄**。`LogDB` 不是布尔开关式的共用连接，而是第二次 `database.Open`（`runtime.go:88-93`）产生的独立句柄，日志库的 PRAGMA 组与主库不同（`gorm.go:89` 对比 `gorm.go:94`）。
- **PrepareStmt 与方言池化可能冲突**。`gorm.go:39` 全局开启 `PrepareStmt`，PostgreSQL 走 PgBouncer 事务池时必须靠 `pgbouncer=true` 切简单协议（`gorm.go:143`、`gorm.go:157-159`），否则服务端预处理语句报错。

扩展新后端时，凡使用预处理语句的中间件都要提供同类「显式关闭」开关，并把它做成 DSN 参数而非新增配置字段，保持 `Options` 不变。

## 结论

本项目的存储扩展性是「窄接缝 + 明确边界」的产物：SQL 侧靠单一分发点与一份 `Options` 结构维持简单，Redis 侧靠 `RateLimiterBackend`、`HotCacheBackend`、`WriteQueueBackend` 三个接口维持可替换性。KISS 体现在不建插件注册表；YAGNI 体现在没有第二种 NoSQL 实现时就不预留驱动位；DRY 体现在 `maskDSN` 一处覆盖三种 DSN 形态；SRP 体现在方言选择、迁移编排、池管理、命令封装各占一个包。

已知取舍：驱动白名单在两处重复，用测试而非抽象来锁一致性（`dialect_test.go:98-109`）。下一步若真要接入第四种方言，工作量集中在第 6、7 步的方言分支，而不是打开函数本身。
