## 简介

本文是**扩展与替换视角**的迁移文档：回答「要新增一个迁移版本该写什么、注册在哪、怎么验证」「要替换备份/恢复的实现该动哪几个函数」。写现状的表清单、字段明细、迁移函数逐条解释属于 [数据存储层/数据迁移管理](../../数据存储层/数据迁移管理.md)，本文不复制其表格，只在该表之外补齐扩展所需的**版本-文件-行**定位、**可否重跑**判定与**新增迁移流程**。

迁移体系当前只有一个编排入口 `store.AutoMigrate`（`migrate.go:22-124`）与一个日志库入口 `store.AutoMigrateLogs`（`:126-139`），共调用 15 个 `Vn` 函数（V2–V15，其中 V13 拆成主库与日志库两个函数）。**没有独立迁移 CLI，也没有 down 迁移**：回退靠备份表重命名与配置备份 JSON，而不是反向 SQL。这一事实决定了扩展只能在「加新函数」维度上做，不能做版本回退。

三条硬约束不可绕过：其一，`V8` 必须早于结构迁移，否则唯一索引因未回填的重复值创建失败（`migrate.go:45-49` 注释原文）；其二，`V13` 主库部分必须早于 `AutoMigrateLogs`，因为启动期 CVE 目录对账会先写 `cve_rules`（`migrate.go:96-101`）；其三，`V6`/`V11` 依赖 `system_settings` 标记表，必须在结构迁移后再跑一次（`migrate.go:117-123`）。

## 架构总览

一次启动的迁移状态机如下：三类守卫（表存在性、列存在性、标记行）决定同一函数在新库、旧库、已迁移库上的三种走向；结构迁移夹在数据迁移与兜底补列之间。

```mermaid
stateDiagram-v2
    state "读取环境变量并取句柄" as OPEN
    state "前置数据迁移（V2/V10/V3/V4/V5/V6/V11/V8）" as PRE
    state "结构迁移 AutoMigrate(31 模型)" as SCHEMA
    state "结构后修补（V9/V13/V7/V15/V14）" as POST
    state "二次一次性迁移（V6、V11）" as RETRY
    state "日志库迁移 AutoMigrateLogs + V12/V13" as LOGS
    state "首启种子 SeedDefaults" as SEED
    state "就绪并进入重载链" as READY
    [*] --> OPEN
    OPEN --> PRE : 句柄可用
    PRE --> SCHEMA : V8 回填完成
    SCHEMA --> POST : 建表加列成功
    POST --> RETRY
    RETRY --> LOGS : system_settings 标记已写
    LOGS --> SEED
    SEED --> READY
    SCHEMA --> [*] : 任一步返回错误即终止启动
```

## 详细组件分析

### 迁移版本表

「是否幂等」指函数在**已迁移库**上重复执行不改变结果；「可否重跑」指**同一次启动内**被再次调用是否安全，两者的差异集中在标记行类与一次性改名类。

| 版本 | 文件:行 | 变更对象 | 是否幂等 | 可否重跑 | 守卫写法 |
|:----:|---------|----------|:--------:|:--------:|----------|
| V2 | `single_site.go:10` | `sites` 补 14 列；`listeners`/`forwarding_profiles` 改名备份 | ✓ | 否（改名后旧表不存在） | `HasTable("listeners")`（`:12`） |
| V3 | `rule_phase.go:13` | `rules.phase` 由 `rate_limit`/`owasp_default` 改写为 `custom` | ✓ | ✓ | `HasTable("rules")` + `WHERE phase IN`（`:14`、`:20`） |
| V4 | `recorded_resource_query_string.go:11` | `recorded_resources.query_string` 加列并回填，删 `ux_recorded_res_key` | ✓ | ✓ | `HasTable`/`HasColumn`/`HasIndex`（`:12`、`:17`、`:30`） |
| V5 | `site_tls_inheritance_defaults.go:12` | 删 `sites.min_tls_version`/`max_tls_version`/`alpn` 列默认值 | ✓ | ✓ | 方言 `switch`，sqlite 直接跳过（`:17-19`） |

| V9 | `default_policy.go:23` | 释放软删策略的默认槽、创建/收敛默认策略、修复 `rules`/`sites` 引用 | ✓ | ✓ | `HasTable` + `HasColumn("policies","default_slot")`（`:24`） |

func V16MigrateSiteExample(db *gorm.DB) error {

        !db.Migrator().HasTable(&migrationSystemSetting{}) ||

        return nil

### 种子与修订号的扩展边界

种子只承担「无人可登录」这一个缺口：`SeedDefaults` 在 `username = 'admin'` 计数为 0 时生成 16 字节随机口令（hex 32 字符），bcrypt 默认代价哈希后落库，并只在 `RowsAffected > 0` 时把明文返回一次（`seed.go:29-53`）。**它不预置任何 API 令牌**——旧文档中「首次运行生成默认 API Key」的表述与现状不符，令牌必须由已登录管理员在自己的账号下创建（`seed.go:16-18` 注释原文）。这也解释了 `V15` 为何要回填 `user_id`：令牌模型改为必须归属账号后，旧库里 `user_id = 0` 的令牌会静默失效（`api_key_owner.go:9-20`）。

修订号与迁移无关但常被混为一谈：`BumpRevision` 用 `ON CONFLICT DO NOTHING` 播种 `id = 1` 行，再以 `revision + 1` 原子自增，`RowsAffected != 1` 即报错（`migrate.go:141-160`）；`CurrentRevision` 走 `FirstOrCreate`（`:162-168`）。生产侧只有一个自增点：`reloadRuntime(propagate bool)` 在 propagate 为真时先 `BumpRevision` 再 `applySnapshotReload`（`server.go:1002-1010`），因此备份恢复末尾的 `reload()` 天然带一次版本推进。新增「配置变更后必须重建快照」的迁移时，触发方是这里的修订号，不是迁移函数本身。

## 结论

迁移体系是**单入口、单向、可重跑**的：`AutoMigrate` 一处编排 15 个函数，顺序即正确性；幂等靠表/列/标记行三类守卫，而不是靠 down 迁移；回退能力来自 V2 的时间戳备份表与 `BackupData` 配置载荷这两条外部路径。可扩展性集中在三个明确动作——加迁移文件、按因果插调用位置、同步备份清单，KISS 体现在不做版本表与迁移框架，YAGNI 体现在没有反向迁移需求时不预留 down 接口。**建议**：新增迁移一律先定守卫再定位置，凡「洗一次就要保护后续显式配置」的语义必须写标记行；涉及列名契约的改动（如 `trusted_cidr`）单独立项评审，不与常规迁移混提交。
