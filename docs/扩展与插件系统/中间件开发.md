## 简介

本项目的「中间件」有两种完全不同的形态，本文同时覆盖，并明确划界：

- **控制面 Hertz 中间件**：真正使用 Hertz 的 `app.HandlerFunc` 链式模型，注册点集中在
  `internal/admin/router.go` 与 `internal/admin/middleware.go`，只有 4 个
  （`SecurityHeaders`、`AccessLog`、`AuthMiddleware`、`RequireRole`）；
- **数据面自研请求处理层**：**不使用** Hertz 中间件链。数据面的每个监听只挂一个
  `app.HandlerFunc`（`dataplane.Handler(opts)`，经 `srv.NoRoute` 与 `CONNECT` 注册），
  拦截、判定、改写、代理全部写在这一个函数体的有序分支里，配合
  `internal/core/pipeline` 的阶段接口与 `internal/proxy` 的响应变换链构成中间层。

这条分界是刻意的架构选择，不是遗漏：数据面的分支需要读取**同一个**已解析请求上下文并就地短路，
用 Hertz 链表达会把状态拆散到多个闭包里，也无法复用 `sync.Pool` 归还语义。

**与既有文档的分工**（避免重复）：11 阶段的语义、短路优先级与缓存失效见
[执行阶段系统](规则引擎扩展/执行阶段系统.md) 与
[管道执行机制](../WAF%20引擎系统/引擎核心架构/管道执行机制.md)；
本文只讲**注册点、挂载层级、执行顺序骨架以及如何新增一个环节**，不重述阶段算法。

数据面侧最容易被误认为「中间件」的三件东西，实际形态各不相同：

1. **`HandlerForBind`** 是唯一的装饰器形态：把监听地址写进 Hertz 上下文，供
   `listenerBind`（`handler_support.go:102-110`）在 handler 内读回，实现「一个 handler 函数、
   多个监听各自绑定」；
2. **Alt-Svc 包装**（`server.go:1633-1640`）是闭包级装饰器，只在启用 HTTP/3 播报时把原 handler
   包一层加头逻辑，不改变处理顺序；
3. **`WithOnConnect`**（`server.go:1597-1609`）不是中间件而是连接级钩子，
   它把 TLS 握手信息与 JA3/JA4 指纹注入 `context`，handler 再用
   `tlsFingerprintFromContext` 取回（`handler.go:66-68`）。

上下文键是两套体系之间唯一共享的表达方式。控制面写入的键全部是字符串键，
由 `c.Set`/`c.Get` 传递：

| 键 | 写入方:行 | 读取方 | 语义 |
|----|-----------|--------|------|
| `request_id` | `middleware.go:154` | handler 与日志 | UUID，同时写 `X-Request-ID` 响应头 |
| `auth_user` / `auth_username` | `middleware.go:72-73`、`:116-117` | 业务 handler | 真实账号名（API Key 也取归属账号） |
| `auth_method` | `middleware.go:74`、`:118` | `AccessLog` :160 | `jwt` 或 `api_key` |
| `auth_role` | `middleware.go:75`、`:120` | `RequireRole` :133 | `admin`/`operator`/`readonly` |
| `auth_jti` | `middleware.go:76` | 会话与撤销链路 | JWT ID |
| `api_key_id` | `middleware.go:119` | 令牌审计 | 令牌主键 |
| `dataplane_bind` | `handler_support.go:96` | `listenerBind` | 数据面监听绑定串 |
| `dataplane_tls_fingerprint` | `handler.go:67` | 指纹与 Bot 阶段 | TLS 客户端指纹 |

## 详细组件分析

### 控制面中间件逐个拆解

`AuthMiddleware` 的判定顺序是「白名单 → 头存在性 → Bearer 前缀 → JWT → API Key」，
每一步的失败响应码都不同，这决定了排障时看哪个字段：

```go
// internal/admin/middleware.go:42-53（签名与白名单为实测原文）
func AuthMiddleware(keyRepo *repository.AdminAPIKeyRepo, accountRepo *repository.AdminAccountRepo,
	tm *auth.TokenManager, sessionMgr *auth.SessionManager) app.HandlerFunc {
	return func(ctx context.Context, c *app.RequestContext) {
		path := string(c.Path())
		if path == "/api/v1/health" ||
			path == "/api/v1/auth/login" ||
			path == "/api/v1/auth/refresh" ||
			path == "/api/v1/auth/logout" {
			c.Next(ctx)
			return
		}
```

两条特殊分支值得单列：`tm.VerifyAccessToken` 返回
`auth.ErrTokenBlacklistUnavailable` 时给 **503** 而不是 401（`middleware.go:85-89`），
因为那是服务不可用而非凭据无效，告警口径完全不同；
API Key 分支必须解析**归属账号**后才能取角色（:105-120），账号被删除令牌即失效，
不存在「API Key 默认 admin」的旧口径。

`RequireRole` 是无状态变参工厂：允许集合在构造期折叠成 map（:128-131），
运行期只做一次 `c.Get("auth_role")` 与查表；键不存在给「no role」，值不匹配给
「insufficient permissions」（:132-145）。它既可 `group.Use`，也可作为路由级实参
（`router.go:116`），后者用于「同组内个别端点需要更高权限」，
本项目只有强制下线这一处这么写。

`AccessLog` 与 `SecurityHeaders` 都是前后两段式：

- `AccessLog`（:150-170）前置生成 `request_id` 并写响应头，`Next()` 之后取
  `time.Since(start)` 与状态码记一条 `Info`；
- `SecurityHeaders`（:172-192）前置设 4 个固定头，并对 `/api/v1/` 前后各设一次
  `Cache-Control: no-store`（:180-186）——后置那一次是必需的，因为 handler 可能重写头；
  随后 4 个 `ensureAdmin*` 依据快照开关决定是否补 `X-XSS-Protection`、`Strict-Transport-Security`、
  `Public-Key-Pins`、`Public-Key-Pins-Report-Only`（:194-248）。判定条件统一是
  「快照非 nil ∧ 对应开关为真 ∧ 状态码 > 0」，HSTS/HPKP 还额外要求协议为 `https`/`h3`
  （:258-313），协议识别走 `adminRequestProtocol`（:315-334），
  其中回环来源才允许采信 `X-Forwarded-Proto`。

### 数据面处理层的阶梯结构

`dataplane.Handler(opts)` 返回的单个 `app.HandlerFunc` 内部是一条有序阶梯。
下表是实测的分支顺序，「短路即返回」意味着后续所有环节都不再执行：

| 序 | 分支 | 位置:行 | 短路即返回 | 触发条件 |
|:--:|------|---------|:----------:|----------|
| 1 | 绑定 CloseNotify + 生成请求 ID + 删 `Server` 头 | `handler.go:55-58` | 否 | 每请求 |
| 2 | 注册 `defer` 收尾（补记访问日志、还原请求体流、取消通知） | `handler.go:59-65` | 否 | 每请求 |
| 3 | 取 TLS 指纹写入上下文 + HTTP/3 内部元数据 | `handler.go:66-84` | 否 | 仅相应传输 |
| 4 | `handleWASMAssets` | `handler.go:87` | 是 | `/__owaf/pow.*` |
| 5 | `handleACMEChallenge` | `handler.go:91` | 是 | `/.well-known/acme-challenge/` |

### 阶段接口：中间层的可插拔点

`internal/core/pipeline` 提供数据面唯一的扩展抽象，签名是实测原文：

```go
// internal/core/pipeline/pipeline.go:277-280
type Phase interface {
	Name() string
	Execute(ctx *RequestCtx) (action.Result, bool)
}
```

第二个返回值是「停止本阶段链的后续处理」而非「请求终止」——`Run` 对挑战类结果会
把 `stop` 与 `IsChallenge` 分开处理，先暂存再让后续阶段有机会给出更高优先级的判定
（`pipeline.go:517-560`，优先级由 `action.TerminalPriority` 决定，`action.go:88-118`）。
`Category`、`Phase`、`MatchDesc` 三个字段最终会进安全事件表，
以 `rules.NewLuaPhase` 生成的结果为例（`lua_phase.go:101-109`）：

| 字段 | 来源 | 说明 |
|------|------|------|
| `Type` | `action.Normalize` 归一化结果 | 未知动作直接忽略，不拦截 |
| `RuleID` / `RuleIDStr` | 判定产出者的 ID/Name | Lua 场景为脚本 ID/脚本名 |
| `Matched` | 恒 `true` | 未命中的 `stop` 不进入 `ObserveHits` |
| `Phase` | `Name()` 返回值 | 如 `lua_pre`、`lua_post`、`owasp_default` |
| `Category` | 阶段自定 | Lua 固定 `lua_plugin` |

阶段与处理层的边界：阶段**拿不到** Hertz 对象，因此任何对真实请求的改写都必须经
`RequestCtx.SetRequestMutation` / `DrainRequestMutation`（`pipeline.go:300-306`、`:448-455`）
表达意图，由数据面在 `handler.go:1056-1075` 写回；管道内的就地生效则通过
`ApplyRequestMutation`（:319-388）完成，它先整体校验再整体应用，任何一项非法都让
整份改写失败而不留部分效果。保留头名单与 JS/Lua 侧逐项一致
（`pipeline.go:398-410`）。

### 响应侧变换链：另一种中间件

响应方向的「中间件」是 `identityResponseTransformer`，它的组合顺序即执行顺序，
实测在 `proxy.go:93-160`：

```go
// internal/proxy/proxy.go:61-63
type identityResponseTransformer interface {
	Transform(identityResponseEntity) (identityResponseEntity, error)
}
```

组合规则有两条硬语义：

1. **HTML → Markdown 协商短路整条链**。客户端显式请求 Markdown 时直接返回该变换器
   （`proxy.go:99-103`），因为动态混淆产出的是密文、脚本改写面向 HTML 形态，两者都无意义；
2. **固定顺序：图像转换 → browser sign 注入 → 动态保护 → JS response 脚本 → Lua post 改写**。
   图像必须早于动态保护（水印与格式转换都需要上游原图，`proxy.go:183-186`）；
   JS 早于 Lua，让 post 看到最终形态（`proxy.go:141-160`、
   `js_plugin_response.go:46-56` 的注释同口径）。

链的输入输出是 `identityResponseEntity`（`proxy.go:49-58`，含 `Body`、`ContentType`、
`ScriptNonces` 等），失败语义分两套：JS 侧按脚本 `FailureMode` 决定继续或返回错误
（`js_plugin_response.go:87-101`），Lua 侧逐项 fail-safe 跳过（:119-152）。
SSE/WebSocket 路径不使用 identity 实体，因此不受该链影响（`js_plugin_response.go:49-52`）。

打破 `proxy → dataplane` 反向依赖的手法值得复用：`proxy` 不认识 `dataplane`，
只持有两个由数据面在 `Handler(opts)` 构造期注入的查找函数
（`handler.go:45-47` → `js_plugin_response.go:21,42`）。

「数据面环节」有三种落点，选错落点比写错代码更常见：

## 性能考虑

- **控制面开销可忽略**：4 个中间件合计只有一次 UUID 生成、若干头写入与两次 map 查表；
  `RequireRole` 的允许集合在构造期折叠为 map（`middleware.go:128-131`），不在请求路径上分配。
- **数据面的成本在阶梯深度而非链长**：分支是顺序 `if`，未命中的分支只付一次字符串比较；
  真正需要关注的是第 14~21 步的解析与采样，以及 `matchInlineOWASPGuards` 的两次调用
  （`handler.go:332`、`:500`）——第二次仅在路径被脚本改写后才可能发生，前置有
  `jsRequestMutated && !skipInlineOWASP` 守卫（:499-501）。
- **对象池收益明确**：`AcquireCtx`/`ReleaseCtx` 复用 header map 与观察命中缓冲
  （`pool.go:20-34`），代价是 `ReleaseCtx` 必须穷举清理；新增字段忘记清理会表现为
  「偶发的跨请求串数据」，比性能问题更难查。
- **派生字段惰性化**：`HeaderOrder`/`ALPN`/`CipherSuites` 各只算一次
  （`pipeline.go:232-257`），避免每请求多次 `strings.Join`。
- **中间件不要做 I/O**：`AuthMiddleware` 的 API Key 分支走仓储 `Verify`（内存/缓存态），
  若在自定义中间件里查库，会把控制面的 P99 直接抬到 DB 水平。

## 结论

本项目把「中间件」一分为二：控制面沿用 Hertz 原生链，只有 4 个中间件、6 个挂载点，
顺序即注册顺序，能力边界是鉴权、角色、日志与安全头；数据面刻意不使用该链，
把全部拦截与判定收进一个 handler 的有序阶梯，再用 `pipeline.Phase` 提供可插拔点、
用 `identityResponseTransformer` 提供响应侧组合。两种形态的取舍标准一致：
**能被同一份请求上下文解释的逻辑就不要拆开**。

扩展时的三个硬约束：写操作只有 POST；`*RequestCtx` 不得逃逸出 `AcquireCtx`/`ReleaseCtx` 区间；
`proxy` 与 `dataplane` 之间只能通过查找函数注入，不得新增直接依赖。
