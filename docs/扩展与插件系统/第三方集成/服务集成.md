## 简介

本篇聚焦「服务集成」的双向语义：**出向**是 My-OpenWaf 作为客户端去连别人（上游源站、IdP、ACME CA、Redis），**入向**是别人作为客户端来连它（Prometheus、探针、管理台浏览器、编排系统、API 调用方）。

能力边界表必须先钉死，避免把本项目写成服务网格：

| 集成意图 | 本项目实况 | 判定依据 |
|---|---|---|
| 上游协议适配 | HTTP/1.1、HTTP/2、h2c、HTTP/3、WebSocket、SSE 透传；gRPC 仅 scheme 别名 + 字节透传 | `internal/upstream/scheme_alias.go:22-28`、`internal/proxy/proxy.go:1548` |
| 负载均衡 | 轮询 + 健康过滤 + 延迟择优，无权重/无一致性哈希 | `internal/upstream/health.go:219-231`、`:421-458` |
| 服务发现 | **未实现**，上游集合来自快照静态配置 | `internal/app/server.go:368-372` |
| 熔断与重试 | **未实现**，只有失败标记与探活恢复 | `internal/upstream/health.go:470-489` |
| 外部认证服务 | OAuth2 / OIDC **已实现**（授权码 + PKCE + 发现）；LDAP / SAML **未实现** | `internal/waf/accessgate/oauth.go:136-336`、`internal/admin/access/providers.go:20` |
| 证书服务 | ACME HTTP-01 **已实现**；DNS-01 / TLS-ALPN-01 **未实现** | `internal/acme/acme.go:146-155` |

| 被编排 | `/healthz` `/readyz` `/status` `/metrics` **已实现**，全部在管理端口且**无鉴权** | `internal/app/server.go:1053-1056` |

系统上下文表回答「和谁交互、怎么交互、断了会怎样」，与 [第三方集成总览](第三方集成.md) 的集成清单表互补：那张表讲状态，这张表讲容错。

| 外部实体 | 类型 | 交互方向 | 协议/方式 | 触发时机 | 失败影响 | 容错处理 |
|---|---|:--------:|---|---|---|---|
| 上游源站 | 后端服务 | 出向 | HTTP/1.1、H2、h2c、H3、WS、SSE | 每个转发请求；10s 探活 | 502/504；目标标记不健康 | 健康过滤 + 延迟择优 + 全不健康回落轮询起点 |
| IdP | 认证服务 | 出向 | OAuth2/OIDC over HTTPS | 首次登录与回调 | 无法建立会话，回落登录页 | 10s 超时 + 1MiB 上限；无自动重试 |
| ACME CA | 证书服务 | 出向 | ACME HTTP-01 | 手动申请、12h tick | 证书不更新，`renew_error` 落库 | 逐域名 continue，成功后 reload |
| 权威 DNS | 解析服务 | 出向 | CAA 查询 | 每次签发前 | 签发被拒（保守失败） | 3s 超时；策略可关闭 |
| Redis | 共享存储 | 出向 | RESP | 限流、会话、事件扇出、广播 | 分布式能力退化 | nil 客户端 → 内存分支 |
| Prometheus | 监控 | 入向 | HTTP GET `/metrics` | 抓取周期 | 看板缺数据 | 无（不影响转发面） |
| 编排系统 | 运维 | 入向 | HTTP GET 探针 | 探针周期 | 实例被判不可用 | 就绪需快照 ∧ `lm.Ready()` ∧ DB Ping |
| 管理台浏览器 | 前端 | 入向 | WebSocket + REST | 登录后 | 实时视图停更 | 票据 60s，一次一用 |

## 详细组件分析

### 上游协议与 scheme 归一

上游 URL 的 scheme 先折叠大小写，再按别名表归一：`tls://`、`grpcs://`、`grpc+tls://`、`grpc+https://` → `https`，`grpc://` → `h2c`（`internal/upstream/scheme_alias.go:22-28`）。归一只改传输层，不改业务语义，因此 gRPC 依旧是 HTTP/2 上的字节流：`application/grpc` 前缀的响应被明确排除出边缘缓存（`internal/proxy/proxy.go:1548`），**不存在 protobuf 解析、方法级路由或 gRPC 状态码改写**。

协议偏好分组按版本排序，用于同一站点混配多协议上游时的优先选择：`h3`=3、`h2c`=2、`https`=1、其余=0（`internal/upstream/health.go:381-402`，分组函数 `GroupURLsByProtocolPreference`）。

### 连接池与出站头处理

主传输参数是唯一的连接池真值：`MaxIdleConns 256`、`MaxIdleConnsPerHost 32`、`IdleConnTimeout 30s`（`internal/proxy/transport/transport.go:157/159/161`），另有 `MaxConnsPerHost 256`（`:172`）、16KiB 读写缓冲（`:163-164`）、`ExpectContinueTimeout 1s`（`:166`）、TLS 握手 10s 与响应头 30s（`:176-177`）。探活走另一套更小的 transport：`128/32` + `MaxConnsPerHost` 常量（`internal/upstream/health.go:660-675`）。

出站前必须重建转发身份头：客户端自带的 `Forwarded`、`X-Forwarded-For`、`X-Forwarded-Host`、`X-Forwarded-Proto` 全部删除后按真实连接信息重写（`internal/security/outbound.go:33-52`），这是后端拿到正确客户端 IP 的唯一保证。

上游列表完全来自站点配置进入的快照，`Pool` 的 `urls` 参数是一个每次 tick 重新读取的回调（`internal/app/server.go:368-372`），这是本项目**唯一**为「动态后端」留出的形状。仓库没有 Consul、etcd、ZooKeeper 或任何 DNS SRV 轮询实现（`go.mod` require 段无相关依赖）。

若要接服务发现，不需要动选路逻辑，只需替换该回调的数据源：

```go
// 现状 internal/app/server.go:368-374
upstreamPool := upstream.NewPool()
upstreamPool.StartWithResult(ctx, func() []string {
	if sn := rt.Snapshot.Load(); sn != nil {
		return snapshotUpstreams(sn) // ← 服务发现替换点：返回 registry 查询结果
	}
	return nil
}, 10*time.Second, upstream.HTTPProbeWithResult(2*time.Second))
```

## 性能考虑

- 传输复用：三类 transport 各自独立（主 256/32/30s、h2c 单例 512/128/90s、探活 128/32/90s），互不挤占空闲连接额度。
- 选路代价：`Pick` 只做一次线性扫描（最多 `len(urls)`），延迟择优在同一轮里完成，无额外锁竞争之外的开销（`internal/upstream/health.go:219-231`、`:421-458`）。
- 认证出向：每个新会话两次外呼（token + userinfo），已用 10s 超时与 1MiB 读取上限封顶；同一会话期内不再出向（`internal/waf/accessgate/oauth.go:26-32`）。
- 广播不阻塞：实时推送单客户端队列 8，慢客户端只会丢消息，不会拖住 ticker（`internal/admin/system/realtime/realtime.go:27`）。
- 配置广播是发布即忘：2s 超时后只记 Warn，不把远端生效作为成功条件（`internal/core/redis/pubsub.go:76-82`）。

## 结论

服务集成的真实现状可以一句话概括：**入向被集成面完整且无鉴权，出向集成只有五类真实连接（上游、IdP、ACME CA、DNS、Redis），没有任何形式的服务发现、熔断、重试或消息队列**。本轮把这三件事分别落成系统上下文表、外部服务依赖表与被集成端点鉴权表，并订正了两处历史错误：把 OAuth/OIDC 写成「未发现实现」（实际已含 PKCE 与 OIDC 发现）、把 gRPC 写成协议级支持（实际只有 scheme 别名与透传）。

下一步若要扩展，优先级建议：先补 ACME 出向超时（当前依赖调用方 ctx，属未设置风险项），再考虑把 `snapshotUpstreams` 回调升级为可插拔的后端源，最后才是 MQ 导出——后者的正确挂载点在观测性 flush 侧，见 [消息队列集成](消息队列集成.md)。
