## 简介

**定位纠偏**：本篇沿用目录里既有的文件名 `消息队列集成`，但项目里**不存在任何消息队列中间件**。
实测依据是 `go.mod` 的 require 段：与非关系型后端有关的客户端只有
`github.com/redis/rueidis v1.0.78`，另外 `github.com/gorilla/websocket v1.5.3` 用于管理台推送；
**没有** Kafka（sarama / kafka-go）、RabbitMQ（amqplib）、Pulsar、NATS、MQTT（paho）等任何队列件。
全库对 Redis 的调用中，`Publish` 与 `Subscribe` 各只出现一次，都在 `internal/core/redis/pubsub.go`；
没有 `XADD`/`XREADGROUP`/`BRPOP` 之类的队列命令。

因此本篇的真实主题是：**本项目实际存在的进程内与跨实例异步通道**，共三条：

1. **Redis Pub/Sub 配置同步**（跨实例、非持久、无重连）——`internal/core/redis/pubsub.go`，
   频道固定 `openwaf:config:reload`，发布 2s 超时，靠 `sourceID` 抑制回环；
2. **进程内异步写通道**（仅本进程、有界队列、满即丢或同步降级）——
   `internal/observability.WriteQueue` 与 `UnifiedWriter`，配合 `Archiver` 做保留期收敛；
3. **管理台 WebSocket 扇出**（进程内发布、跨进程只到浏览器）——
   `internal/admin/system/realtime`（616 行）+ `router.go` 的 `/api/v1/realtime/ws`。

需要特别澄清一处常见误读：`internal/dataplane/sse.go` 的 `ForwardSSE` **不是**本项目的事件总线，
它是面向**客户上游**的 `text/event-stream` 响应流式透传，把上游推给浏览器的事件原样搬过去，
既不产生事件也不消费事件（详见「数据面 SSE 透传边界」一节）。

任何把本篇当作「Kafka/RabbitMQ 接入指南」的读法都会落空。若确实要接入外部队列，
真实挂载点在 `UnifiedWriter.flushBuffered` 之前与 `ConfigSync.PublishReload` 的替换处，
本篇附录给出扩展点清单。Redis 作为存储后端的能力边界见
[NoSQL 存储适配](../存储后端扩展/NoSQL%20存储适配.md)，本篇只谈「通道」不谈「存储」。

## 核心组件

三条通道的能力对照是本篇的**主表**：投递语义一栏决定你该不该把状态放上去。

| 通道 | 范围:行 | 投递语义 | 持久性 | 失败行为 | 适用场景 |
|------|---------|----------|--------|----------|----------|
| 配置重载广播 | `core/redis/pubsub.go:65-121` | 至多一次，离线即永久丢失 | 无持久化（Pub/Sub 无留存） | 发布失败仅 `warn`（:79-81），本地重载照常完成；订阅 `Receive` 返回即结束，**不重连**（:97） | 让其他节点重建快照；不是配置同步的唯一保证 |
| 仓储写队列 | `observability/write_queue.go:300-394` | 最多一次：`Submit` 满即丢；`SubmitWait`/`SubmitPriority` 满则**同步降级** | 落库即持久，队列本身进程内存 | 满丢弃计数 `dropped_full_total`；事务失败整批记失败；回调 panic 转 error（:264-286） | SQLite 单写者下的写合并，消除锁竞争 |
| 观测记录通道 | `observability/unified_writer.go:566-690` | 最多一次；有 `slowLogGrace` 宽限（默认 30s） | DB 为权威；Redis LIST 只是副本 | 连续满超宽限即丢弃并计数；关停预算 8s+5s，超时放弃剩余记录 | 访问日志/安全事件/drop/bot 评分的高吞吐落库 |
| Redis LIST 扇出 | `observability/unified_writer.go:1094-1152` | 尽力而为，先于 DB 事务推送 | `LTRIM` 上限 + 7 天 TTL | 单条 `resp.Error` 即整批判失败，只 `warn`，DB 事务继续 | 外部实时消费方的低延迟副本；**不可当可靠队列** |
| 管理台 WS 扇出 | `admin/system/realtime/realtime.go:467-581` | 每客户端有界队列 8，满则丢最旧再塞新 | 无（快照可重取） | 再塞仍失败则直接踢掉该客户端连接（:477-479） | 控制台实时看板与播报 |
| 上游 SSE 透传 | `dataplane/sse.go:20-89` | 逐块搬运，不缓存不重放 | 无 | 上游错误直接返回给数据面处理 | 客户自有事件流穿过 WAF |
| 保留期清理 | `observability/archiver.go:332-401` | 定时任务，非消息 | 删除即生效 | 仓储 panic 被转 error（:137-144），单表失败不杀循环 | 控制存储增长 |

两条设计口径必须先固定：**权威状态只在关系库**，Redis 上的频道与 LIST 都是通知或副本；
**所有队列都是「有界 + 丢弃可观测」**，没有任何一条通道具备 ACK、重试、死信或回放语义。
需要可靠消费时读 DB，不读 Redis LIST。

`WriteQueue` 与 `UnifiedWriter` 是两套独立通道，不可混为一谈：前者接收「写函数」
（`func(tx *gorm.DB) error`），由仓储层调用；后者接收「记录结构体」，由数据面热路径调用。
前者的默认容量是 256 条任务，后者是 16384/8192 条记录。

## 详细组件分析

### 通道一：Redis Pub/Sub 配置同步

频道与消息形态（`pubsub.go:16-22`）：

```go
const configSyncChannel = "openwaf:config:reload"
const configSyncActionReload = "reload"

type configSyncMessage struct {
	SourceID string `json:"source_id"`
	Action   string `json:"action"`
}
```

发布侧只有一个入口 `PublishReload`：构造 JSON、2s 超时、失败只写 `warn`（:77-81）；
`cs == nil` 或 `client == nil` 直接返回（:66-68），未启用 Redis 的部署完全无感。
`NewConfigSync` 在 `client == nil` 时返回 nil（:39-41），调用方必须做接口判空。

订阅侧有两个必须知道的边界：

1. **无重连**。`Subscribe` 只调用一次 `client.Receive`（:97），返回即订阅结束，没有任何重启循环。
   Redis 端断连后本节点静默失去跨节点重载通知，只能靠下一次本地变更或重启恢复。
2. **裸 `"reload"` 串会自我回环**。`Receive` 回调先判 `msg.Message == configSyncActionReload`
   （:98-104），命中就无条件执行 `reload()`，**不比对 `source_id`**；JSON 分支的回环抑制在
   :111-116。因此手工 `PUBLISH openwaf:config:reload reload` 会让发起节点自己也多重载一次。

```go
// internal/core/redis/pubsub.go:111-120
if event.Action != configSyncActionReload {
	return
}
if event.SourceID != "" && event.SourceID == cs.sourceID {
	return
}
cs.log.Info("received config sync reload")
if err := reload(); err != nil {
	cs.log.Error("config sync reload failed", slog.Any("err", err))
}
```

`sourceID` 缺省时由 8 字节随机数十六进制生成（:45-47、:56-62）。`replaceConfigSync`
（`server.go:834-847`）传的是空串，因此每次 Redis 热切换都会得到新的 `sourceID`。
关停路径值得注意：`Subscribe` 内部起了一条协程，`stopCh` 关闭时调用的是
`cs.client.Close()`（:93-96）——关的是**共享** client，所以热切换必须「先新建、再关旧」，
复用同一实例会把新订阅一起误杀。

| 键设计 | 值 | 位置 | 说明 |
|--------|----|------|------|
| 频道名 | `openwaf:config:reload` | `pubsub.go:16` | 全库唯一 Pub/Sub 频道 |
| 动作常量 | `reload` | `pubsub.go:17` | 同时是旧格式的裸串兼容值 |
| 消息体 | `{"source_id":"16hex","action":"reload"}` | `pubsub.go:19-22`、`:69-72` | `source_id` 为空即失去回环抑制 |
| 发布超时 | 2s | `pubsub.go:77` | 与限流 50ms、扇出 5s 分属不同预算 |
| 订阅 context | `context.Background()` | `pubsub.go:97` | 不受请求取消影响，由 `stopCh` 收尾 |
| 客户端拨号超时 | 5s（`Dialer.Timeout`） | `redis.go:26` | 写超时 3s（:27） |
| 键体系归属 | 不写任何键 | — | Pub/Sub 与 `openwaf:`/`owaf:`/`waf:` 三套前缀无关 |

### 通道二：WriteQueue 仓储写队列

`WriteQueue` 接收的是**写函数**而非记录，接口契约在仓储侧以窄接口定义，避免
`store → observability` 的反向依赖：

```go
// internal/store/repository/repository.go:11-14
type WriteQueueBackend interface {
	Submit(fn func(tx *gorm.DB) error)
	SubmitWait(fn func(tx *gorm.DB) error) error
}
```

`Repos.SetWriteQueue` 只接到三个仓储：`AccessLog`、`SecurityEvent`、`DropEvent`
（`repository.go:99-102`）。装配点在 `server.go:328-335`，容量、批大小、ticker 周期
全部来自 `rt.Config.Queue`。

三种提交方式的语义差异是这套通道的核心：

| 方法 | 满时行为 | 返回 | 使用方 |
|------|----------|------|--------|
| `Submit`（:300-325） | 直接丢弃，`dropped_full_total` 计数 + 限频 warn | 无 | 热路径异步补写 |
| `SubmitWait`（:332-362） | 降级为**同步执行**，`sync_fallback_total` 计数 | `error` | 调用方必须知道结果 |
| `SubmitPriority`（:365-394） | 同上同步降级 | `error` | 鉴权变更等紧急写，入队即触发 flush |

关闭队列后三种入口统一走 `dropped_closed_total` 并返回 `ErrWriteQueueClosed`（:65、:306-311）。
`submitMu` 读写锁把「检查 closed」与「发送」组成一个临界区，杜绝「检查时未关闭、
发送时消费循环已退出」的悬空任务（:33-38 注释、:426-439）。

批执行的原子性口径也值得单列：`flushBatch` 在**单个事务**里跑完整批任务，
每个回调先拿一个 `SAVEPOINT wq_i`，失败则 `RollbackTo`（:539-561），
所以一条写坏的记录不会连累同批其余记录；但事务级错误会让**整批**都不算持久化，
包括那些回调返回 nil 的（:564-579）。这里刻意**不重试**——通用写函数没有幂等契约，
提交结果不明时重试可能造成重复写入。

### 通道三：UnifiedWriter 观测记录通道

四条独立有界通道，默认容量与批参数（`unified_writer.go:124-129`、`:399-409`）：

| 通道 | 记录类型 | 默认容量 | 触发 flush |
|------|----------|:--------:|-----------|
| `eventCh` | `store.SecurityEvent` | 16384 | 四类累计 ≥ 256 或 3s 定时 |
| `accessCh` | `store.AccessLog` | 16384 | 同上 |
| `dropCh` | `store.DropEvent` | 8192 | 同上 |
| `botScoreCh` | `store.BotScoreLog` | 8192 | 同上 |

`drainLimit` 取 `4 × BatchSize` 以限制单次事务体积（:407-409），定时分支用 `drainChanInto`
把四路一次性吸到上限（:783-788）。硬上限集中在 `:113-120`：容量 1M、批 10K、flush 周期 60s、
慢速宽限 5m；越界由 `clampUnifiedWriterOptions` 钳制并打 WARN（:289-327），`BatchInterval` 不设上界。

关停预算分两段：`unifiedWriterCloseTimeout = 8s`（逐批之间检查的排空 deadline）加
`unifiedWriterCloseGrace = 5s`（兜底等待 loop 退出），因为 deadline 打不断已进入驱动的
那一次写入（:341-349、:702-744）。`abortWaitCh` 与 `stopCh` 必须是两个 `sync.Once`
（:67-71 注释）：前者在取写锁**之前**关闭，让正在慢速等待的入队立刻退回丢弃，
`Close` 才可能拿到 `submitMu` 写锁；共用一个 `Once` 会让第二次 `Do` 变空操作，
`stopCh` 永不关闭、排空分支永不执行。

Redis 扇出在同一个 flush 里、**先于** DB 事务执行（:921-927），整批 5s 超时，
四个 LIST 各自 `LPUSH` + `LTRIM` + `EXPIRE 7d`（:1094-1152）：

| 键 | 结构 | LTRIM 上限 | TTL | 位置 |
|----|------|:----------:|:---:|------|
| `openwaf:security_events` | LIST | 99999 | 7 天 | `:1130` |
| `openwaf:access_logs` | LIST | 99999 | 7 天 | `:1137` |
| `openwaf:drop_events` | LIST | 49999 | 7 天 | `:1144` |
| `openwaf:bot_scores` | LIST | 49999 | 7 天 | `:1151` |

因为扇出先于落库，Redis 里可能短暂存在尚未持久化的记录；反过来说，
`pushToRedis` 失败只把 `failed` 置真并告警，不影响落库、也不重试——
这四个 LIST 是**尽力而为的下游副本**，不是可靠队列。

### 通道四：Archiver 保留期收敛

`Archiver` 不是消息通道，但它是三条通道的下游收敛点，且旧文档对它有两处错误必须订正：

1. **默认清理间隔是 24 小时，不是 1 小时**（`defaultArchiverIntervalSeconds`，:53-57）；
   且 `loop` 是「先等 timer 再看 stopCh」（:219-242），**启动时不预跑清理**。
2. **分批删除 5000 行 / 每批之间 sleep 50ms**（`repository/security_event.go:410-431`），
   用 `id IN (SELECT id ... LIMIT 5000)` 的方式缩小锁范围；`access_logs`、`drop_events`、
   `threat_intel_sync_logs` 三张表同口径。

保留配置有三个来源，由低到高依次覆盖：构造参数（30 天，`server.go:352-357`）、
系统设置里的 `retention_config` JSON、单项键 `security_event_retention_days` /
`access_log_retention_days`（:244-330）；天数取 0 表示**永不清理**，负值回退 0 并告警（:94-104）。
清理之后按方言做维护：SQLite 走 `PRAGMA optimize` + `wal_checkpoint(PASSIVE)` +
`wal_checkpoint(TRUNCATE)`，MySQL 走 `OPTIMIZE/ANALYZE TABLE`，PostgreSQL 走 `VACUUM ANALYZE`，
统一 30s 超时（:409-472、:474-511）。

需要登记的实测缺口：`bot_score_logs` 与 `stats_retention_days` 都**没有对应的清理分支**，
`SetRetention` 在生产路径上无调用方，归档器本身也没有专属指标。

### 数据面 SSE 透传边界

`internal/dataplane/sse.go` 的定位必须说清楚：它是**反向代理的一段流式转发实现**，
与项目自身的通知机制无关。判定只看客户端 `Accept` 是否含 `text/event-stream`
（`IsSSERequest`，:262-277，且要求其后是串尾或 `;`/`,`/空白，避免 `text/event-streamx` 误判）。

转发路径的要点：逐跳头、`Host` 与内部标记头 `x-openwaf-internal-*` 一律不转发给上游
（`sse.go:39-49`、`:115-117`）；上游响应头按 `IsHopByHop` 与 `Connection` 令牌过滤（:60-68）；
强制 `Cache-Control: no-cache`、**删除** `Connection` 与 `Content-Length`、`SetContentLength(-1)`、
`ImmediateHeaderFlush = true`（:77-81）；优先走 `StreamResponseViaHijack`，失败才回落
`SetBodyStream`（:83-86）；`sseBodyStream` 用 `mutex + cond` 跟踪活跃读者，确保 `cleanup`
等所有 `Read` 退出后才 `rc.Close()` 并取消上游 context（:141-215）。

数据面在主 switch 里排在扩展 CONNECT 与 WebSocket 之后（`handler.go:1126-1131`），
命中 SSE 的请求不参与响应体记录与大小统计（:1229）。

结论：**本篇的三条通道与 SSE 透传没有任何交汇**。若客户上游用 SSE 推事件，WAF 只做搬运；
WAF 自己的事件出口是 Redis LIST 扇出与 `openwaf_writer_*` 指标，两者不可混用。

## 性能考虑

- **入队必须非阻塞**。热路径只允许一次 `select`：`deliver` 的快路径与 `WriteQueue.Submit`
  都是这个形状（`unified_writer.go:630-636`、`write_queue.go:314-320`）。任何新增的
  「等一会儿再丢」都必须有窗口上限，且以「连续满」计时而非按条计时。
- **合并写入的收益点在事务数**。`flushBatch` 把整批放进一个事务并逐 job 加 SAVEPOINT
  （`write_queue.go:539-561`），`UnifiedWriter` 把四类记录放进一个事务
  （`unified_writer.go:936-1009`），这是 SQLite 单写者下消除锁竞争的主要手段。
- **预算要分层**。发布 2s、扇出整批 5s、KV 单命令 1s、排空 8s+5s、归档维护 30s、
  WS 写 3s。新增调用点必须显式 `context.WithTimeout`，不要沿用无超时写法。
- **告警必须限频**。两处丢弃告警都限 10s 一条（`write_queue.go:67`、`unified_writer.go:330`），
  计数器仍逐条累加；持续背压下逐条打日志会在磁盘 I/O 上二次放大故障。
- **轮询式扇出的成本随订阅者增长**。`RealtimeHub.Start` 每个分支先查
  `hasSubscribers` 再查库（`realtime.go:250-283`），没有客户端时零 DB 开销；
  若要提高频率，应改为事件驱动而不是缩短 ticker。
- **容量调大不等于不丢**。真正的丢失发生在 DB 长期落后：宽限窗口之后一律退回丢弃，
  上限 5m 只是把「能救的削峰」救回来（`unified_writer.go:117-120`、`config.go:105`）。

## 结论

本篇把「消息队列集成」标题下的虚构内容全部替换为实测事实：**项目没有任何 MQ 客户端**，
真实的异步能力由三条通道构成——Redis Pub/Sub 负责跨实例的「重载提醒」这一种动作，
`WriteQueue` 与 `UnifiedWriter` 负责进程内的有界批量落库，`RealtimeHub` 负责到浏览器的轮询式扇出。
三者的共同取舍是：**放弃可靠投递换取不阻塞热路径**，再用「丢弃必须计数、告警必须限频、
关停必须有界」把不可靠变成可观测。

对扩展者的判断标准只有一条：某个状态丢了会怎样。丢了只是看板晚几秒的，走 WebSocket；
丢了要重算的，走进程内队列并接受丢弃计数；丢了会导致集群长期不一致的，
**必须落到关系库并由修订号驱动重载**，不能依赖 Pub/Sub——它至多一次、不重连、无留存。

订正清单：外部 MQ 由「可扩展建议」改列为「未实现」；归档间隔 1 小时订正为 24 小时且启动不预跑；
`UnifiedWriter` 批大小订正为 256 并补上默认 30s 慢速宽限；SSE 由「事件流」纠偏为「上游透传」；
新增 Pub/Sub 无重连与裸串自我回环两条硬边界。
