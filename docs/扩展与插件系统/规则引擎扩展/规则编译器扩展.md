## 简介

本篇只回答一个问题：**要扩展「编译器」本身，改哪里、按什么顺序改、会踩什么坑**。
这里的「编译器」指把规则表达式（DSL 串或 JSON 复合条件）转换为可执行匹配器的两段代码：
快照构建期的 `compileRules` 与请求路径的 `rules.Compile`。

为避免与已完成文档重复，划界如下，遇到交叉一律以链接为准：

本篇的三条结论先说在前面：编译是**两遍**的（快照期一遍、引擎期一遍），两遍各自持有
一份 kind 白名单；两处 fail-closed 都在**编译期**发生而不是运行期抛错，因此错误只表现为
「规则永不命中」而不是「规则保存失败」；校验函数的 `switch` **没有 default 分支**，
未登记的 kind 会直接通过校验。

## 详细组件分析

### 两处 kind 白名单与一处 phase 白名单

同一份「允许的名字」在项目里存在三处独立集合，互不引用。扩展时三处都要看清，
但**只有前两处需要同时改**，第三处是 phase 维度、仅在新增阶段时涉及。

| 白名单 | 定义位置 | 条目 | 判定作用 | 缺失后果 |
|--------|----------|:----:|----------|----------|
| `rules.knownPrefixes` | `compiler.go:119-142` | 57 | 引擎期 `ParsePattern` 是否认这个 kind；校验期是否放行 | 规则在编译期被静默丢弃（`Compile` 里 `continue`） |
| `snapshot.ParsePattern` 内联 `prefixes` | `build.go:1205-1215` | 30 | 快照期是否把规则纳入 `CompiledRule` | 规则连快照都进不去，引擎期根本没有输入 |
| `store.skipPathPhaseKeys` | `protection.go:326-334` | 9 | 允许配置「按路径跳过」的 phase 名 | `ValidateSkipPathByPhase` 直接报 `unsupported phase` |

实测差集关系：`build.go` 的 30 项是 `knownPrefixes` 57 项的**真子集**，
差集恰为 **27 项**（`path_wildcard`、`body_wildcard`、`block_body_regex`、
`block_header_exact` 等只被引擎期接受）。这带来一条硬性约束：

> 新增 kind 若只补 `build.go` 不补 `compiler.go`，快照会接受但引擎会丢弃；
> 若只补 `compiler.go` 不补 `build.go`，规则可以在管理端保存并通过 `ValidateRule`，
> 却永远不会进入快照，表现为「保存成功但不生效」。
> 两种情况都不报错，这是全系统最难排的一类缺陷。

`skipPathPhaseKeys` 的第三个位置独立于规则 kind，它的消费点有两个：
`internal/admin/shared/json_bind.go:44-63` 的持久化前校验，
与 `engine.go:471-477` 的按阶段包装装饰器。`signature` 与 `custom` 有意不在其中，
因为用户自建规则本身可以直接停用（`protection.go:320-325` 的注释给出理由）。

### 新增一类编译目标的流程（一）：登记与构建

「编译目标」指 `buildMatcher` 分派出来、被 `Compiled.matcher` 持有的具体类型。
第一半只解决「能被编译出来」，改动点固定为四处，顺序不可调。

| 步 | 动作 | 位置 | 判据 |
|:--:|------|------|------|
| 1 | 决定 kind 名与 arg 语法，并确认它不属于既有 57 项 | `compiler.go:119-142` | 命名与前缀不冲突（首个冒号为界） |
| 2 | 把 kind 加入 `knownPrefixes` 的规范清单 | `compiler.go:120-136` | `ParsePattern` 能返回该 kind |
| 3 | 实现匹配器类型与 `Match(MatchCtx) bool` | 新增于 `matcher.go` 匹配器族附近 | 空输入必须返回 false，不得 panic |
| 4 | 在 `buildMatcher` 加 `case`，非法参数回落 `neverMatcher` | `matcher.go:1473-1775` | `default` 分支保持原样，不得吞掉 |

在每次 revision 变更时产生成倍的编译抖动。

### 新增一条 pattern 校验规则

校验层是唯一「会向管理端报错」的地方，扩展点集中在三个函数，彼此调用关系简单：

- `ValidatePattern(pattern) (kind, arg string, errs []string)`（`validate.go:26-32`）
  是对外入口，`admin/rule/validate.go:51-62` 与规则保存路径都用它；
- `validateParsedPattern(kind, arg)`（`validate.go:36-44`）是编译期的内部入口，
  返回值只看长度不看内容，**非空即降级为 `neverMatcher`**；
- 叶子校验 `validateSimplePattern`（`validate.go:123-257`）按 kind 分组给中文提示。

两个必须注意的实现事实：

1. **没有 `default` 分支**。`switch kind` 走完所有 `case` 后直接 `return ""`，
   所以一个已登记进 `knownPrefixes` 但没有校验分支的新 kind，会「无条件通过校验」。
   这不是 bug 而是既成事实，扩展者必须自己补 `case`，不能期待编译器兜底。
2. 校验函数会调用 `cachedCompile`（`validate.go:139-256` 多处），
   因此**一条非法正则在保存期就会写入正则缓存的编译尝试路径**（失败不入表，
   但成功入表且永不淘汰）。批量导入规则时，这条路径会放大缓存体积。

新增校验时的推荐写法与既有分支保持一致：先判空、再判格式、最后判可编译性，
错误串用中文且不包含用户输入的原始值（避免日志与响应中出现可控内容）。

### 新增一个归一化步骤

编译链上有两类完全不同的「归一化」，扩展点不能混。

第一类是 **arg 归一化**，发生在 `ParsePattern` 内，规则很窄：
`strings.TrimLeftFunc(p, unicode.IsSpace)` 只剥前导空白（`compiler.go:149`），
JSON 分支额外 `TrimSpace`（:153），DSL 分支中**只有 `_wildcard` 后缀的 kind 保留 arg 原样**，
其余才 `strings.TrimSpace(arg)`（:164-167）。理由写在注释里：对通配符匹配器而言
首个冒号之后的空白是模式的一部分。新增 kind 若名字以 `_wildcard` 结尾，
会自动落入「不 trim」分支——这是命名即语义的隐式契约，改名等于改行为。

第二类是 **载荷归一化**，属于 OWASP 检测侧，入口
`normalizeTarget(s string, queryPlusAsSpace bool) string`（`internal/waf/owasp/normalize.go:62-192`）。
它是一条有严格顺序依赖的链，新增步骤必须插在正确位置而不是追加在末尾：

| 阶段 | 步骤 | 顺序约束（违反的后果） |
|:----:|------|------------------------|
| 1 | UTF-7 预解码（门限：结果须产生标记字符） | 必须先于 URL 解码，否则 `+ADw-` 被解成空格而整体漏检 |
| 2 | U+2215 归一为 `/` | 先于路径穿越判定 |
| 3 | overlong UTF-8 百分号与字节对归一 | 先于多层 URL 解码 |
| 4 | 至多三轮 URL 解码 | 首轮用 `queryPlusAsSpace` 语义 |
| 5 | 解码产物二次 overlong 归一 | 处理 `%25C0AE` 之类多层产物 |
| 6 | 多轮 HTML 实体解码 | 条件门限 `shouldDecodeHTMLEntities` |
| 7 | JS 转义解码（`\xNN`/`\uXXXX`/八进制） | 其后必须再接一轮 URL 解码 |
| 8 | JS 转义后再至多三轮 URL 解码 | 覆盖双重/三重编码 |
| 9 | UTF-7 终解码 | 处理 `charset=UTF-7` 载荷 |
| 10 | 小写化、`%uXXXX` 解码、零字节剥离 | 零字节须**剥离而非替换空格**，否则破坏词形 |
| 11 | 内嵌混淆标签剥离、SQL 注释剥离、空白折叠 | 三者顺序固定，折叠必须最后 |

新增步骤的自检口径：只对**确实出现该编码特征**的输入生效（沿用第 1、6 步的门限写法），
否则会把正常查询串改坏；任何「解码后可能引入新编码形态」的步骤之后，
必须重跑一次对应的 overlong/URL 解码环节。

### 频次包装：由表单参数生成第二类编译目标

`applyRuleFrequencyLimit`（`build.go:955-985`）是快照期唯一会**改写 kind** 的步骤：
规则的 `window_seconds` 与 `request_count` 同时大于 0 时，把已解析的 `{kind,arg}`
包装成 `{"op":"cc_rate",...}` 复合条件，kind 从具体匹配器变成 `compound`。
这条路径有三个隐含约束，扩展时必须保持：

- 已是 `compound` 的规则**不叠加包装**，避免 `cc_rate` 嵌套 `cc_rate`（:956）；
- 包装发生在快照期，因此引擎期的 `knownPrefixes` 只需认 `compound`，不必认新语法；
- `cc_rate` 的共享状态挂在 `ccRateStates` 全局 `sync.Map` 上，键为
  `md5(child+window+threshold+duration_seconds)`（`matcher.go:1858-1875`），
  **不随快照 revision 清理**；改阈值会产生新状态，旧状态里的计数会继续驻留到自然过期。

`cc_rate` 与 `if/if_else` 的构建分支位于 `buildCompound`（`matcher.go:1898-1917`），
参数不合法（`len(children)!=1`、`window<=0`、`threshold<=0`）一律回落 `neverMatcher`，
与 `validateCompoundNode` 的错误串口径一一对应（`validate.go:76-92`）。
新增复合算子时，这两处必须同步：校验侧不加 `case`，任何未知 `op` 都会被
`validateCompoundNode` 的 `default` 判为「不支持的操作符」（`validate.go:99-101`），
这与简单 kind 的「无 default、无条件通过」恰好相反。

### 编译产物元数据与缓存判据

编译结果的每条都带三份派生元数据，全部由编译器生成、供日志与归因使用：

| 字段 | 生成方式 | 位置 | 说明 |
|------|----------|------|------|
| `ruleIDStr` | `"rule:" + phase + ":" + kind` | `compiler.go:67` | 事件归因用，不含 arg，避免把用户输入写进 ID |
| `matchDesc` | `kind + ":" + arg`，`compound` 且 arg 超 60 字符时截为 `compound:{...}` | `compiler.go:68,80-85` | 展示用，防超长 JSON 刷屏 |
| `runtimeAction` | `normalizeConfiguredAction(string(action))` | `compiler.go:66`；实现 `phases.go:1301-1310` | `log→observe`，非法值→`intercept` |

`normalizeConfiguredAction` 是动作侧唯一的归一化点：非法动作**不会**降级成 observe，
而是升级为 `intercept`（fail-closed 取向），扩展动作时如果新增别名，必须同时改
`action.Normalize`（`action.go:28-44`）与此处，否则别名会在编译期被当成非法值。

包外手工构造的 `Compiled`（如单测、`TestRule` 路径）可能缺元数据，
由 `ensureCompiledMetadata`（`compiler.go:87-115`）在需要时做写时复制补齐；
`hit()` 里还有一份同构兜底（`phases.go:1312-1324`）。扩展时若新增元数据字段，
这三处（生成、补齐、兜底）都要加，缺一处就会出现「同一条规则在不同路径下归因串不同」。

缓存侧的判据决定了「改编译器后什么时候生效」：

| 缓存 | 键 | 失效判据 | 位置 |
|------|----|----------|------|
| 规则编译缓存 | `{siteID, policyID}` | 快照 `revision` 变化即整表重建 | `engine.go:34-37,387-430` |
| 阶段链缓存 | `{policyID, siteID, antiReplayEnabled}` | revision + `prot` 指针 + `lua` 指针 + `luaRevision` + `deps` 指针，四判据全等才复用 | `engine.go:60-64,455-463` |

两者都是 `atomic.Pointer` 无锁读 + 写时复制（`compiledWriteMu` / `phasesWriteMu`），
没有 LRU 也没有容量上限，容量预分配只发生在阶段链（`make([]pipeline.Phase, 0, 11)`，
`engine.go:467`）。因此编译器改动**不需要**考虑缓存击穿，但需要考虑
「同一 revision 下缓存永不重编译」——灰度时只能靠改配置推 revision。

## 性能考虑

- 编译代价的分布：单条规则的开销主要来自 `regexp.Compile`。`cachedCompile` 把同一 pattern
  的重复编译降为一次（`matcher.go:1785-1808`），但缓存无淘汰，
  规模上界等于历史上出现过的不同正则数量；若扩展中出现「arg 内嵌时间戳/随机值」的 kind，
  会让这张表无界增长，这类 kind 必须在归一化阶段把可变部分剥离。
- `cc_rate` 状态表同理无淘汰（`matcher.go:45`），且键含 child 条件的完整 JSON，
  频繁改阈值会让表按变更次数增长。
- 排序只在编译期做一次（`Priority` 升序、`ID` 升序，`compiler.go:71-76`），
  阶段执行按该顺序线性扫描并在命中时短路（`phases.go:112-134`），
  因此把高命中率规则放在小 `Priority` 上，收益直接体现在每请求的比较次数上。
- `ensureCompiledMetadata` 只在确实缺元数据时才复制切片（`compiler.go:91-102`），
  扩展字段时不要破坏这个「先扫描再复制」的判定，否则每次请求都会产生一次全量复制。
- `matchDesc` 对 `compound` 的 60 字符截断（`compiler.go:81-84`）是日志体积的主要防线，
  新增 kind 若 arg 可能很长（例如内嵌 base64），要同样在 `compiledMatchDesc` 里加规则。

## 结论

编译器扩展的本质是三件事：**让名字被认出来（两处 kind 白名单）、让参数被约束住
（`validateSimplePattern` 的显式 `case`）、让取数被准备好（`ruleNeedsDerivedHeaders`）**。
其中任何一环缺失都不会报错，只会让规则静默恒假，这与编译器「双重 fail-closed」的设计取向
直接相关——它优先保证不误伤流量，代价是把可观测性压力转给了扩展者。

本篇刻意没有重写匹配器族与阶段链的内容：接口口径见 [匹配器开发](匹配器开发.md)，
阶段注册与短路语义见 [执行阶段系统](执行阶段系统.md)，
端到端选型见 [规则引擎扩展](规则引擎扩展.md)。
下一步值得做的改进（未实施，仅登记）：为 `knownPrefixes` 与 `buildMatcher` 分支
加一个全局表驱动一致性断言，把当前靠人维持的隐式不变量变成测试约束。
