## 简介
本文件是「规则引擎扩展」主题目录的总览，负责三件事：给出规则引擎全部可扩展面的选型地图、明确每条扩展路线需要登记的位置、把与引擎侧文档的分工讲清楚。

面向的扩展类型只有四条主线，超出这四条的需求不属于规则引擎：

| 扩展意图 | 落点 | 详解文档 |
|---|---|---|
| 让引擎多做一个检测步骤 | 新增 `pipeline.Phase` 并在引擎注册 | [执行阶段系统](执行阶段系统.md) |
| 让规则 DSL 多一种条件 | 新增 `Matcher` 类型 + kind 登记 | [匹配器开发](匹配器开发.md) |
| 让规则多带一个参数或动作 | 扩 `Compiled` 字段与动作映射 | [规则编译器扩展](规则编译器扩展.md)、[动作集成](动作集成.md) |
| 不改编码、用脚本表达策略 | Lua / JS 插件 | [Lua 策略插件](../Lua%20策略插件.md) |

四条主线共享同一条实测事实链，任何一条写错都会导致「改了不生效」：阶段链是 **11 阶段**（不是旧文档的 9 阶段）；`Matcher` 只有 `Match(MatchCtx) bool` 一个方法（**不存在 5 参数形式**）；兜底匹配器只有 `neverMatcher`（**`alwaysMatcher` 不存在**）；kind 白名单存在**两处**且不互通；写操作只有 POST。

## 架构总览
规则引擎的扩展面在一条请求生命周期上的位置如下：管理期决定「规则能不能存」，快照期决定「规则能不能进运行时」，编译期决定「规则会不会命中」，编排期决定「哪个阶段来跑它」。

| 期 | 触发 | 关键函数 | 扩展落点 |
|---|---|---|---|
| 管理期 | POST 创建/更新规则 | `admin/rule.CreateRule` `rule.go:98` | 模板、校验、kind 提示 |
| 校验期 | 同上 | `rules.ValidatePattern` `validate.go:28` | 参数校验分支 |
| 快照期 | `BumpRevision` → 重载 | `snapshot.compileRules` `build.go:920` | **第二份 kind 白名单** |
| 编译期 | 站点首次命中或代次变化 | `rules.Compile` `compiler.go:40`、`convertAndCompile` `engine.go:625` | `Compiled` 字段与元数据 |
| 编排期 | 同上 | `getOrBuildPhases` `engine.go:441` | 阶段注册与跳过白名单 |
| 执行期 | 每请求 | `pipeline.Run` `pipeline.go:517` | 终态判定与改写写回 |
| 链外 | 每请求 | `applyPostLuaDecision` `engine.go:369-371` | Lua post 覆盖判定 |

## 详细组件分析

### 扩展路线选型
先判断需求属于哪条路线，再动代码。判据只看一件事：**是否需要引擎在请求路径上多做一次判定**。

| 需求表述 | 路线 | 是否要重载快照 | 是否改 Go |
|---|---|:--:|:--:|
| 「按某个新字段拦截」且该字段已在 `MatchCtx` | 新增 kind + 匹配器 | 是 | 是（两处白名单） |
| 「按某个新字段拦截」且字段不在 `MatchCtx` | 先扩 `MatchCtx`，再走上一行 | 是 | 是 |
| 「满足条件时打标签/改写请求/自定义响应」 | Lua `pre` 或 JS 脚本 | 视配置 | 否 |
| 「内置判定之后对特定误报放行」 | Lua `post`（链外） | 否 | 否 |
| 「加一种需要跨请求计数的检测」 | 状态型匹配器（参照 `ccRateMatcher`） | 是 | 是 |
| 「加一类与规则无关的检测（如协议一致性）」 | 新增 `Phase` | 是 | 是（三处登记） |
| 「规则要多带一个参数（如新的响应控制）」 | 扩 `store.Rule` + `Compiled` | 是 | 是 |
| 「只要换动作展示或响应码」 | 复用既有 `action.Type` | 否 | 否 |

四条路线的取舍理由：`MatchCtx` 只有 16 个字段，凡是它已携带的信息用 kind 表达成本最低（一个 struct + 一个 case）；不在其中的信息（如响应内容、上游状态）不要硬塞进管道，改用 Lua post 或 JS response 脚本；需要外部 IO 或持久状态的检测才升级为独立阶段，因为它必须拿到依赖注入位。

### 两处 kind 白名单与静默丢弃
本仓库最需要记住的扩展陷阱。两份前缀表串联使用，第二份只有 30 项，导致 27 个 kind 的**裸 DSL 写法无法生效**。

| 侧 | 函数 | 位置 | 规模 | 是否 import rules |
|---|---|---|:--:|:--:|
| 引擎 | `rules.ParsePattern` | `compiler.go:119-170` | 57 | — |
| 快照 | `snapshot.ParsePattern` | `build.go:1197-1222` | 30 | 否 |

| 后果 | 表现 | 规避 |
|---|---|---|
| 裸 DSL 丢弃 | `compileRules` 见 `kind==""` 直接 `continue`，规则不进快照 | 新 kind 同时登记两处 |
| 复合包装可绕开 | `build.go:1201-1203` 对首字符 `{` 无条件返回 `compound`，叶子随后由 `buildCompound` 交回 `buildMatcher` | 只作为临时验证，不作长期方案 |
| 校验接口验不出 | `/rules/validate`、`/rules/test` 都只走引擎侧 | 必须走「建规则 → 重载 → 观察」全流程 |

## 性能考虑
- 规则侧成本在编译期一次性付清：`Compile` 构造 matcher 并按 `Priority`、`ID` 排序，运行期只做遍历与匹配；因此新增 kind 的正则编译成本落在快照重载，而不是每请求。
- 阶段链与规则各有缓存：规则按 `{siteID,policyID}`（`engine.go:34-37`），阶段链按 `{policyID,siteID,antiReplayEnabled}` 加 4 项判据（`engine.go:446-461`）。扩展时新增运行时依赖必须走 `updatePhaseDeps`，否则缓存会复用旧链。
- 匹配器成本排序（从低到高）：`strings` 比较 < CIDR 包含 < 缓存正则 < 通配符 < 需要派生串的 kind < 状态型（加锁） < 依赖外部能力的阶段（GeoIP、OWASP 扫描）。
- 每请求一次派生：ALPN/密码套件/头顺序串通过 `Derived*` 闭包缓存在 `RequestCtx` 上，跨阶段复用（`pipeline.go:232-257`）。新阶段需要同类值时复用该模式，不要重算。
- 对象池约束：`RequestCtx` 来自 `sync.Pool`，池容量上限见 `pool.go:12-17`。扩展上下文时同步 `ReleaseCtx`，否则会跨请求脏读并驻留大 map。
- 挑战类动作会跑完整条链：`pipeline.Run` 对挑战只记 pending、不中断（`pipeline.go:529-538`）。若把新阶段排在前段并返回挑战，后面所有检测仍会执行。

## 结论
规则引擎的可扩展性集中在四个真实接入点上：`Phase`（阶段）、`Matcher` + 两处 kind 白名单（条件）、`Compiled`/`store.Rule`（参数）、`action.Type`（结果），外加 Lua/JS 两条不改代码的旁路。总览的价值在于给出选型地图与登记清单，具体实现步骤分别由 [执行阶段系统](执行阶段系统.md)、[匹配器开发](匹配器开发.md)、[规则编译器扩展](规则编译器扩展.md)、[动作集成](动作集成.md) 承载。

本次迭代成果：订正阶段链为实测 11 阶段；按 `Match(MatchCtx)` 重画接口关系并删除不存在的 `alwaysMatcher` 与 5 参数签名；清除已废弃路径（`admin/handler_rule.go`、`store/models.go`、`waf/eval.go`、`frontend/components`）；补齐模块清单表、代码上下文表、扩展点总表、路线选型表、流程步骤表、依赖矩阵表与 12 行排查表；明确持久化规则阶段只有 3 个可用、写操作只有 POST。

原则落点：KISS——四条路线各自只需一个接入点；YAGNI——不为「未来可能的规则插件框架」抽象，脚本需求直接走 Lua/JS；DRY——把三处已知重复（kind 表、改写计划结构、保留头名单）显式列出而非假装不存在；SOLID——`LuaPluginEvaluator` 与 `jsplugin.Executor` 都是消费方定义的最小接口，依赖倒置成立。

遇到的问题：原文档多处把「ACL allow 短路」「Evaluate/EvaluateWithBot 位于 eval.go」「前端存在 `RULE_KINDS`」当作事实。处理方式是逐条回到代码验证后改写；`RULE_KINDS` 实际不存在，前端 kind 是散落在 `translateRow`/`backendToRow` 的 36 处字面量。下一步建议：让 `snapshot` 复用 `rules.knownPrefixes` 以消除 27 项差集，这属于代码改动，需另轮处理。
