## 简介
本文件面向「出站安全控制」，说明 WAF 作为反向代理向上游发起请求时实际施加的约束，以及**没有**施加的约束。覆盖：
- 上游目标地址的写入侧校验：协议白名单、authority 合法性、`upstream_host` 模板校验
- 协议别名归一：RPC 前缀到传输 scheme 的单一实现点
- 出站请求净化：非法头名/头值丢弃、安全相关头单列计数、裸 `%` 转义
- 转发身份头重建：先删客户端自带值，再写可信值
- 连接层：按 TLS 配置分池的 `http.Transport`、最小 TLS 版本、mTLS 客户端证书
- SSRF 相关能力的真实覆盖面与未覆盖情形

关于 SSRF 必须先说清边界：本仓库的出站目标是**管理面配置的上游地址**，不是客户端可任意指定的 URL。因此风险模型与「用户可控 URL 抓取器」不同。已实现的校验集中在协议与语法层；**内网/链路本地/云元数据地址不拦截、重定向逐跳不复校验、DNS 解析结果不与地址集合比对**，这三项在当前代码中没有对应实现，本文逐项标注「当前未覆盖」并给出证据位置。

## 核心组件
- **上游地址校验器**：`ValidateSiteUpstreamURLs` 对每条上游做 `url.Parse` + 协议白名单；`ValidateSiteUpstreamHost` 对 Host 覆写值做模板或字面校验
- **协议别名归一器**：`schemealias` 提供映射表与两个入口（`Scheme`、`AliasForURL`），`NormalizeURLPrefix` 是跨包唯一切换点
- **请求净化器**：`sanitizeUpstreamHeaders` 就地删除无法通过 `net/http` 出站校验的头，并对安全相关头单列计数
- **路径转义器**：`sanitizeRawPercentEscapes` 把裸 `%` 改写为 `%25`
- **转发身份重建器**：`RebuildOutboundForwardingHeaders` + `ApplyOutboundForwarding`
- **连接池与 TLS 装配**：`transportKey` 分池、`ResolveUpstreamBase` 分派 h2c/h3/别名/常规四种传输
- **观测面**：`UpstreamRequestGuardSnapshot` 四计数、`logUpstreamRequestError` 上游错误日志

## 详细组件分析

### 中间件链：出站请求构建顺序
`buildUpstreamRequest` 是单函数流水线，步骤顺序即安全语义顺序，任何一步都不改写前一步的结论。

| 序 | 步骤 | 实现行号 | 安全作用 | 失败行为 |
|:--:|------|----------|----------|----------|
| 1 | 拼 URL：base + 原始 path + query | `proxy.go:523-558` | 保留原始 path，不做二次解码 | path 空时补 `/` |
| 2 | 裸 `%` 转义 | `upstream_request_guard.go:157-173`，调用点 `proxy.go:532` | 阻断解析器差异型走私 | 无需转义时返回 nil |
| 3 | 方法归一 | `proxy.go:567-604` | 常量串复用，减少分配 | 未知方法原样透传 |
| 4 | 请求创建 | `proxy.go:648-651` | 绑定 context 取消 | `error` 上抛 |
| 5 | 头复制 | `proxy.go:663-677` | 过滤 Hop-by-Hop 与 Connection 令牌 | 命中即跳过 |
| 6 | TE 白名单 | `proxy.go:679-681`、`proxy.go:765` | 只放行可转发的 TE 值 | 置空即不写 |
| 7 | 请求体解码/降级 | `proxy.go:683-743` | 压缩炸弹超限降级为原始字节转发 | 记事件，不拒绝 |
| 8 | Trailer 同步 | `proxy.go:745-758` | 保留分块尾语义 | 无尾则跳过 |
| 9 | 身份头重建 | `outbound.go:74-81`，调用点 `proxy.go:760` | 客户端伪造值先删后写 | 值为空则不写 |
| 10 | 头净化 | `upstream_request_guard.go:58-122`，调用点 `proxy.go:761` | 删除 net/http 会拒绝的头 | 删头并计数 |

关键顺序约束是 **9 在 10 之前**：可信身份头写入后仍会被净化复校一次，若其本身含非法字节也会被删除并计入 `DroppedSecurityHeaderNames`（`upstream_request_guard.go:89-91`）。

### 净化器观测面
`UpstreamRequestGuardSnapshot` 暴露四个累计计数（`upstream_request_guard.go:44-51`），与结构体字段一一对应（`upstream_request_guard.go:26-37`）。

| 计数字段 | 含义 | 递增位置 | 是否落日志 |
|----------|------|----------|:----------:|
| `DroppedHeaderNames` | 非法头名个数（按头字段计） | `upstream_request_guard.go:99` | DEBUG 抽样 |
| `DroppedHeaderValues` | 非法头值个数 | `upstream_request_guard.go:100` | DEBUG 抽样 |
| `SanitizedPaths` | 做过裸 `%` 转义的请求个数 | `upstream_request_guard.go:162` | 否 |
| `DroppedSecurityHeaderNames` | 安全相关头被整体丢弃个数 | `upstream_request_guard.go:103` | WARN 抽样 |

安全相关头名单在 `isSecurityRelevantOutboundHeader`（`upstream_request_guard.go:130-144`）：`Authorization`、`Cookie`、`Proxy-Authorization`、`X-Forwarded-For`、`X-Forwarded-Host`、`X-Forwarded-Proto`、`X-Real-Ip`、`Client-Ip`、`Forwarded`。这类丢弃不改变请求成败，客户端与上游都看不到异常，因此单独升 WARN，并沿用上游错误的抽样规则（首见 + 每 1024 条，`upstream_request_guard.go:117-121`、`proxy.go:434`）。日志只记截断后的**头名**样本，最多 4 个、每个 64 字节，完整取值一律不落日志（`upstream_request_guard.go:20-23`、`upstream_request_guard.go:66-72`、`upstream_request_guard.go:146-155`）。

### SSRF 防护的真实覆盖面
下表逐项给出实现位置与结论。凡写「当前未覆盖」的都是全仓检索后确认没有对应实现的能力，不是「未统计」。

| 校验项 | 覆盖状态 | 证据与行为 |
|--------|:--------:|------------|
| 协议白名单（写入侧） | ✓ 已实现 | `site_upstreams.go:37-50`：仅 `http`/`https`/`h2c`/`h3` 与 `tls`/`grpc`/`grpcs`/`grpc+tls`/`grpc+https`；其余落 `default` 返回 `errSiteUpstreamsUnsupportedScheme`（`site_upstreams.go:18`、`site_upstreams.go:48-49`）。`file`、`gopher`、`dict` 等**无法写入配置** |
| scheme 语法合法性 | ✓ 已实现 | `url.Parse` 失败或 scheme 为空即拒绝（`site_upstreams.go:33-36`）；标准 scheme 必须带非空 Host（`site_upstreams.go:41-43`） |
| RPC 别名 authority 兜底 | ✓ 已实现 | `url.Parse` 认不出 `tls://` 的 Host，改由 `siteUpstreamRPCURLHasAuthority` 判定（`site_upstreams.go:44-47`、`site_upstreams.go:85-96`），`grpc:///path` 被拒 |
| 上游地址非空 | ✓ 已实现 | 空列表返回 `errSiteUpstreamsRequired`（`site_upstreams.go:29-31`） |
| Host 覆写值合法性 | ✓ 已实现 | 模板形态经 `text/template` + `missingkey=error` 解析（`site_upstreams.go:102-106`）；字面形态经 `NormalizeHostHeaderValue` 做 punycode 与 `ValidHostHeader`（`site_upstreams.go:108`、`host.go:19-25`） |
| 协议别名归一 | ✓ 已实现 | 快照构建期展开（`build.go:836` 调 `schemealias.NormalizeURLPrefix`，映射表 `schemealias.go:7-13`）；运行期分派 `transport.go:800-844` |
| 客户端可控目标地址 | ✓ 不构成风险 | `base` 只来自 `SiteRuntime.UpstreamURLs`（`snapshot.go:48`），客户端只贡献 path/query（`proxy.go:523-558`），authority 段不接受客户端输入 |

### 协议别名与传输分派
`schemealias` 是全仓唯一的别名实现，映射表固定五条（`schemealias.go:7-13`）：`tls`/`grpcs`/`grpc+tls`/`grpc+https` → `https`，`grpc` → `h2c`。

- `Scheme` 折叠大小写后查表，入参不带 `://`（`schemealias.go:18-24`）
- `IsRPCScheme` 允许带或不带 `://` 两种形态（`schemealias.go:28-32`）
- `AliasForURL` 按「完整别名 + ://」做前缀比较，避免 `grpcs` 被 `grpc` 抢先匹配（`schemealias.go:38-44`）
- `NormalizeURLPrefix` 未命中时原样返回，保证旧四前缀行为不变（`schemealias.go:51-56`）

运行期分派 `ResolveUpstreamBase` 的四条分支（`transport.go:800-844`）：

| 输入前缀 | 归一结果 | 使用的 transport | 判定行号 |
|----------|----------|------------------|----------|
| `h2c://` | `http://` + 余串 | h2c 单例 | `transport.go:802-810` |
| `h3://` | `https://` + 余串 | 按上游主机分池的 h3 | `transport.go:811-823` |
| RPC 别名 | 命中 `h2c` 或 `https` | 对应池 | `transport.go:824-838` |
| 其余 | 原串 | 按 `isHTTPS` 取共享池 | `transport.go:839-843` |

注释明确指出别名分支在量产数据面上不可达，因为快照构建期已展开（`transport.go:825`）；它保留的是语义完整性。`isHTTPSUpstreamBase` 同样对别名做前缀折叠（`transport.go:208-229`）。

探活侧另有一套等价归一：`parseUpstreamURL` 先试标准解析、失败后按别名重试（`health.go:136-156`），`protocolPreference` 按 `h3 > h2c > https > 其余` 排序（`health.go:381-402`），`normalizeUpstreamBase` 只在 scheme 或大小写需要变化时重写串（`health.go:869-920`），`isValidUpstreamScheme` 只做 RFC 3986 字符集检查而**不是白名单**（`health.go:922-935`）。

### 请求体与采样解码边界
出站路径存在两套刻意分开的解码：转发要完整明文，采样只要够填检测窗的前缀（`request_inspection.go:8-34`）。三态语义在 `RequestBodyInspectionSample` 中显式建模（`request_inspection.go:48-54`）：

## 性能考虑
- 连接复用：池键只包含 TLS 相关维度，非 HTTPS 上游共用一个键（`transport.go:138-145`），避免同 scheme 反复建池
- 会话恢复：HTTPS 上游独享 `ClientSessionCache`，LRU 容量与单主机空闲数对齐（`transport.go:187`）
- URL 拼装：三段长度已知，一次 `make` + `append`，避免 `strings.Builder.Grow` 的超额预留（`proxy.go:542-557`）
- 别名前缀比较按字节折叠大小写，未命中不分配（`transport.go:208-229`）
- 净化器就地修改头 map，不复制整个头集合（`upstream_request_guard.go:58-95`）
- 丢弃计数走 `atomic.Uint64`，无锁（`upstream_request_guard.go:13-18`）
- 客户端整体超时 30s 与响应头超时 30s 同量级，避免长尾请求占住连接池（`proxy.go:1037`、`transport.go:177`）

## 故障排查指南
- 症状：保存站点提示 `upstream_urls supports only http, https, h2c, h3, tls, grpc, grpcs, grpc+tls, grpc+https`
  - 原因：scheme 不在白名单内（`site_upstreams.go:18`、`site_upstreams.go:48-49`）
  - 排查：确认是否误写 `tcp://`、`unix://`、`file://`
  - 方案：改用受支持前缀，或用监听层做协议适配
- 症状：提示 `upstream_urls contains invalid URL`
  - 原因：标准 scheme 无 Host，或 RPC 别名去前缀后 authority 为空（`site_upstreams.go:41-46`、`site_upstreams.go:85-96`）
  - 方案：补全 `scheme://host:port`
- 症状：上游看不到客户端真实 IP
  - 排查：确认站点 XFF 模式与可信网段（`clientip.go:17-35`），以及解析结果非 `nil`（`clientip.go:19-21`）
  - 说明：`X-Forwarded-For` 只写单个解析结果，不透传整条链（`outbound.go:47-49`）
- 症状：上游收到被改写的请求头
  - 排查：查 `UpstreamRequestGuardSnapshot` 的四个计数（`upstream_request_guard.go:44-51`），并开 DEBUG 日志看抽样头名（`upstream_request_guard.go:106-113`）
  - 说明：安全相关头被丢弃会额外出 WARN，且日志只含截断头名（`upstream_request_guard.go:117-121`、`upstream_request_guard.go:146-155`）
- 症状：上游 TLS 握手失败
  - 排查：确认 `upstream_tls_server_name` 与上游证书 CN/SAN 匹配（`transport.go:181`），注意主路径下限是 TLS 1.2（`transport.go:183`），探活与 h3 侧下限是 TLS 1.0（`internal/upstream/transport.go:37`）
  - 方案：`upstream_tls_skip_verify` 仅限测试环境（`site.go:98`）；生产改用可信证书或 mTLS
- 症状：连接频繁重建
  - 排查：确认不同站点的 SNI/跳过校验/证书指纹是否一致，三者任一不同即分池（`transport.go:138-145`）
- 症状：担心 WAF 被当作内网跳板
  - 结论：上游目标只能由管理面配置且协议受限，但内网地址、重定向逐跳、DNS 解析结果均无校验（见「SSRF 防护的真实覆盖面」）
  - 方案：以管理面权限收敛为边界，上游网段用网络策略兜底，避免把 WAF 部署在可直达云元数据的位置

## 结论
本次逐文件核对得到清晰结论：出站安全控制的**实现重心在请求净化与连接治理**，而不是目标地址筛选。

已实现且可靠：
- 写入侧协议白名单与 authority 校验（`site_upstreams.go:24-96`），非法协议无法进入配置
- Host 覆写的模板与字面双形态校验（`site_upstreams.go:97-112`）
- 出站头两级复校：可信重建 + `httpguts` 净化（`outbound.go:36-56`、`upstream_request_guard.go:58-122`），并有四个计数与抽样日志支撑可观测性
- 裸 `%` 转义与压缩体降级放行，避免解析器差异与解压放大（`upstream_request_guard.go:157-173`、`proxy.go:683-743`）
- 按 TLS 语义分池、mTLS 指纹入键、会话缓存复用（`transport.go:137-206`）

当前未覆盖（不构成缺陷断言，属能力边界）：
- 内网、回环、链路本地与云元数据地址的出站拦截
- 重定向逐跳的再校验，沿用 Go 默认最多 10 次跟随
- DNS 解析结果与地址集合的比对，因此无 DNS rebinding 防护

建议：把「谁可以改上游配置」当作主要信任边界管理；若需要把 WAF 用于多租户自配上游的场景，应先补齐地址段黑名单与解析后校验，再放开写入。

### 能力与限制
- 上游地址只接受管理面配置，客户端无法影响 authority 段，这与「用户可控 URL 抓取器」的风险模型不同
- `DisableCompression` 为真（`transport.go:170`），出站不做透明解压，响应解压由 `internal/proxy/compression.go` 独立处理
- 重定向跟随能力存在但不可配置：无 `CheckRedirect` 注入点（`transport.go:246`、`transport.go:265`、`transport.go:984`、`transport.go:1001`、`transport.go:1013`）
- 净化器只删不改：不存在「改写非法头值后放行」的路径（`upstream_request_guard.go:78-94`）
- 头名单截断策略固定为 64 字节 × 最多 4 个样本（`upstream_request_guard.go:20-23`）
- `internal/upstream` 的别名表与 `internal/pkg/schemealias` 语义一致但分属两处调用面（`health.go:381-402`），修改时须同步
