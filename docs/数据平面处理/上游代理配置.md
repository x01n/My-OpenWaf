## 简介
本文件面向运维与开发人员，系统性阐述本项目的上游代理配置与实现机制，重点覆盖以下方面：
- 上游选择：轮询起点 + 健康位与平均延迟择优（`internal/upstream/health.go`）
- 上游服务器配置：URL 列表形态、协议白名单、`upstream_host` 模板
- 传输层：三类 transport 池的参数差异、超时与 HTTP/2/HTTP/3 分流
- 代理头部处理：入站 XFF 解析与出站 `X-Forwarded-*` 重建
- 错误处理：探活摘除、失败回写与 502 语义
- 可观测与调优：池统计、上游状态接口与参数建议

## 核心组件
- 上游状态池：以规范化 URL 为键维护 `Healthy`、`FailCount`、`LastFailureKind`、`AverageLatencyMs` 等状态位（`health.go:40-56`）。
- 择优器：`Pick` 先用调用方给的原子计数取起点，再在「未被判死」的集合内按平均延迟择优，全死则回落起点（`health.go:219-240`、`health.go:404-458`）。
- 探活循环：`StartWithResult` 以 10 秒间隔探测全部上游，探测超时 2 秒（`server.go:370-374`、`health.go:609`）。
- 传输池：按 `transportKey` 缓存 transport，并按 scheme 分流到 h2c 单例或 h3 池（`transport.go:71-92`、`transport.go:800-856`）。
- 转发器：构造上游请求、剥离逐跳头、按 30 秒 client 超时回源并回写响应（`proxy.go:1006-1054`）。
- 安全工具：入站按 XFF 模式解析真实 IP，出站重建 `X-Forwarded-For/Host/Proto`（`clientip.go:16`、`outbound.go:74`）。
- 观测接口：`/upstreams/status` 输出健康位（`router.go:245`），运行时接口输出池统计（`runtime.go:157-198`）。

## 详细组件分析

### 负载均衡策略与择优算法
- 起点：`Handler` 用 `atomic.Uint32` 递增取模生成轮询起点（`handler.go:1101`、`handler_support.go:150`）。
- 择优：`pickFastestKnownAvailable` 跳过 `Healthy=false` 的条目；若全部已知条目都有延迟样本，则取平均延迟最小者，否则取第一个可用（`health.go:421-458`）。
- 协议偏好：`PickByProtocolPreference` 按 h3 > h2c > https > 其它分组轮询，pool 为 nil 时走无池分支（`health.go:268-281`）。
- 兜底：`Pick` 在无任何可用条目时仍返回起点地址，由请求失败路径写 502 并 `Mark` 失败（`health.go:219-240`、`handler.go:1215`）。
- 边界：SSE 与 WebSocket 分支同样先经过 `Pick`，但 WebSocket 走 Raw TCP 拨号，不使用 transport 池。

### 传输层：三类 transport 池参数对照
连接池实现全部位于 `internal/proxy/transport/transport.go`，`internal/proxy/proxy.go` 不再持有 `transportPool` 与 `transportKey`。三类池的取值来自实测代码行，互不可混用：

| 参数 | 共享上游池 | h2c 明文 HTTP/2 单例 | 探活 transport |
|------|:---:|:---:|:---:|
| `MaxIdleConns` | 256（`transport.go:157`） | 512（`transport.go:872`） | 128（`health.go:667`） |
| `MaxIdleConnsPerHost` | 32（`transport.go:159`） | 128（`transport.go:873`） | 32（`health.go:668`） |
| `IdleConnTimeout` | 30s（`transport.go:161`） | 90s（`transport.go:874`） | 90s（`health.go:671`） |
| `MaxConnsPerHost` | 256（`transport.go:172`） | 未设 | 32（`health.go:669`） |
| 拨号超时 | 10s（`transport.go:110`） | 未设 | 等于探测超时（`health.go:663`） |
| `TLSHandshakeTimeout` | 10s（`transport.go:176`） | 未设 | 10s（`health.go:672`） |
| `ResponseHeaderTimeout` | 30s（`transport.go:177`） | 未设 | 未设 |
| 读/写缓冲 | 16 KiB（`transport.go:163-164`） | 默认 | 默认 |
| `ForceAttemptHTTP2` | 是（`transport.go:168`） | 是（`transport.go:875`） | 是（`health.go:674`） |
| `DisableCompression` | 是（`transport.go:170`） | 是（`transport.go:876`） | 是（`health.go:675`） |
| `ExpectContinueTimeout` | 1s（`transport.go:166`） | 未设 | 1s（`health.go:673`） |
| 客户端会话缓存 | LRU 32（`transport.go:187`） | 无 | 无 |
| `MinVersion` | TLS 1.2（`transport.go:183`） | 默认 | 默认 |
| 池化键 | `transportKey`（`transport.go:71`） | 单例（`transport.go:863`） | 每 client 一份 |

- 取值理由：256/32 比 Go 默认的 512/128 更省空闲连接内存，30 秒让峰值后的空闲连接更快释放（原为 90 秒）；`MaxConnsPerHost` 限制单上游并发，避免洪峰占满临时端口。
- client 侧：`*http.Transport` 走 `sharedClient`（整体超时固定 60 秒，`transport.go:246`）或 `sharedNoTimeoutClient`（超时 0，`transport.go:266`）；调用方传入的超时值只对 `*http3.Transport` 生效（`transport.go:967-1016`），因此 `proxy.go:1037` 的 30 秒在 HTTP/1 与 h2 路径上被 60 秒档覆盖，真正的响应头约束来自 `ResponseHeaderTimeout` 的 30 秒。
- 回收：`PruneInactiveUpstreamTransports` 按快照清理不再使用的键，`CloseIdleUpstreamTransports` 用于关停（`transport.go:1044-1136`）。

### 代理头部处理：X-Forwarded-For 与客户端 IP 传递
- 入站 IP 解析
  - 仅当 `xff_mode = trust_outer_waf_cidr_then_take_leftmost` **且**直连 IP 落在可信网段内时，才按 `client_ip_header_order` 依次取头；否则一律用直连 IP（`clientip.go:16-34`）。
  - 可用头为 `X-Forwarded-For`（取最左有效 IP）、`X-Real-IP`、`Forwarded`（`site.go:20-22`）。
  - 默认模式是 `strip_all_and_set_remote`，即不信任客户端自带的任何转发头（`site.go:92`）。
- 出站头部设置
  - `RebuildOutboundForwardingHeaders` 先删除客户端带来的 `Forwarded`/`X-Forwarded-For`/`X-Forwarded-Host`/`X-Forwarded-Proto`，再按解析结果重写（`outbound.go:36-57`）。
  - `X-Forwarded-Host` 只在 `preserve_original_host` 为真时写入；`upstream_host` 独立决定请求的 `Host` 头，二者不互相覆盖（`outbound.go:52`、`snapshot.go` 的 `ResolveOutboundHost`）。
  - `X-Forwarded-Proto` 由入站协商结果推导：内部 h3 标记 → `h3`，站点启用 TLS → `https`，否则取受信入站值。
- 逐跳头剥离：请求侧由 `RequestConnectionHeaderStripper` 处理 `Connection` 列出的扩展逐跳头，响应侧由 `IsHopByHop` 白名单处理（`proxy.go:2868-2956`、`proxy.go:2771-2863`）。

| 头 | 入站处理 | 出站处理 | 位置 |
|----|----------|----------|------|
| `X-Forwarded-For` | 条件解析为真实 IP | 重写为解析结果 | `clientip.go:16`、`outbound.go:48` |
| `X-Forwarded-Host` | 丢弃 | `preserve_original_host` 为真时写入 | `outbound.go:41`、`outbound.go:52` |
| `X-Forwarded-Proto` | 受信时用于判决 | 按入站协商重写 | `outbound.go:59`、`outbound.go:44` |
| `Forwarded` | 可作 IP 来源 | 一律丢弃后不重建 | `clientip.go:39`、`outbound.go:38` |
| `Connection` 列出的头 | 按 token 剥离 | 响应侧同样剥离 | `proxy.go:2936`、`proxy.go:981` |
| `Host` | 参与站点匹配 | 由 `upstream_host` 覆写 | `handler.go:136`、`snapshot.go` |

### 错误处理与故障转移
- 已有能力
  - 周期探活：`StartWithResult` 每 10 秒探测全部上游，探测超时 2 秒，结果写入 `State`（`server.go:370-374`、`health.go:587-608`）。

- 仍然存在的边界
  - 单请求不做多上游重试：一次 `Pick` 只发一次，失败即 502。
  - 全部上游判死时回落到起点地址继续尝试，避免整站不可用。
  - 探活状态不影响 WebSocket 的 Raw TCP 拨号结果判定，只影响被选中概率。

### 代理性能调优与监控最佳实践
- 连接与协议：HTTP/2 由 `ForceAttemptHTTP2` 自动协商；h2c 与 h3 需显式 scheme，参数各自独立，调共享池不会影响它们。
- 空闲与并发：`MaxIdleConnsPerHost` 32 与 `MaxConnsPerHost` 256 是一对权衡——前者控内存，后者控端口占用。
- 超时：响应头 30 秒是回源首字节的主约束；client 侧 60 秒档只在缓冲路径生效。
- 择优：上游规模大时保持探活开启，让 `AverageLatencyMs` 参与选择，比纯轮询更稳。
- 观测：`/upstreams/status` 看健康位与延迟；运行时接口看池规模；`/metrics` 看 `openwaf_upstream_*` 与 `openwaf_dataplane_*`。

## 性能考虑
- 连接复用：共享池 256/32/30 秒 + TLS 会话缓存 32，决定回源握手成本。
- 协议选择：h2 由 `ForceAttemptHTTP2` 尝试；h2c 与 h3 各用独立池，参数互不影响。
- 择优与探活：10 秒周期 + 2 秒超时，故障节点在下一轮前即被跳过。
- 超时分层：`ResponseHeaderTimeout` 30 秒约束首字节，client 60 秒只约束整体，SSE 走无超时。
- 并发上限：`MaxConnsPerHost` 256 保护本机临时端口，配合 `hertzH2CUpstreamGateCapacity` 128 限流 h2c 上游并发。

## 故障排查指南
- 无上游配置：`UpstreamURLs` 为空时直接 502，前端录入与后端校验（协议白名单）需同时通过。
- 协议被拒：非白名单 scheme 在保存阶段即报错，运行期不会出现未知协议上游（`site_upstreams.go:18`）。
- TLS 握手失败：核对 `upstream_tls_server_name`、`upstream_tls_skip_verify` 与客户端证书对；证书内容变化会使旧池键自然失效。
- 上游被判死：查 `/upstreams/status` 的 `Healthy`、`LastFailureKind`、`FailCount`，必要时看 `openwaf_upstream_unhealthy_total`。
- 首字节慢：区分是 `ResponseHeaderTimeout` 触发还是客户端网络问题；SSE 场景看是否走了 hijack 通道。
- XFF 异常：确认直连 IP 是否在可信网段，模式是否为 trust_outer；否则解析结果恒为直连 IP。
- 端口耗尽：`MaxConnsPerHost` 与上游并发是否匹配，必要时增加上游实例而非放宽上限。

## 结论
上游代理能力由三层协作构成：`upstream.Pool` 负责择优与探活，`proxy/transport` 负责连接复用与协议分流，`proxy` 负责请求与响应的头语义。健康检查与故障摘除已经内置（10 秒探活 + 状态位 + 延迟择优），单请求不重试是有意取舍——把重试交给上层与客户端语义更清晰。调参时应按池分别处理，共享池的 256/32/30 秒、h2c 的 512/128/90 秒与探活的 128/32/90 秒是三套互不影响的取值。
