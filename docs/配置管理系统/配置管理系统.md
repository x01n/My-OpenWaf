## 简介

My-OpenWaf 是单进程双平面应用，配置管理系统要回答三个问题：**配置存在哪里、什么时候生效、多个实例如何看到同一份配置**。

答案由四类载体构成，且必须区分清楚，否则很容易造出「第二配置源」：

| 载体 | 写入方式 | 生效时机 | 真相源地位 |
|------|----------|----------|------------|
| 环境变量（`MY_OPENWAF_*`） | 部署时注入 | 仅进程启动期 | **唯一引导源**，见 [README.md:311-347](file://README.md#L311-L347) |
| `system_settings` 键值表 | 管理 API 专用端点 | 多数经 reload 生效 | **业务配置唯一源** |
| 逐键覆盖表 `runtime_config_overrides` | `/api/v1/runtime-config/env-overrides` | 视键是否 `RestartRequired` | 环境变量的**运行时补丁**，不是新配置源 |
| 领域表（sites/rules/policies/certificates…） | 管理 API CRUD | reload 后进入快照 | 数据面配置的权威存储 |

**项目不解析 YAML 配置文件**。`internal/core/config.go:14-20` 等结构体上的 `yaml:` 标签只是字段命名口径与外部工具对接预留，运行期唯一的文件型输入是环境变量（`LoadConfigFromEnv`，config.go:334）。因此本文所有配置结构均以环境变量（`env`）与 `system_settings` 的 JSON 存储形态（`json`）表达。

本文档给出全链路的索引与边界；实现细节分述于五个子页面，架构视角的快照发布语义见 [docs/系统架构设计/快照机制.md](file://docs/系统架构设计/快照机制.md)。

## 架构总览

配置生效是一条单向链：**写入 → 递增代次 → 重建快照 → 原子替换 → 监听器协调 → 广播其他节点**。任何一步缺失都会造成「库里已改、面仍在旧值」。

```mermaid
sequenceDiagram
participant OP as "管理员/前端"
participant ADM as "admin 写端点"
participant DB as "主库"
participant SRV as "app.Run reload 链"
participant RT as "core.Runtime"
participant DP as "数据面"
participant RS as "Redis 频道"
OP->>ADM : POST 配置变更
ADM->>DB : 落库（sites / system_settings）
ADM->>SRV : 调用 reload 回调
SRV->>DB : BumpRevision（migrate.go:141）
SRV->>RT : ReloadSnapshotWithPrePublish
RT->>DB : currentRevision + snapshot.Build
RT->>RT : StoreIfNewer 原子替换
RT-->>SRV : 新快照可见
SRV->>DP : reconcileListeners 启停监听
SRV->>RS : PublishReload（pubsub.go:65）
SRV-->>OP : 200 成功
```

架构分层与各层约束：

| 层 | 承载 | 关键约束 |
|----|------|----------|
| 引导层 | 环境变量 → `Config` | 只在 `NewRuntime` 读一次，改环境变量必须重启 |
| 覆盖层 | `runtime_config_overrides` | 仅 `ScopeRuntime` 键可写；`RestartRequired` 键写后进库等重启 |
| 存储层 | `system_settings` + 领域表 | 每个键有唯一专用写入口（`protectedSettingKeys`） |
| 读模型层 | `Snapshot` | 构建后不可变；只经 `StoreIfNewer` 发布 |
| 编排层 | `applySnapshotReload`（server.go:868-889） | 快照换代才清响应缓存、重建监听 |
| 同步层 | Redis pub/sub | 只传事件，各节点自行重建快照 |

1. **ACME 配置确实调用 reload**，但 `acme_config` 不在 `snapshot.Build` 的读取集合内（build.go:102 的 `loadAllSettings` 结果只被 network/tls/protection/compression 系列消费），签发流程每次现读 `loadACMEConfig`（acme.go:192、285）。因此 reload 对 ACME 配置本身没有传递效果，只额外递增了一次代次。

## 性能考虑

- **读路径零锁**：数据面每次请求只做一次 `atomic.Pointer.Load`（snapshot.go:489），配置读放大为零。
- **代次缓存复用**：`cache.Layer` 按 `snapshot:<rev>` 缓存已构建快照（layer.go:44-62），多节点各自 reload 时同一代次只构建一次； ristretto 参数 `NumCounters 1e4 / MaxCost 1<<20 / BufferItems 64` 属快照层，不是规则层（layer.go:30-34）。
- **CAS 二次核对的代价**：`ReloadSnapshotWithPrePublish` 每轮最多读三次修订号（runtime.go:219、236、250、262），换来的是「不会用旧代次覆盖新代次」。
- **重建监听器是主要成本**：`reconcileListeners` 用指纹 tag 比较，仅对漂移的 bind 重启（server.go:771-778），避免全量重启。
- **引导类参数不可热调**：队列容量、解压上限、响应缓存容量均在启动期固化，压测调参必须重启，不要指望 reload。

## 结论

配置管理系统的最小可用模型是一句话：**环境变量决定进程长成什么样，`system_settings` + 领域表决定请求怎么被处理，快照是后两者的唯一读视图，reload 是两者之间唯一的桥**。

三条设计原则的落点：

- **KISS**：只有 4 类载体、1 条优先级链、1 个发布原语（`StoreIfNewer`），没有热更新框架。
- **YAGNI**：不提供回滚、不提供配置 diff、不提供第二写入口；`ScopeDelegated`/`protectedSettingKeys` 用「拒绝写」而不是「合并写」来守住单一真相源。
- **SRP/DRY**：校验口径只有一处（`configoverride` 的 `Parse*` 家族被端点提交与库里解析共用，resolve.go:130-141），依赖注入靠回调而不是让 `admin` 直接依赖 `core`。

已知弱点（不属本轮修复范围）：引导类参数无法热调；跨节点无一致性水位可读；`/log-config` 与 `/redis-config` 的成功响应不代表集群其他节点已完成热替换。

### 变更配置的标准操作

```bash
# 1. 读取当前三态（只读，operator 亦可）
curl -s -H "Authorization: Bearer {token}" \
  https://127.0.0.1:9443/api/v1/runtime-config/env-overrides

# 2. 写覆盖表（admin）；写后自动 reload
curl -s -X POST -H "Authorization: Bearer {token}" \
  -H "Content-Type: application/json" \
  -d '{"overrides":{"bot_threshold":90},"clear":["trace_enabled"]}' \
  https://127.0.0.1:9443/api/v1/runtime-config/env-overrides

# 3. 显式重载验收（admin）
curl -s -X POST -H "Authorization: Bearer {token}" \
  https://127.0.0.1:9443/api/v1/reload
```

`overrides` 的值是**裸 JSON 取值**（`map[string]json.RawMessage`），`{"value":..,"set":true}` 是库里的存储形态，不是请求形态（runtime_overrides.go:247-250、resolve.go:45-46）。未知键与 `Scope != runtime` 的键直接 400，不做静默忽略（runtime_overrides.go:283-305）。`{token}` 为占位，真实令牌不得出现在文档与脚本中。
