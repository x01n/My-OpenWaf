## 简介

本篇只讲快照的**配置层视角**：一份快照由哪些字段构成、每个字段是从哪张表或哪个设置键解析出来的、键是怎么拼的、DB 形态与快照形态之间如何映射、解析失败时走哪条分支。

同一个对象在三篇文档里各自负责一部分，本篇严格不复制另两篇的表格：

| 文档 | 视角 | 负责回答 | 本篇如何引用 |
|------|------|----------|--------------|
| [系统架构设计/快照机制](../系统架构设计/快照机制.md) | 架构 | 为什么快照是双平面唯一共享物、构建时机、发布牵动面 | 时机与副作用一律只给链接 |
| [WAF 引擎系统/引擎核心架构/快照系统](../WAF 引擎系统/引擎核心架构/快照系统.md) | 引擎消费 | 引擎如何读快照、两级缓存键与失效判据 | 消费路径只写「消费方」列 |
| 本篇 | 配置层 | 字段构成、解析来源、键设计、DB 映射 | — |

三个结论先行（均可逐行验证）：

1. `Build` 是配置生效的**唯一入口**，站点、监听、证书、规则、策略、访问控制、动态防护与全部保护设置都在这一个函数里读完后编译（`internal/snapshot/build.go:47-554`）。
2. 快照字段与 DB 形态不是一一对应：JSON blob 列要先被 `PeelJSONStringBlobs` 摘成字符串再入模型（`internal/admin/shared/json_bind.go:31-41`），三态指针列要在构建期折叠成终值（`build.go:707-770`）。
3. 快照对请求侧只读，可变性只存在于构建期；跨重载的可变状态不属于快照（限流窗口、连接池等）。

## 核心组件

- `Snapshot`：配置层的最终产物，`Revision` 之外的全部字段在 `Build` 返回后不再被写入（`snapshot.go:213-287`）。
- `SiteRuntime`：站点视角的配置终值集合，把「DB 列 + 全局默认 + 站点覆盖」折叠成一个只读结构（`snapshot.go:44-141`）。
- `Holder`：`atomic.Pointer[Snapshot]` 的极薄封装，只提供 `Store` / `StoreIfNewer` / `Load`（`snapshot.go:453-489`）。
- `Build`：读取 + 解析 + 编译 + 键注册四件事的执行者，错误分「致命返回」与「记入诊断继续」两档。
- `Layer`：进程内 Ristretto 快照缓存，键 `snapshot:<rev>`，写入前置校验 `sn.Revision == rev`（`layer.go:44-51`）。

### 构建顺序与失败分流

`Build` 的读取顺序本身就是依赖顺序：先取全局（策略、设置、证书字典），再逐站点折叠，最后统一注册键。分流规则只有一条判据——**是否会让整份配置失去意义**。

```mermaid
flowchart TD
Start(["Build(db, rev, keyBase)"]) --> LoadSites["sites(enabled=true)"]
LoadSites --> CheckPolicy{"默认策略恰好 1 个?"}
CheckPolicy --> |0 个或多个| Fatal["致命: 返回 error"]
CheckPolicy --> |是| LoadListeners["site_listeners 全量, 按 site_id,bind,id 排序"]
LoadListeners --> LoadCerts["certificates 全量"]
LoadCerts --> LoadRules["rules(enabled=true) 按 policy 分组排序"]
LoadRules --> CheckRulePolicy{"规则 policy_id 合法?"}
CheckRulePolicy --> |0 或不存在| Fatal
CheckRulePolicy --> |是| LoadSettings["system_settings 预加载成 map"]
LoadSettings --> ParseProt["protectionConfigFromMap"]
ParseProt --> ParseOK{"JSON 与 captcha_type 合法?"}
ParseOK --> |否| Fatal
ParseOK --> |是| LoadAppRules["application_route_rules(enabled=true) 按站点编译"]
LoadAppRules --> LoadPlugins["lua_plugins / js_plugins"]
LoadPlugins --> PerPlugin{"单脚本编译失败?"}
PerPlugin --> |是| Diag["记入 *Errors, 继续构建"]
PerPlugin --> |否| SiteLoop
Diag --> SiteLoop["逐站点折叠 SiteRuntime"]
SiteLoop --> NoUpstream{"upstream_urls 为空?"}
NoUpstream --> |是| Skip["continue: 跳过该站点"]
NoUpstream --> |否| BuildRT["编译规则 / 合并保护 / 解析 TLS"]
BuildRT --> KeyReg["registerSiteKeys"]
KeyReg --> Dup{"跨站点键冲突?"}
Dup --> |是| Fatal
Dup --> |否| Done["装配 Snapshot 并返回"]
Skip --> Done
```

### 键设计与唯一性约束

站点键与 SNI 键都是「bind 前缀 + `\x00` + 归一化主机名」的二段结构，因此不同监听地址下同名站点天然不冲突；`SiteMapKey` 是对外构造入口，`siteMapKeyNorm` 用于 host 已归一化的内部路径（`snapshot.go:289-300`）。

| 键 | 构造:行 | 组成 | 冲突处理:行 | 查找级数 |
|----|---------|------|-------------|:--------:|
| 站点键 | snapshot.go:293 | `bind` + `\x00` + 小写去空白 host | build.go:795-800 直接报错 | 3 |
| 多主机注册 | build.go:789、812 | `sites.host` 逗号切分逐个入键 | 同站点重复键 `continue` | — |
| SNI 证书键 | snapshot.go:298 | 固定前缀 `sni:` + `bind` + `\x00` + 归一化 SNI | 逐监听器覆盖 | 3 |
| catch-all 键 | build.go:789（`sites.host` 写成 `*`） | `bind` + `\x00` + `*` | 同站点键规则 | — |
| 快照缓存键 | layer.go:48、55 | `snapshot:<rev>` | 仅同 `Revision` 允许写入 | 1 |

查找优先级为「精确 → `*.` 单级父域 → catch-all `*`」，至多三级（`MatchSitePtr` 在 `snapshot.go:373-400`）。两条实测约束：

- **IP 型 host 跳过通配**：`isIPAddress` 为真时不做 `*.` 与 `*` 回退（`snapshot.go:441-450`），避免把 IP 请求误落到泛域名站点。

## 性能考虑

- 构建成本随配置规模线性增长：站点数、监听器数、规则数与 `system_settings` 行数共同决定一次 `Build` 的读取量；规则与应用路由规则都在构建期编译，请求期不再解析字符串。
- 设置表只读一次：`loadAllSettings` 把整表预加载成 map 后复用（`build.go:1432`），逐键解析不再触库。
- 上游 mTLS 的 PEM 解析在站点循环前一次性预计算并写回切片元素（`build.go:226-228`），主循环复用 DER/指纹。
- 键查找是 O(1) 哈希 + 至多三级回退，没有树结构；`MatchSite` 拷贝结构体、`MatchSitePtr` 零拷贝，热路径应使用后者。
- 缓存 MaxCost 很小，若把重载频率拉高，命中率会下降；批量变更请合并为一次写请求。
- 详细性能口径属架构与引擎视角，见 [缓存与性能优化](../系统架构设计/缓存与性能优化.md)。

## 结论

配置层的快照机制做的是「**把多表、多形态的配置压成一个只读对象**」：`Build` 负责读取与折叠，键设计负责命中与唯一性，诊断数组负责解释被丢弃的部分，`Holder` 负责把代次语义变成一次指针交换。

三条值得坚持的设计：

1. 一次读取、全程只读，让数据面无需为配置加锁。
2. 致命错误与可跳过错误显式分档，可选能力的坏配置不会拖垮整个控制面。
3. 三态字段在入库前折叠从属值、在构建期按判据合并，使「继承全局」与「显式关闭」在库里就是两种可区分状态。

一条已知代价：`rules` 的 kind 在快照侧另有一套 30 项白名单，与管理侧 57 项不等价，属于真实的口径分裂，已在验证篇登记。
