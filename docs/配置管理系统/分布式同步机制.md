## 简介

My-OpenWaf 的多实例同步回答的是一个很窄的问题：**配置真相源只有一个（共享数据库），实例之间只传"该重载了"这个事件，不传配置本身**。

这决定了整套机制的形状：

- 任何实例上的管理 API 写库后，先递增 `config_revisions.revision`，再本地重建快照，最后向 Redis 频道广播一次 `reload`；
- 其他实例收到事件后，用**同一套**代码从**同一个库**读取最新版本并重建快照，因此不存在"配置副本漂移"，只存在"生效时间差"；
- Redis 是**可选依赖**：`OptionalClient` 在地址为空、连接失败或 Ping 超时时一律返回 `nil`，进程继续启动并降级为单实例行为，不广播、不选主、计数不出进程。

因此本文同时是两份清单：有 Redis 时的同步链路，以及无 Redis 时的降级路径。把 Redis 写成必需组件的表述都是错的。

## 详细组件分析

### 重载链路与发布时机

`reloadRuntime` 是全链路唯一入口，`propagate` 参数区分「本地发起」与「远端驱动」两种语义：只有本地发起才递增版本号并广播。Redis 配置即将切换时还有一个前置发布（`prePublish`），目的是让其他节点在**本节点后端换装之前**就看到新快照，避免新旧后端交叠期间漏通知。

| 步 | 动作 | 执行位置 | 输入 | 输出 | 失败分支 | 可观测点 |
|:--:|------|----------|------|------|----------|----------|
| 1 | 串行化重载 | `server.go:1003` `runtimeReloadMu.Lock` | 任意 reload 触发源 | 单飞临界区 | 阻塞等待前一次完成 | 无独立指标 |
| 2 | 递增版本 | `store/migrate.go:141`（仅 propagate） | `config_revisions` 行 | revision+1 | 返回错误，中止本次重载 | `/status` 的 `revision` |
| 3 | 代次 CAS 重建 | `runtime.go:211-274` | 读到的 rev | 不可变快照 | 版本被并发推进则 `continue` 重试 | 日志 `snapshot build` |
| 4 | 发布快照 | `snapshot.go:474` `StoreIfNewer` | 新快照 | 原子指针替换 | 修订不更新则返回 false | `/readyz` |

### 一致性保证

一致性由三层叠加，**没有任何一层依赖消息可靠性**：

1. **版本号 CAS**：重建前后各读一次 `config_revisions`，任一时刻发现版本被推进就丢弃当前结果重来（runtime.go:224-268），保证「发布出去的快照一定对应当前最新修订」。
2. **单调发布**：`StoreIfNewer` 用 `CompareAndSwap` 循环，只在当前修订更旧时才替换（snapshot.go:474-487），因此并发重载不会用旧快照覆盖新快照。
3. **收敛观测**：`/status` 暴露 `revision`、`sites`、`listeners`（health.go:75-100），逐节点比对该值即可直接判定是否收敛。

未实现的部分必须说清楚：**没有消息确认、没有重传、没有版本号携带**。`PublishReload` 失败只写一条 `Warn`（pubsub.go:79-81），此后该事件永久丢失，落后节点要等到下一次变更或人工 `POST /api/v1/reload`（router.go:313）才会追平。这是一个明确的最终一致设计，冲突解决等价于「以库里当前版本为准」。

选主语义要点：`sinkOnce` 先争锁再 `DrainAggregated`，而 Drain 的 Lua 是「读两个 hash + 立即 `DEL`」的原子操作（redis_kv.go:222-227），因此同一批计数只会被回写一次；锁 TTL（30s）大于 sink 周期（5s），持锁节点宕机后最多 30s 由其他节点接管。锁**没有续期**，若单轮 Drain+逐条 `Upsert` 超过 30s，其他节点可能并行进入——这是可接受的窗口，因为 Drain 本身原子，不会双重累加。

`Incr` 走的是 Lua（`INCR` + 首次 `PEXPIRE`，redis_kv.go:20-26、197），**不是 Pipeline**；只有 `HAggregateFlush` 用 `DoMulti` 批量管道（redis_kv.go:255）。两者的超时也不同：前者 1s，后者 2s。

### Redis 有/无两态行为差异

Redis 全程可选：`OptionalClient` 地址为空即返回 `nil`（redis.go:19-21），建连失败也返回 `nil`（redis.go:30-32）；`NewRuntime` 的 Ping 失败只关客户端、置空并打印 `redis unavailable, continuing without redis`（runtime.go:104-116），**不会让启动失败**。引导期校验还会刻意清空环境变量里的 Redis 字段（runtime.go:40-43），因为库里存的 `redis_config` 才有权决定最终状态。

同为「Redis 出错」，两条路径的策略是**相反**的，必须分开记：限流是 fail-open（`Allow` 在 50ms 超时或错误时返回 `true`，ratelimit/redis.go:133-137），防重放是 fail-closed（Lua 出错或应答畸形时返回 `false, true`，即当作重放拦截，antireplay.go:145-177）。把二者统称「降级放行」是错的。

`RedisKV` 自带健康位与回退窗口：任一命令出错即置 `health=false` 并记录 `unavailableUntil = now + 5s`（redis_kv.go:82-97），期间 `Available()` 直接返回假，调用方走本地路径；成功一次即恢复。这意味着 Redis 抖动表现为「5 秒一段的本地/共享交替」，而不是频繁超时重试。

后端可在运行期整体换装：`applyRedisRuntimeReload` 依次对 `RedisKV`、`HotCache`、`UnifiedWriter`、`CaptchaManager`、`ShieldManager`、`ChainChallengeManager`、`AntiReplayManager`、`EscalationManager`、访问控制存储共九处 `Set*`，再 `Swap` 两个限流后端并重建 `ConfigSync`，最后关闭旧客户端（server.go:1205-1252）。

### 多实例写入协调

需要明确：`WriteQueue` 与 `UnifiedWriter` **只做进程内协调**，没有任何跨节点锁。`WriteQueue` 用单通道 + 单消费 goroutine 合并批写，靠 SQLite WAL 与 `busy_timeout=10000` 承受多进程并发（write_queue.go:13-60）。真正的跨节点协调只发生在两处：资源聚合的 sink 选主，以及事件向 Redis 列表的双写。

`UnifiedWriter` 的 Redis 双写发生在 DB 事务**提交之后**，用 `LPUSH` + `LTRIM` + `EXPIRE 7d` 写四个列表：`openwaf:security_events`、`openwaf:access_logs`（裁剪到 99999）、`openwaf:drop_events`、`openwaf:bot_scores`（裁剪到 49999），单次超时 5s（unified_writer.go:1105-1220）。顺序刻意是「先提交、后推送」：先写 Redis 再写 DB 时，DB 回滚会留下永远无法回源校验的脏记录；而 DB 成功后推送失败只把本轮标记为 `failed`，读路径可回源数据库补齐，不影响已提交记录。

风险项：这四个列表在当前代码里**只有写入方，没有读取方**。实时看板走 `RealtimeHub` 轮询数据库（server.go:1054），并未消费这些列表。因此无 Redis 时实时功能不受影响，而有 Redis 时这份双写是纯开销。

## 性能考虑

- 广播是低频控制面操作，单条 `PUBLISH` 的 2s 超时上限决定了它对请求路径无影响；请求路径永远只读原子指针（`Holder.Load`）。
- 快照重建的开销由 `cache.Layer` 的按修订缓存吸收：同一修订的重复通知直接命中缓存（runtime.go:223），因此「多节点同时收到广播」不会造成 N 倍建库查询。
- 限流与计数类命令统一压到 50ms（ratelimit、escalation、challenge），且都是**请求路径上的有界等待**，最坏情况增加 50ms 尾延迟，不会级联。
- `HAggregateFlush` 用一次 `DoMulti` 承载「N 个 `HINCRBY` + M 个 `HSET` + 2 个 `EXPIRE`」，把每命中一次往返一次降为每个 flush 窗口一次。
- sink 周期（5s）刻意大于本地 flush 周期（2s），进一步合并跨节点计数、降低 DB 写频率（resource_aggregator.go:25-33）。

## 结论

本项目的分布式同步是一条刻意做窄的链路：**共享数据库负责一致性，Redis 只负责"通知"**。版本号 + 代次 CAS + 单调发布三者叠加，使每个节点独立重建出的快照必然等价；广播丢失不会破坏正确性，只推迟生效。

- **KISS**：频道名、负载结构、回环抑制各一处，无额外协调服务。
- **YAGNI**：没有节点注册表、没有确认重传、没有配置合并算法——当前规模下这些都是负债。
- **DRY**：本地与远端共用同一个 `reloadRuntime`，仅以 `propagate` 布尔区分，避免两套重载实现。
- **SRP**：`ConfigSync` 只搬事件，`Runtime` 只管代次，`RedisKV` 只管共享状态，`applyRedisRuntimeReload` 只管换装顺序。

主要短板是发布侧无重传、以及四个事件列表只写不读。

- 限流：`openwaf:request:rl:*`、`openwaf:error:rl:*`（server.go:1239-1244，ratelimit/redis.go:136）
- 例外命名：绕过 `RedisKV` 直接用客户端的组件各自带独立前缀——`owaf:escalation:*`（escalation.go:82-91，50ms）、`owaf:captcha:*`（captcha.go:207，50ms）、`owaf:shield:*`（shield.go:200）、`owaf:chain:*`（chain.go:155，状态 TTL 10 分钟）、`waf:nonce:spent:*` 与 `waf:nonce:idem:*`（antireplay.go:142-143，80ms）。
- 因此库内实际并存**三套**前缀（`openwaf:`、`owaf:`、`waf:`），且超时也不统一（1s/2s/5s/80ms/50ms/3s）。这属已登记的不一致项，不影响功能，但会影响按前缀做的运维扫描与容量估算。

### 部署拓扑建议

- 所有实例连接**同一个** SQL 数据库，这是同步的前提；各自独立的 SQLite 文件不构成集群。
- 控制面与数据面同进程部署（单二进制双平面），管理端口暴露 `/healthz`、`/readyz`、`/status`、`/metrics`（server.go:1052-1056）。
- 收敛验证方式：逐节点 `GET /status`，比对 `revision` 是否一致；`/readyz` 要求快照非空、监听就绪、令牌管理器就绪且数据库 Ping 成功（health.go:29-39）。
- 无 Redis 的部署必须把「人工触发 `POST /api/v1/reload` 逐节点执行」写入运维流程，或改用裸 `PUBLISH`。
- 监听器按 bind 指纹增量启停（server.go:722-801），`lifecycle.Manager` 的移除路径使用 500ms 短超时（lifecycle.go:19-21），因此配置变更的重启窗口只影响对应站点。
