## 简介

本文件系统梳理 My-OpenWaf 的配置验证体系，按**校验发生的层次**而非按文件组织，覆盖五层：

1. 引导层：`Config.Validate` 在进程启动前校验数据库驱动、DSN、监听地址。
2. 覆盖层：`configoverride` 按 `Kind` / `Scope` / 枚举 / 区间校验 `runtime_config_overrides` 的每个键。
3. 入库层：Admin 处理器在写库前校验动作、phase、限流配额、验证码类型、JSON blob、站点上游与证书。
4. 构建层：`snapshot.Build` 再解析一遍规则与设置，决定「致命失败」还是「记诊断继续」。
5. 呈现层：`ApiError` 与 i18n 把后端错误串映射为界面提示。

三条实测结论，后文逐条给证据：

- 校验函数**不止一处实现**，规则的 kind 白名单实测分散在三处，且互不等价：管理侧 57 项、快照侧 30 项、路径跳过 9 项 phase。
- 多数写入口是**非 fail-closed**：配置先落库，重载失败只返回 500，不回滚。
- `TestRule` 只构造 6 个匹配字段，TLS / Host / Header 顺序类 kind 在测试接口里**恒不命中**，属真实缺陷。

边界说明：字段构成与 DB 映射见 [配置快照机制](配置快照机制.md)；重载链与代次 CAS 见 [热重载系统](热重载系统.md)；本篇不重复其表格。

## 核心组件

- `Config.Validate`：值接收者，返回 `(warnings []string, err error)`；错误一条即中止启动，告警只打印（`config_validate.go:11-49`）。
- `configoverride.Spec`：把「一个键能不能写、按什么类型校验、要不要重启」集中成静态元数据（`registry.go:85-118`）。
- `rules.ValidatePattern`：唯一的规则表达式语义校验器，返回 `(kind, arg, errs)`，`errs` 为可枚举的多条错误（`validate.go:28-34`）。
- `knownPrefixes`：57 项 kind 白名单，`ParsePattern` 与 `validateSimplePattern` 共用（`compiler.go:119-142`、`validate.go:124-126`）。
- `shared.Validate*` 家族：动作、验证码类型、CC 规则、质询动作、反重放模式、bot 阈值、上游地址与主机名（`helpers.go:104-310`、`site_upstreams.go:24/97`）。
- `normalizePersistedRuleConfig`：规则入库前的总闸，phase、pattern、action、redirect、captcha、频次参数逐项校验并归一（`rule.go:298-340`）。
- `snapshot.Build`：构建期二次解析，致命错误与可跳过诊断分档（`build.go:34-50`）。
- `luaplugin.DryRun` / `luaplugin.Validate`：脚本的干跑与仅编译校验（`dryrun.go:55-132`）。

## 架构总览

验证发生在「写」与「生效」两个时刻，中间由一次重载相连。实测的关键事实：**写入口的校验用 57 项白名单，生效端的解析用 30 项白名单**，两者不交集的部分会静默丢失。

## 详细组件分析

### 引导层：启动前配置校验（Config.Validate）

`Validate` 是纯函数，不触碰数据库，返回「告警数组 + 一个致命错误」。实测规则：

| 对象 | 规则:行 | 失败行为 | 是否 fail-closed |
|------|---------|----------|:---:|
| `DBDriver` | 必须 ∈ {"", sqlite, mysql, postgres, postgresql}（config_validate.go:15-20） | 返回 error，启动中止 | 是 |
| `DBDSN` | 非空（config_validate.go:23-25） | 返回 error | 是 |
| `AdminBind` | `net.SplitHostPort` 可解析（config_validate.go:28-30） | 返回 error | 是 |
| `RedisAddr` | 非空时必须可解析（config_validate.go:33-37） | 返回 error | 是 |
| 驱动与 DSN 一致性 | sqlite + `host=` 或 `@tcp(` → 告警（config_validate.go:40-42） | 仅告警 | 否 |
| 管理端口 | 绑定 `:80`/`:443` → 告警（config_validate.go:44-46） | 仅告警 | 否 |

两点容易被忽略的实测语义：

1. `postgresql` 是合法别名，与 `database.Open` 的分支保持一致；早期文档只写三值白名单是错的。
2. `NewRuntime` **两次**调用 `Validate`：引导期把 Redis 三字段清空后校验一次（`runtime.go:39-43`、`55-61`），读入库中 `redis_config` 与覆盖表之后再校验一次（`runtime.go:71-87`）。第一次刻意不因环境变量里的 Redis 值失败，因为此时库里覆盖值尚未应用。

### 覆盖层：Kind 与 Scope 校验（配置项表）

`runtime_config_overrides` 的校验完全由静态注册表驱动，45 个键的分布实测如下：

| 维度 | 取值 | 键数 | 校验含义 |
|------|------|:---:|----------|
| Kind | `string` | 20 | 仅当声明 `EnumValues` 才做白名单（resolve.go:216-231） |
| Kind | `int` | 13 | JSON 数字、整数性、`Min/Max` 区间、非负（resolve.go:173-190、236-249） |
| Kind | `bool` | 9 | 只接受 JSON 布尔与 `true`/`false` 文本，**不接受 0/1**（resolve.go:161-175） |
| Kind | `duration` | 3 | 必须可 `time.ParseDuration`，按纳秒区间校验（resolve.go:193-212） |
| Scope | `runtime` | 29 | 可写；`IsWritable()` 仅此值为真（registry.go:580） |
| Scope | `delegated` | 7 | 只展示，写入口在专用端点（如 `redis_addr` → `/api/v1/redis-config`） |
| Scope | `bootstrap` | 7 | 只读；引导参数不可覆盖 |
| Scope | `test_only` | 2 | 不进界面、不可覆盖 |
| 属性 | `Secret: true` | 5 | 端点不回显真值（`dsn`、`log_dsn`、`jwt_secret`、`redis_password` 等） |
| 属性 | `RestartRequired: true` | 26 | 覆盖需重启才生效，重载只改库不改结构体 |

三条失败路径：

- 未知键 → 400 `unknown key`（`runtime_overrides.go:276-280`、`291-295`）。
- 非 `runtime` 作用域 → 400 `key is not overridable`，附带 `scope`（`runtime_overrides.go:281-285`）。
- 取值不合法 → 400 并回显 `key`（`runtime_overrides.go:297-301`）。

存储侧读取则是**降级而非失败**：`ParseStoredOverrides` 对未知键、非可写键、不可解析值一律告警后跳过（`resolve.go:71-90`），因此库里脏数据不会阻塞重载。

### 规则层：pattern 语法与语义校验

`ValidatePattern` 先用 `ParsePattern` 拆 kind/arg，再分派到复合或简单校验（`validate.go:28-46`）。简单 kind 的语义规则并不统一，逐组实测：

| kind 组 | 规则:行 | 失败文案 | 是否 fail-closed |
|---------|---------|----------|:---:|
| `block_path` | 需非空前缀（validate.go:129-132） | `block_path 需要非空路径前缀` | 是 |
| `allow_ip` / `block_ip` | 先试 `ParseCIDR`，再试 `ParseIP`（validate.go:140-146） | `IP/CIDR 匹配器要求合法的 IP 地址或 CIDR` | 是 |
| 正则族（`block_path_regex` 等 6 项） | 非空 + `cachedCompile` 成功（validate.go:147-153） | `规则表达式使用了非法的正则表达式` | 是 |
| Header 族 | 需 `name:value` 两段非空（validate.go:154-171） | `Header 匹配器需要 name:value 格式` | 是 |
| `query_param*` | `param:value` / `param:regex`（validate.go:172-184） | `query_param 需要非空的 param:value 格式` | 是 |
| 通配符族（5 项） | 非空 + `globToRegexSource` + 编译（validate.go:212-238） | `通配符匹配器需要非空的通配符模式` | 是 |
| `tls_version` | `tlsmeta.NormalizeRuntimeVersionToken` 非空（validate.go:239-242） | `tls_version 需要合法的 TLS 版本标识` | 是 |
| `tls_cipher_suite(s)` | 逗号切分后至少一个合法套件（validate.go:243-254） | `tls_cipher_suites 至少需要一个合法的密码套件标识` | 是 |
| 未知 kind | `knownPrefixes` 未命中（validate.go:124-126） | `复合条件叶子节点使用了不支持的 kind` | 是 |

复合条件（`kind == "compound"`）的 op 白名单实测为 6 个分支，早期文档写「op 必须为 and/or/not」是错的：

| op | 结构约束:行 | 失败文案 |
|----|-------------|----------|
| `and` / `or` | `children` 至少 1（validate.go:57-61） | `复合条件至少需要一个子条件` |
| `not` | `children` 恰好 1（validate.go:62-66） | `非条件必须且只能包含一个子条件` |
| `if` / `if_else` / `ifelse` | `if` 与 `then` 必须同时存在，`else` 可选（validate.go:67-75） | `条件必须同时提供 if 和 then 分支` |
| `cc_rate` | 恰好 1 子条件，`window>0`、`threshold>0`、`duration_unit ∈ {"", seconds, minutes}`、时长非负（validate.go:76-92） | 逐条对应文案 |
| 空 op（叶子） | `kind` 必填且过简单校验（validate.go:93-99） | `复合条件叶子节点必须定义 kind` |
| 其它 | 直接拒绝（validate.go:100-102） | `复合条件使用了不支持的操作符` |

绕过保存校验进入编译路径的非法模式不会报错，而是**退化为恒不命中的 `neverMatcher`**：`Compile` 先装配 `neverMatcher`，仅当 `validateParsedPattern` 返回空错误时才替换为真匹配器（`compiler.go:50-52`），`buildMatcher` 的 30 余条分支也各自在参数非法时回落（`matcher.go:504-507`、`1474-1926`）。这是匹配层的 fail-closed 兜底，与快照层「kind 为空直接丢弃」构成两道独立的静默失效路径——两者都不产生诊断，因此界面无从感知。

### TestRule 的采样面缺陷（如实登记）

`TestRuleRequest` 有 7 个字段（`rule.go:213-221`），但构造 `MatchCtx` 时只填 6 个（`rule.go:251-257`）：`ClientIP`、`Method`、`Path`、`Query`、`Headers`、`Body`。

`rules.MatchCtx` 实际有 15 个字段（`phases.go:33-52`），其中 `Host`、`Bind`、`SiteID`、`HeaderOrder`、`TLSALPN`、`TLSCipherSuites`、`TLS *tlsfp.TLSClientFingerprint`、`HeadersLowercase` 均未被赋值。后果按 kind 实测分类：

|---------|----------|---------------|------|
| `host*` | `MatchCtx.Host` | **恒不命中** | 请求体没有 host 字段可填 |
| `tls_ja3` / `tls_ja3_hash` / `tls_ja4` / `tls_version` / `tls_sni` / `tls_alpn` / `tls_cipher_suite(s)` | `MatchCtx.TLS`、`TLSALPN`、`TLSCipherSuites` | **恒不命中** | 指纹只在握手期可得 |

| IP/路径/查询/头/方法/正文族 | 已覆盖的 6 字段 | 结果可信 | — |

## 性能考虑

- 正则缓存：所有正则类校验与匹配都走 `cachedCompile`，同一模式串只编译一次（`matcher.go:1791-1808`）。
- 通配符先行归一：`globToRegexSource` 在校验期就展开为正则源串，运行期不再做模式转换。
- 设置表单次读取：`loadAllSettings` 一次取全表成 map，覆盖表解析不重复查库（`build.go:1432`）。
- 干跑成本可控：`DryRunNContext` 上限 100 次迭代，单次超时由脚本自身 `TimeoutMS` 决定，且使用独立 VM 池（`dryrun.go:66-115`）。
- 校验顺序遵循「便宜的先做」：`BindJSON` → 判空 → `ParsePattern` → 语义校验 → 正则编译，避免为非法输入付出编译成本。
- 反向注意：`validateEnabledLuaPlugin` 会为每个启用脚本付出一次真实执行，批量导入脚本时应控制并发。

## 结论

验证体系的形状是「**四层各自成立、层间不等价**」：

- 引导层与覆盖层是真正的 fail-closed：错误即中止或 400，不留中间态。
- 入库层校验最丰富，但失败后是否落库取决于错误发生在 reload 之前还是之后，因此存在「已落库未生效」的正常态。
- 构建层是最后防线，却采用「致命/可跳过」两档，可跳过项里最危险的是规则 kind 的**静默丢弃**。

三项建议（按性价比排序）：

1. 给白名单 2 与 1 的差集加一条契约脚本，口径沿用 `check-skip-path-by-phase.ts` 直接读源码的做法；短期内可先在 `compileRules` 的 `kind == ""` 分支写入 `ConfigDiagnostics`，把静默变成可见。
2. `TestRule` 对无法采样的 kind 返回「不适用」，避免把接口局限误读成规则错误。
3. 前端规则编辑器暴露的 33 个 kind 中，有 21 个落在快照侧 30 项之外，应在编辑期即标注「当前构建链路不生效」。
