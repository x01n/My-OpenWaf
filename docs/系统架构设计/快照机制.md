## 项目结构
从架构上看，快照由「生产者—持有者—消费者」三种角色构成，三者之间没有直接调用，只通过对象与代次耦合。

| 平面归属 | 角色 | 承载 | 架构职责 |
|---|---|---|---|
| 双平面之间 | 共享视图 | `snapshot.Snapshot` | 唯一可跨平面传递的配置物 |
| 装配侧 | 生产者 | `Runtime.ReloadSnapshotWithPrePublish` | 把库里的配置变成一个代 |
| 装配侧 | 发布闸门 | `Holder.StoreIfNewer` | 只允许新代替换旧代 |
| 数据面 | 消费者 | `dataplane.Handler`、`engine.Engine` | 每请求读一次，不再回查库 |
| 控制面 | 间接消费者 | `health.Checker`、响应头策略 | 判断就绪与 HSTS 取值 |
| 编排侧 | 二次消费者 | `reconcileListeners` | 据快照决定监听器集合 |
| 缓存层 | 代次记忆 | `cache.Layer` | 同代不重复构建 |
| 存储层 | 代次来源 | `store.BumpRevision` | 单调递增的唯一写入点 |

## 架构总览
快照存在的理由是：数据面必须以**无锁**方式读配置，而配置又必须能被管理端随时改写。把「随时改写」收敛为「换指针」，把「无锁读」收敛为「读一次指针」，两侧就都不需要协调。这是整个架构里最关键的一次取舍。

| 架构层 | 快照在该层的作用 | 关键约束 |
|---|---|---|
| 装配层 | 构建并持有第一个代 | 构建失败即 `os.Exit(1)`，不允许无快照启动 |
| 控制面层 | 递增代次、触发重建 | 只写库，不直接改运行态 |
| 共享视图层 | 不可变承载 | 构建后零改写 |
| 数据面层 | 每请求读一次 | 读不到就 503，不猜测默认配置 |
| 编排层 | 依据快照算期望监听集 | 指纹变化才重启 |
| 观测层 | 就绪判定包含快照非空 | `/readyz` 会因空快照返回 503 |

| 外部实体 | 与快照的关系 | 契约 |
|---|---|---|
| 管理员 | 间接生产者 | 写入 + `Reload` |
| Redis 同级节点 | 触发对端重建 | 只传「reload」事件，不传快照内容 |
| 上游源站 | 无直接关系 | 其健康态存在进程内池中，不属快照 |
| Prometheus / 探针 | 读取代次数值 | `/status` 的 `revision` |
| ACME 续期循环 | 触发重建 | 与管理员同一条 reload |
| 威胁情报订阅源 | 定时触发重建 | `reload` 作为回调注入 |

## 详细组件分析

### 构建时机：四个触发源
快照不会自己更新。全库只有四处会真正发起重建，它们都汇到同一个入口 `reloadRuntime`。

| 时机 | 触发点 | 是否递增代次 | 位置 |
|---|---|---|---|
| 进程启动 | 首代构建，失败即退出 | 否（沿用库中当前代） | server.go:293 |
| 管理端写操作 | `deps.Reload` → `reloadRuntime(true)` | 是 | router.go:62、server.go:1031 |
| Redis 收到对端广播 | 订阅回调 → `reloadRuntime(false)` | 否（对端已递增） | server.go:1040、964-969 |
| 后台周期任务 | 威胁情报同步、ACME 续期 | 是（走同一个 `reload`） | server.go:1036、1057 |

### 发布语义：prePublish 与代次 CAS
`ReloadSnapshotWithPrePublish` 的契约有两层含义，都属于架构约束而非实现细节：

1. **回调时机**：`prePublish` 在该代快照对请求处理器**可见之前**执行（runtime.go:231-235 命中路径、257-261 构建路径）。当前唯一使用者是 JS 引擎的对齐——若脚本集合要求先切执行器再发布，反过来会让在途请求读到「新快照 + 旧执行器」。
2. **失败即不改态**：回调返回错误时整次重载失败，**已发布的快照保持不变**（runtime.go:232-234、258-260 直接返回错误，`StoreIfNewer` 不会被调用）。

发布本身用 CAS 而非无条件写：`StoreIfNewer` 只在当前已激活代更旧时才替换（snapshot.go:474-487）。`Holder.Store` 仍然存在但注释明确要求运行时重载不要用它，否则可能用旧修订覆盖更新的快照（snapshot.go:457-464）。

`reloadMu` 让同进程的重载彼此串行（runtime.go:212-213），因此「并发 reload」只可能发生在多节点之间，而跨节点冲突由 CAS 与代次单调性解决。

### 一次发布的牵动面
换掉一个指针不是「配置生效」的全部。`applySnapshotReload` 在发布之后还串起六类副作用，它们决定了「哪些状态属于快照、哪些状态属于进程」这条边界。

| 副作用 | 触发条件 | 效果 | 位置 |
|---|---|---|---|
| 响应缓存清空 | 新旧快照指针不同 | `responseCache.Clear()` | server.go:879-882 |
| 保护参数重下发 | 新快照非空 | 限流、验证码超时、盾参数、链步骤、登录爆破、drop 阈值、GeoIP | server.go:884、637-688 |
| Lua 脚本热替换 | 新快照非空 | 整体原子替换脚本集合 | server.go:886 |
| IP 名单重载 | 每次 reload | 黑白名单全量重灌 | server.go:888 |
| 监听器调谐 | 每次 reload | 按 `bind` 增删重启，含 HTTP/3 | server.go:889、722-825 |
| 上游 transport 修剪 | 每次 reload | 清理不再活跃的池对象；端点集合变化时关闭空闲连接 | server.go:890-895 |

这条边界是可验证的：**「新代理的默认配置」不在快照里**（`upstream.Pool` 的健康态与 transport 是进程态），而**「站点的上游地址列表」在快照里**（`SiteRuntime.UpstreamURLs`）。二者混用会导致 reload 后行为不确定。

### 跨节点同步：只传事件不传快照
架构上刻意不做的事：不把序列化后的快照通过网络搬运。原因是 `Snapshot` 内含 `tls.Config`、已编译脚本、指针比较的 `*ProtectionConfig` 等不可序列化也不该重建的对象；跨节点只广播「该重载了」，各节点从**自己的**数据库读同一条代次，再用**自己的**代次缓存构建（pubsub.go:64-121、layer.go:18-23 的包注释明确写了这条设计判断）。

| 环节 | 取值/行为 | 位置 |

| 频道 | `openwaf:config:reload` | pubsub.go:16 |
| 载荷 | `{source_id, action}` | pubsub.go:19-22 |
| 发布超时 | 2 秒，失败仅告警 | pubsub.go:77-81 |
| 回环抑制 | `sourceID` 相同直接忽略 | pubsub.go:114-116 |

## 性能考虑
- 读路径成本固定：每请求一次 `Load()` 加至多三次 map 探底，不随配置规模变化。
- 构建成本被代次缓存吸收：同一代在进程内只构建一次（layer.go:44-51，写入后 `Wait()` 保证可见）。
- 缓存参数属于**快照层**而非规则层：`NumCounters 1e4 / MaxCost 1<<20 / BufferItems 64`（layer.go:30-34）。规则编译缓存没有 LRU 与 MaxCost，它靠整体替换不可变 map 来控制规模。
- 二次核对会让 reload 多读两次 `config_revisions`（runtime.go:224-242），这是用一次极廉价的单行查询换「不用旧代覆盖新代」的正确性。
- 副作用链是同步执行的：`reconcileListeners` 与 transport 修剪都在 reload 调用栈内完成，因此高频写配置会把重载排队在 `reloadMu` 之后。

## 结论
从架构看，快照做的是三件事：把「可变配置」变成「不可变对象」，把「改配置」变成「换指针」，把「多节点一致」变成「各自重建」。它让数据面的读永远无锁、让控制面的写永远不必担心在途请求，同时把跨节点通信压缩成一个事件。代价也很明确：配置生效不再即时而是代次驱动，副作用链在重载栈内同步执行，且必须靠代次 CAS 与二次核对来防止旧覆盖新。

引擎如何消费这份视图、配置层如何组织这份视图，分别由另外两篇快照文档负责，本篇不重复。
