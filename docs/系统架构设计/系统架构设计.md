## 简介
本文件系统性阐述 My-OpenWaf 的系统架构设计，重点围绕控制面与数据面的分离理念、双服务器架构的工作原理与优势、快照模式的不可变性与热重载机制展开。通过对核心组件（运行时、快照、引擎、数据平面处理器、生命周期管理、Redis 配置同步）的深入分析，解释数据流向与组件交互关系，并提供架构决策的技术考量、性能权衡与可扩展性设计建议。

**本域文档划界**：本文只回答「系统分成哪几层、为什么这样分、层之间靠什么契约」；组件级拓扑与依赖边集中在 [组件关系图](组件关系图.md)，请求路径上的数据转换集中在 [数据流分析](数据流分析.md)。快照主题同样按视角三分——本文只写快照在双平面间的角色与发布时机，引擎内部如何消费快照见 [快照系统](../WAF 引擎系统/引擎核心架构/快照系统.md)，配置层快照与热重载落地见 [配置快照机制](../配置管理系统/配置快照机制.md)。

## 项目结构
My-OpenWaf 是单进程双平面应用：`cmd/main.go` 只做子命令分派与 pprof 开关（`MY_OPENWAF_PPROF_BIND`），其余全部交给 `internal/app.Run()`；`Run()` 按固定顺序装配运行时、持久层、缓存、引擎、数据面与生命周期管理器，最后 `lm.Start()` 一次性拉起全部监听器并在 `WaitForSignal()` 上阻塞。

## 架构总览
My-OpenWaf 将控制平面与数据平面解耦到同一进程的两个端口组：控制面监听 `AdminBind`，只承担配置写入、可观测性与生命周期编排；数据面按**监听地址**（不是按站点行）创建 Hertz 服务器，共享同一个快照持有者与引擎实例。两平面之间唯一的契约是「修订号 + 不可变快照」：控制面写库并 `BumpRevision`，数据面只读 `Holder.Load()` 的结果。

| 层 | 承载 | 平面 | 职责 | 层间契约 |
|---|---|---|---|---|
| L0 引导 | `cmd/main.go` | — | 子命令与 pprof 开关 | 调用 `app.Run()` |
| L1 装配 | `internal/app` | 跨平面 | 16 阶段启动链、监听器调谐、HTTP/3 计划 | 向下游注入依赖，不被下游依赖 |
| L2 控制面 | `internal/admin` | 控制面 | 217 个管理端点、认证鉴权、SPA 回退 | 写库 + `Reload()` 回调 |
| L3 数据面接入 | `internal/dataplane` | 数据面 | 门禁、动作落地、协议分派 | 只读快照，不写配置库 |
| L4 决策 | `internal/core/engine`、`pipeline`、`rules` | 数据面 | 阶段链组装与执行 | 输入 `RequestCtx`，输出 `ProcessResult` |
| L5 配置视图 | `internal/snapshot`、`internal/cache` | 双平面 | 不可变视图与按代次缓存 | `Holder` 原子发布 |
| L6 转发 | `internal/proxy`、`internal/upstream` | 数据面 | 连接池复用、探活、响应回写 | 按站点 TLS 键复用 transport |
| L7 持久 | `internal/store`、`repository` | 控制面写 | 主库（配置）与日志库分离 | `BumpRevision` 单调递增 |
| L8 观测 | `internal/observability`、`dataplane/metrics` | 双平面 | 指标导出与批量落库 | 异步通道，不阻塞请求路径 |

## 详细组件分析

### 启动链路：16 个装配阶段
`Run()` 的阶段顺序不是随意的：快照构建必须在写队列之前完成（否则 `applyProtectionRuntimeConfig` 拿不到 `Protection`），而挑战栈与限流器又依赖快照里的保护参数，监听器调谐最后执行。任一前置阶段失败即 `os.Exit(1)`，不留半启动态。

| 序 | 阶段 | 位置 | 产出 |
|:--:|---|---|---|
| 1 | 日志器与根上下文 | server.go:236-240 | `logger.New("app")`、ACME 子上下文 |
| 2 | 运行时装配 | server.go:242 | 双库、可选 Redis、缓存层、Holder |
| 3 | 主库迁移 | server.go:249 | `store.AutoMigrate` |
| 4 | 内置目录对账 | server.go:253、257 | OWASP / CVE 目录 |

### 站点解析：哈希键加至多三级查找
旧文档曾把这里描述成「Trie 树加速」，这是错误的：全库没有任何 trie 实现，`internal/dataplane` 下也不存在 `trie.go`。真实机制是把 `(bind, host)` 拼成单一哈希键 `bind + "\x00" + host`，然后在一个 `map[string]*SiteRuntime` 上做**至多三次**查表。

| 序 | 候选键 | 触发条件 | 代码位置 |
|:--:|---|---|---|
| 1 | `bind + NUL + 精确 host` | 始终先试 | snapshot.go:343-346 |
| 2 | `bind + NUL + "*." + 单级父域` | host 不是 IP 且含 `.` | snapshot.go:348-355 |
| 3 | `bind + NUL + "*"` | catch-all 站点 | snapshot.go:357-359 |

Host 在查表前统一经 `NormalizeMatchHost` 处理：小写化、去首尾空白、剥离端口；若已是规范形式则原样返回、零分配（snapshot.go:409-439）。写入侧 `registerSiteKeys` 不做 first-come 抢占：同一键若属于另一站点，直接返回 `duplicate site route` 错误使本次 reload 失败；同站点重复键则幂等跳过（build.go:787-804）。未命中站点不会返回 404，而是记 `no site match` 告警、写出欢迎页 200 并以 `routing_error` 落审计行（handler.go:151-162）。

## 性能考虑
- 快照不可变与原子切换：读路径只有一次 `atomic.Pointer.Load()`，无锁竞争；旧代由 GC 回收。
- 阶段链与规则编译缓存：`getOrBuildPhases` 以 `{policyID, siteID, antiReplayEnabled}` 为键，加上 `prot`/`lua`/`luaRevision`/`deps` 四判据，热路径走无锁快路径（engine.go:446-464）。
- 请求上下文池化：`pipeline.AcquireCtx/ReleaseCtx` 复用 `RequestCtx`，池对象超过容量上限时在 Release 侧重建，避免峰值后 RSS 不回落（pool.go:11-28）。
- 上游连接复用：主 transport 为 `MaxIdleConns 256 / MaxIdleConnsPerHost 32 / IdleConnTimeout 30s`，`MaxConnsPerHost 256`，16KiB 读写缓冲（transport.go:157-164、172）。
- 观测性异步化：`UnifiedWriter` 用四条通道加单 goroutine 批量事务落库，容量与批大小由 `rt.Config.Queue` 注入（server.go:340-350）。
- 按监听地址拆分服务器：负载与 TLS 配置隔离到不同 bind，便于灰度与故障隔离，但站点数不等于监听数。

## 结论
My-OpenWaf 的双服务器架构通过控制平面与数据平面的清晰分离，实现了管理与防护的高内聚低耦合。控制平面专注配置与可观测性，数据平面专注高性能实时处理；两平面之间以「单调递增修订号 + 不可变快照 + 原子指针发布」这一条契约贯通，避免了共享可配态带来的锁竞争。快照驱动的热重载与按监听地址的漂移检测保证了零停机变更，Redis 发布订阅只传「该重载了」这一件事而不搬运序列化后的快照，把跨节点同步成本压到最低。

需要澄清的一处历史误述：站点解析不含 Trie，实现是哈希键加至多三级查找；这一事实已在「详细组件分析」中按代码重写。
