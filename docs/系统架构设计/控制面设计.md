## 简介
本文件面向 My-OpenWaf 的控制面设计，系统性阐述控制面的核心职责、架构与实现细节，重点覆盖：
- 管理端口与健康/就绪/状态/指标四个探针端点的设计与实现
- 路由注册机制、角色分组与中间件体系
- 生命周期管理与优雅停机
- 配置变更如何触发重载并广播到其它节点
- 控制面与数据面的交互边界

**划界**：本篇只写控制面自身的装配与探针语义。快照在双平面之间的角色见 [快照机制](快照机制.md)，配置层热重载与迁移见 [热重载系统](../配置管理系统/热重载系统.md)，管理端点的逐条契约见 [管理 API 系统](../管理 API 系统/管理 API 系统.md)。

## 架构总览
控制面与数据面在进程内共享同一份快照持有者，但写入权只属于控制面。控制面永不下发「新配置内容」给数据面，只把「配置代次变了」这件事通过修订号与 Redis 事件传达。

| 层 | 控制面承载 | 职责 | 与数据面的边界 |
|---|---|---|---|
| 接入层 | Hertz + 全局中间件 | TLS、安全头、请求 ID、认证鉴权 | 不与数据面共享端口与中间件链 |
| 领域层 | `admin/<域>` 子包 | 参数校验、业务写入、只读聚合 | 领域 handler 不 import `internal/app` |
| 契约层 | `Dependencies.Reload` | 把写库动作兑换为一次重载 | 数据面不订阅数据库，只订阅 `Holder` |
| 视图层 | `snapshot.Holder` | 原子发布，双平面共读 | 控制面写代次，数据面只读 |
| 观测层 | `/metrics`、`/status`、Realtime | 聚合数据面指标与库内统计 | 读取而非干预 |
| 编排层 | `lifecycle.Manager` | 站点监听器的增删重启 | 由 reload 链驱动，不由请求驱动 |

| 外部实体 | 与控制面的交互 | 入口 | 判定依据 |
|---|---|---|---|
| 系统管理员（浏览器） | 提交配置、查看仪表盘 | `/api/v1/*` + SPA 静态资源 | router.go:109-140 |
| 自动化脚本 | 以 API Key 调用 | `Authorization: Bearer {api_key}` | middleware.go:95-124 |
| Prometheus | 抓取指标 | `GET /metrics` | server.go:1056 |
| 容器编排 / 负载均衡 | 存活与就绪探针 | `GET /healthz`、`GET /readyz` | health.go:46-66 |
| 同级 WAF 节点 | 接收重载广播 | Redis 频道 `openwaf:config:reload` | pubsub.go:16 |
| ACME 签发方 | 拉取 HTTP-01 应答 | `/.well-known/acme-challenge/:token` | router.go:425-436 |
| 上游源站 | 仅状态探测与连通性检查 | `Upstreams` 依赖注入 | server.go:1088 |

## 详细组件分析

### 管理端口与探针端点
管理服务器在 `AdminBind` 上启动，四个探针绕过 `AuthMiddleware`——它们注册在 `h` 上而不是 `/api/v1` 组上（server.go:1053-1056），因此容器探针不需要携带凭据。

| 端点 | 方法 | 语义 | 判据 | 位置 |
|---|---|---|---|---|
| `/healthz` | GET | 存活 | `Alive()` 恒真 | health.go:29-55 |
| `/readyz` | GET | 就绪 | 快照非 nil ∧ `ready()` ∧ DB Ping 成功 | health.go:32-44 |
| `/status` | GET | 运行时状态 JSON | 九字段快照 | health.go:75-105 |
| `/metrics` | GET | Prometheus 文本 | 含 `owaf_cache_*` 缓存族 | server.go:1056、metrics.go:532-550 |
| `/api/v1/health` | GET | 认证前的管理侧健康检查 | 位于鉴权白名单 | router.go:94、middleware.go:45-52 |

`ready` 回调被装配两次：先设为 `lm.Ready()`（server.go:597），随后在令牌管理器构造完成后覆盖为 `lm.Ready() && tokenMgr.Ready()`（server.go:629）。语义是：持久化 JWT 黑名单若加载失败，实例不得对外声明自己已可接收需鉴权流量。`/status` 的 `sites` 与 `listeners` 分别按站点 ID 去重与按 `bind` 去重统计，两者不相等属正常（一个监听地址可承载多站点）。

### 路由分组与角色模型
`RegisterRoutes` 把端点分成三档角色组，全部挂在 `/api/v1` 之下。实测端点总数 217 个：GET 100、POST 117、PUT 0、DELETE 0——所有更新与删除都以 POST 加语义后缀表达（如 `/api-keys/:id/delete`），以此简化反向代理与 CORS 配置。

| 分组 | 允许角色 | 注册区间 | 典型端点 |
|---|---|---|---|
| 免鉴权 | — | router.go:94-107 | `/api/v1/health`、`auth/login`、`auth/refresh`、`auth/logout` |
| `readGroup` | admin、operator、readonly | router.go:124-254 | `GET /sites`、`GET /certificates`、`GET /policies` |
| `opsGroup` | admin、operator | router.go:255-371 | 站点/规则创建更新、事件处置 |
| `adminGroup` | admin | router.go:372-417 | `backup/import`、`redis-config`、`admin-users/*`、`cve-rules/*` |
| 旁路 | — | router.go:418-437 | `pow.wasm`、`realtime/ws`、ACME challenge |

只读类里存在一个刻意例外：`POST /certificates/parse` 被放进 `readGroup`（router.go:138），因为它只解析用户提交的 PEM 文本，不触碰库存私钥、无副作用。高危的备份导入除触发 `reload` 外，还额外使 CVE/OWASP 读快照失效并吊销全部访问会话（router.go:381-388）。

### 中间件链与执行顺序
全局只挂两个中间件（`SecurityHeaders`、`AccessLog`），鉴权与角色是分组级 `Use`，因此探针天然不受认证影响。

| 序 | 中间件 | 挂载范围 | 职责 | 失败响应 |
|:--:|---|---|---|---|
| 1 | `SecurityHeaders` | 全局（router.go:91） | nosniff/DENY/Referrer-Policy/CSP；`/api/v1/` 追加 `no-store`；`c.Next()` 后按快照补 HSTS/XSS/HPKP | 不拦截 |
| 2 | `AccessLog` | 全局（router.go:92） | UUID `X-Request-ID`，记录方法/路径/状态/耗时/认证方式 | 不拦截 |
| 3 | `AuthMiddleware` | `/api/v1`（router.go:110） | JWT 优先，失败回退 API Key | 401 或 503 |
| 4 | `RequireRole(...)` | 各角色组 | 比对 `auth_role` 与允许集合 | 403 |

`SecurityHeaders` 在 `c.Next()` 前后各写一次 `Cache-Control: no-store`（middleware.go:177-183），是因为下游 handler 可能在响应阶段重置该头；HSTS、XSS 防护与 HPKP 三项取自快照配置，因此控制面自身的响应头策略与站点策略共用同一份配置视图（middleware.go:184-192）。

### 跨节点同步与回环抑制
`ConfigSync` 以 `sourceID`（8 字节随机十六进制）标记消息来源，订阅端遇到 `event.SourceID == cs.sourceID` 直接丢弃，避免自己发布的通知把自己再重载一遍（pubsub.go:114-116）。发布带 2 秒超时，失败只记告警不回滚本地重载——本地一致性优先于跨节点通知。`NewConfigSync` 在 client 为 nil 时返回 nil，因此无 Redis 部署下整条广播链自动降级为单节点。

## 性能考虑
- 探针实现保持轻量：`/healthz` 无 IO，`/readyz` 只做一次 `sqlDB.Ping()` 与一次原子加载，适合高频容器探针而不引入数据库压力放大。
- `/status` 的站点与监听计数需要遍历当前快照 map（health.go:83-93），因此该端点的成本随站点规模线性增长，不宜作为毫秒级探针使用。
- 数据面指标由原子计数承载，控制面通过注入的 `dpmetrics.Metrics` 读取（server.go:1075），读取路径不加锁。
- 仪表盘类聚合走 `RedisKV` 缓存，配置广播走低频 Pub/Sub，两者都不进入请求热路径。
- 中间件里 UUID 生成用于每次管理请求，管理面 QPS 远低于数据面，此处成本可接受；数据面另用更快的 `dpreqid.FastRequestID()`（handler.go:56）。

## 结论
控制面以一个独立的 Hertz 实例承载全部管理语义：四个免鉴权探针保证编排系统能在配置未就绪时正确摘除实例；三档角色分组把「读、运维、高危」分离到注册期而非 handler 内部；写路径统一收敛到注入的 `Reload` 回调，使「落库 → 递增修订号 → 重建快照 → 原子发布 → 调谐监听器 → 跨节点广播」成为唯一一条生效链路。控制面从不向数据面推送配置内容，只推进代次——这是本架构最重要的约束。
