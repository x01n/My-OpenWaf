## 简介
阻断是判定之后的**动作落地层**：阶段链只产出 `action.Result`，本模块负责把它变成「断连、响应页、还是放行」。它由两部分组成：

- **零响应阻断**：`internal/waf/drop` 直接关闭 TCP 连接，不产生任何 HTTP 响应，是严重度最高（`TerminalPriority` 90）的处置
- **响应式阻断**：`internal/waf/pages` 按四级回退渲染拦截页、维护页、挑战页与上游错误页

实测澄清三点常被写错的事实：**仓库中不存在 `drop-policy` 前端页面**（配置入口在 `captcha/` 页的 detection 域覆盖卡，策略读写另有 REST 接口）；**代码中没有 `X-WAF-Action` 响应头**，对外只有 `X-Request-ID` 与降级标记 `X-OWAF-Drop-Degraded`；**阻断页模板只注入请求 ID 与状态码**，规则 ID、阶段名、命中描述一律留空，避免向客户端泄露判定细节。

## 详细组件分析

### 零响应执行器
`Execute` 的三步顺序是刻意的：先 `SetLinger(0)` 再 `Close`，让内核发 RST 而不是 FIN，避免客户端看到半开连接；只有关闭成功才记统计与告警（drop.go:47-72）。

```go
// internal/waf/drop/drop.go:51-56
rST := func() error {
	if tcp, ok := conn.(*net.TCPConn); ok {
		_ = tcp.SetLinger(0)
	}
	return conn.Close()
}
```

日志采样阈值为「前 16 条全打，之后每 1024 条打一条」，攻击期不会把日志刷满（drop.go:74-76）。

| 统计字段 | 计数来源（`DropReason.Source`） | 说明 |
|---|---|---|
| `TotalDropped` | 所有来源 | 进程内累计，`ResetStats` 可清零 |
| `DroppedByBot` | `bot` | — |
| `DroppedByCVE` | `cve` | — |
| `DroppedByRule` | `rule` **与** `ip_reputation` | 两类合并计同一桶 |
| `DroppedOther` | 其它任意值 | — |
| `LastDropTime` | 最近一次断连时间 | `atomic.Value` |

实测口径注意：数据面传入的 `Source` 是阶段名（如 `bot_detection`、`cve_detection`、`owasp_default`、`ip_reputation`），而 `recordStats` 只识别 `bot`/`cve`/`rule`/`ip_reputation` 四个字面值，因此除 `ip_reputation` 外其余来源都落进 `DroppedOther`；落库的 `drop_events.source` 则是原始阶段名（handler.go:733-741、drop.go:78-91）。内存统计与数据库聚合不能直接互相核对。

### 策略配置与继承
策略以 JSON 存在 `SystemSettings` 的 `drop_policy` 键里，四个字段与 `core.DropConfig` 一一对应。

| 配置项 | 类型 | 默认 | 载体 | 证据 |
|---|---|:--:|---|---|
| `enabled` | bool | `true` | `drop_policy` | config.go:60、protect/drop/drop.go:18 |
| `bot_score_threshold` | int | 80 | `drop_policy`，与 `bot_settings.score_threshold` 双向同步 | config.go:61、bot/bot.go:257-261 |
| `cve_auto_drop_critical` | bool | `true` | `protection`（同时镜像进 `drop_policy`） | config.go:62、protection.go:50 |
| `cve_auto_drop_high` | bool | `true` | `protection`（同时镜像进 `drop_policy`） | config.go:63、protection.go:51 |

优先级链是：`drop_policy` 设置行 > `MY_OPENWAF_DROP_ENABLED` / `MY_OPENWAF_DROP_BOT_THRESHOLD` 环境变量与逐键覆盖 > `DefaultDropConfig`。环境变量只在启动期落进 `rt.Config.Drop` 作为兜底，reload 时 `loadDropPolicy` 重新读设置行覆盖它（config.go:419-427、server.go:457、server.go:659-661）。`MY_OPENWAF_DROP_ENABLED` 只认字面 `false`，其它任意值都是「不关闭」（registry.go:384-388）。

站点级三态：站点表没有任何 drop 专属字段，`*bool` 三态列（如 `owasp_enabled`、`cve_enabled`、`bot_protection_enabled`、`rate_limit_enabled`）决定的是「哪个能产出 Drop 的阶段入链」，nil = 继承全局（site.go:60-91、build.go:711-760）。唯一能由站点关掉自动升 Drop 的路径是把 `cve_action` 覆盖为 `observe`，此时合并阶段会显式清掉两个 auto-drop 开关（build.go:737-746）。

### 事件追踪与统计
`DropEvent` 与 `SecurityEvent` 是两条独立记录：前者专供 Drop 面板，后者覆盖所有命中。二者都在 drop 成功分支同批写入，状态码一个记 0（无响应）一个由访问日志记 0。

| 字段 | 表 | 来源 | 备注 |
|---|---|---|---|
| `site_id` | `drop_events` | `rt.Site.ID` | 站点维度过滤键 |
| `client_ip` | `drop_events` | 解析后的客户端 IP | 字符串存储，支持 IPv6 |
| `source` | `drop_events` | `result.Action.Phase` | 阶段名，非执行器分桶值 |
| `rule_id` | `drop_events` | `RuleIDStr` | 内置规则带前缀，如 `owasp:sqli:001` |
| `detail` | `drop_events` | `MatchDesc` | 长度上限 512 |
| `status_code` | `security_events` | 成功为 0，降级为 403 | 用于区分两种结局 |

聚合口径：`Stats24hBySite` 用一条 `SUM(CASE WHEN source = ? ...)` 产出总数与四类分来源计数；`DeleteOlderThan` 以 5000 为一批分批删除，降低大表锁竞争（drop_event.go:156-208）。计数缓存会在每次直接写入或批量提交后按前缀失效，保证列表总数与详情一致（drop_event.go:26-32）。

## 性能考虑
- Drop 跳过 HTTP 响应生成与上游转发，是四种终端动作里开销最小的一种
- `SetLinger(0)` 让连接立刻释放，不进入 `TIME_WAIT` 堆积
- 告警与统计全用原子量与采样阈值，断连风暴期间不引入锁竞争（drop.go:61-76）
- 模板解析失败即走字符串兜底页，不做二次解析（block.go:190-195）
- 事件写入异步批量，队列容量与批量大小可调；容量吃紧时表现为「慢速宽限」而非丢请求
- 自定义 HTML 越大，模板解析成本越高，拦截页应保持精简

## 故障排查指南
| 症状 | 判据 | 处置 |
|---|---|---|
| 判定 drop 但客户端收到 403 | 响应头 `X-OWAF-Drop-Degraded: h2-h3-no-stream-reset` | 属协议限制，h2 当前恒走降级分支 |
| Drop 统计全为 0 | 执行器 `Enabled()` 是否为假 | `MY_OPENWAF_DROP_ENABLED=false` 会关掉 |
| 面板数字与内存统计不符 | 两侧 `source` 口径不同 | 库中存阶段名，执行器只认四个短名 |
| 拦截页空白或默认样式 | `block_html` / `DefaultBlockHTML` / `BlockPage` 是否为空 | 按四级回退逐级检查 |
| 模板变量不显示规则 ID | 属预期 | 渲染只注入 RequestID 与状态码 |
| 站点改了 `block_status` 没变 | 仅当结果为 403 时覆盖生效 | 429 等状态码不受该字段影响 |
| 事件表膨胀 | 归档任务是否运行 | `DeleteOlderThan` 分批 5000 删除 |
| 保存策略报 reload failed | 返回体含 `policy` 字段 | 配置已落库，重载失败需查快照构建日志 |

## 结论
阻断层的价值在于把「判定」与「落地」解耦：阶段不需要知道连接能否关闭、页面来自哪一级模板，只需给出 `action.Result`。本模块的两个关键设计是零响应路径的 `SetLinger(0)` 与协议不可触达时的 403 降级，以及响应页对内部字段的强制脱敏。

已知遗留项：`DropExecutor` 的分桶字面值与数据面传入的阶段名不一致，导致内存统计的 bot/cve/rule 三桶长期为空；`useDropPolicy` 系列 hook 已就绪但无页面消费者。建议后续把来源值统一为阶段名常量，并在前端补一个策略编辑面板。

### 术语
- **零响应阻断**：不发送任何 HTTP 响应即关闭连接，访问日志状态码记 0
- **降级阻断**：判定为 Drop 但拿不到可关闭的连接时，改写为 Intercept 返回 403
- **四级回退**：站点 HTML → 全局 HTML → 外观配置模板 → 内嵌页 → 字符串兜底
- **协议守卫**：`InboundProtocolGuard`，负责在多协议/多层包装下找到能安全触碰的裸 TCP 连接
