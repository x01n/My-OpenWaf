## 简介

本篇只讲 `internal/waf/ratelimit/ratelimit.go` 中的 `RateLimiter`：一个进程内的固定窗口计数器。它是 Redis 滑动窗口不可用时的默认后端，也是单节点部署的推荐形态。选取该实现的理由有三点：

- 零外部依赖，判定路径不产生网络往返，尾延迟与请求处理线程绑定。
- 与 `RedisRateLimiter` 共享同一个 `RateLimiterBackend` 契约（`ratelimit.go:10-17`），装配层可在运行时互换两者而无需重建引擎。
- 参数非法时采取「整体停用」而非「全部拦截」的失效保护，避免零配额被解读成人为 429。

本篇覆盖：窗口结构与原子计数、`Allow`/`Increment`/`IsOverLimit` 的判定语义差异、`cleaner` 协程的回收粒度、无效参数的失效保护路径、配置来源与热重配，以及与滑动窗口的边界。计数键的真实构成是 `bind|siteID|归一化 Host|clientIP` 四段而非「IP + Host」，这一点在「限流键的构成」一节展开。

## 详细组件分析

### 结构体与并发保护

窗口映射与配置参数由两把不同的锁分别守护，这是实现里最容易读错的一点。

| 字段 | 类型 | 保护方式 | 写入点 | 读取点 |
|------|------|----------|--------|--------|
| `mu` | `sync.Mutex` | 互斥 | 窗口新建 | `Allow`、`Increment`、`IsOverLimit`、`cleaner` |
| `configMu` | `sync.RWMutex` | 读写锁 | `SetEnabled`、`Reconfigure` | `Enabled`、`Allow`、`Increment`、`IsOverLimit` |
| `windows` | `map[string]*window` | `mu` | `Allow`、`Increment`、`cleaner` | 同上 |
| `windowS` / `maxReqs` | `int64` | `mu` 取值，`configMu` 提交 | `Reconfigure` | `Allow` 等一次读快照 |
| `enabled` | `atomic.Bool` | 原子 | `SetEnabled`、`Reconfigure` | 各判定入口 |
| `stopCh` | `chan struct{}` | 关闭信号 | `Close` | `cleaner` |
| `closeOnce` | `sync.Once` | 幂等 | `Close` | `Close` |

`Allow` 的关键设计是：先在 `configMu` 读锁下一次性取到 `enabled`、`windowS`、`maxReqs` 三项（`ratelimit.go:100-104`），再在 `mu` 下完成窗口查建并立即解锁，最后的自增走 `atomic.Int64`（`:116`）。因此临界区只覆盖 map 操作，计数完全无锁。`TestRateLimiterReconfigureAndAllowDoNotExposePartialConfig` 以 2000 轮「先置非法再恢复」与并发 `Allow` 交叉执行，验证读取到的永远是完整一致的参数三元组（`ratelimit_extra_test.go:143-159`）。

### 限流键的构成

`RateLimiter` 自身不产生键，键由调用方构造。真实构成是四段（`phases.go:63-70`）：

| 键段 | 取值 | 为空时的表现 | 隔离目的 |
|------|------|--------------|----------|
| `bind` | 监听器绑定地址，如 `:443` | 空串，键以分隔符开头 | 同站点在不同监听端口各有一份额度 |
| `siteID` | 站点主键十进制串 | `0` | 通配兜底站点不与显式 host 站点互挤配额 |
| 归一化 Host | `snapshot.NormalizeMatchHost` | 空串 | 大小写、首尾空白、端口差异不得拆桶 |
| `clientIP` | `net.IP.String()` | `nil` 时写空串 | 客户端维度 |

Host 归一化只做三件事：小写化、去首尾空白、在末冒号后全是数字时剥离端口（`snapshot.go:409-435`）。数据面与规则阶段共用同一构造函数：`reqRateLimitPhase` 直接调用（`phases.go:320`），数据面经 `rateLimitKey` 转调（`handler_support.go:355-357`），CC 规则的 `ccRateKey` 亦同源（`matcher.go:107-109`）。

### 窗口状态迁移

单个键的窗口在进程内只有三种状态，迁移条件全部由「到期秒」与当前秒比较决定。

```mermaid
stateDiagram-v2
    [*] --> 无窗口 : 首次访问该键
    无窗口 --> 活跃窗口 : expiry = now + windowS，count 置 1
    活跃窗口 --> 活跃窗口 : now < expiry，count.Add(1)
    活跃窗口 --> 已过期 : expiry <= now
    已过期 --> 活跃窗口 : 下一次 Allow/Increment 重建窗口
    已过期 --> [*] : cleaner 每 30 秒删除
    活跃窗口 --> [*] : Close 触发 stopCh，协程退出后由 GC 回收
```

迁移的判定细节如下表，其中「已过期但仍在 map 中」是正常中间态，由下一次访问就地重建，而非由清理协程负责。

| 状态 | 判定条件 | 触发点 | 是否计数 |
|------|----------|--------|:--------:|
| 无窗口 | map 中不存在该键 | `Allow` :110、`Increment` :134 | 建窗后计数 |
| 活跃窗口 | `expiry > now` | 同上 | 是 |
| 已过期（滞留） | `expiry <= now` 且尚未被 `cleaner` 扫到 | `IsOverLimit` :156-161 | 判定仍读旧计数 |
| 已删除 | `cleaner` 遍历删除 | `cleaner` :185-189 | 否 |

`IsOverLimit` 是唯一不重建窗口的入口，因此它可能对已过期但未被清理的窗口返回「超限」。这一保守偏差只在错误率限流链路上出现，且下一次判定即会因窗口重建而消失。

### Increment 与 IsOverLimit 的语义差异

两者常被误认为同一判定的读写两面，实际存在三处差异。

| 维度 | `Increment` | `IsOverLimit` |
|------|-------------|---------------|
| 是否改变计数 | 是，自增后返回 | 否，只读 |
| 比较口径 | 无比较 | `count > maxReqs`，严格大于 |
| 窗口缺失时 | 重建窗口并计 1 | 返回 `false` |
| 参数非正时 | 返回 0，不建窗 | 返回 `false` |
| 停用校验项 | 只看 `enabled` 与 `windowS` | 只看 `enabled` 与 `maxReqs` |
| 主要调用方 | `botPhase.behaviorScore`、错误率累加 | 错误率前置拦截 |

差异的直接后果：`Allow` 用 `<=` 放行配额个请求，`IsOverLimit` 用 `>` 判定超限，两者在同一配额下的触发点相差一个请求。`ratelimit_extra_test.go` 中配额 2 时第 3 次 `Allow` 之后 `IsOverLimit` 才为真（`:39-49`），配额 3 时 2 次请求仍判为未超限（`:28-37`）。

### 清理协程与内存上界

`cleaner` 以 30 秒为固定周期扫描整张映射，删除 `expiry <= now` 的窗口；当映射长度归零时重建空 map，以释放底层数组容量（`ratelimit.go:175-196`）。`Close` 通过 `sync.Once` 关闭 `stopCh`，重复调用安全（`ratelimit.go:164-173`、`ratelimit_extra_test.go:135-141`）。

| 参数 | 取值 | 影响 |
|------|------|------|
| 扫描周期 | 30 秒，硬编码 | 窗口过期后最长滞留 30 秒 |
| 键的上界 | 周期内的不同 `(bind, siteID, host, ip)` 组合数 | 决定常驻内存规模 |
| 单窗口开销 | 一个 `window`（两个 `int64`）+ map 项 + 字符串键 | 与配额无关，远小于 Redis ZSET |
| 停用后行为 | 协程随实例存活直到 `Close` | 停用不清空映射，只停止写入 |

与 Redis 实现相比，本实现的内存规模与「活跃键数」成正比而与配额无关，Redis 侧则两者都相关。`DynamicRateLimiter.Swap` 在替换后端时关闭旧实例，因此运行期切换会把旧映射整体丢弃（`dynamic.go:23-32`）。

## 性能考虑

| 问题 | 优化手段 | 效果与代价 |
|------|----------|------------|
| 锁竞争 | 参数读取用 `configMu` 读锁，映射操作只在 `mu` 下进行 | 临界区只覆盖 map 查找与新建 |
| 计数开销 | `window.count` 为 `atomic.Int64`，自增在解锁后执行 | 高并发下无原子争用以外的开销 |
| 参数撕裂 | 三元组在同一次 `RLock` 下读取 | 代价是多一次读锁 |
| 键基数膨胀 | 30 秒周期清理 + 空映射重建 | 清理粒度粗于窗口粒度，最长滞留 30 秒 |
| 边界突发 | 无内建平滑 | 固定窗口在窗口切换处最坏放过约 2 倍配额 |
| 协程泄漏 | `Close` 幂等关闭 `stopCh`，`ticker` 随 `defer` 停止 | 实例必须显式 `Close`，`Swap` 已代为处理 |

边界突发的量化例子：窗口 60 秒、配额 300 时，在第 59 秒与第 61 秒各打满 300 次请求，任意 60 秒滑动区间内实际通过 600 次。若业务对峰值平滑度敏感，应缩短窗口（例如 10 秒 / 配额 50）使边界误差按比例下降，而不是引入 Redis 往返。

## 结论

`RateLimiter` 把「固定窗口」这一经典算法收敛到不到两百行代码里，并用两把锁的分工换取热路径的低开销：参数三元组一致、计数无锁、映射有界。它的三条判定入口各有口径——`Allow` 用不大于配额放行、`Increment` 只自增、`IsOverLimit` 用严格大于判定——混用会得出与实际相反的阈值。作为默认后端与 Redis 缺失时的落点，它在整个速率限制体系中的角色是「基线」，而不是「简易版」。
