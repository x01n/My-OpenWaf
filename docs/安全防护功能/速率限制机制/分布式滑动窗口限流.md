## 简介

本篇只讲 `internal/waf/ratelimit/redis.go` 中的 `RedisRateLimiter`：以 Redis 有序集合承载滑动窗口、以三条 Lua 脚本保证单往返原子性的分布式限流后端。它与本地固定窗口实现共享 `RateLimiterBackend` 契约，由 `DynamicRateLimiter` 在运行时择优注入，因此 Redis 是**可选**依赖而非前置条件：客户端为 `nil` 时构造函数直接返回 `nil`，装配层随即落回本地实现。

本篇覆盖的内容按风险从高到低排列：

- 窗口边界的精确定义与它与「配额」之间的比较口径差异（`Allow` 与 `IsOverLimit` 相差一个请求）。
- 三条 Lua 脚本的逐指令语义、单键约束与集群可用性。
- 时间来源全部取自 WAF 节点时钟，因而存在的时钟漂移影响与缓解手段。
- Redis 报错与超时构成的三条独立失败路径，以及它们的共同取向：失败即放行。
- ZSET 的规模上界，以及 `Allow` 路径与 `Increment` 路径在上界上的本质区别。
- TTL 计算单位与窗口参数不一致造成的键滞留问题，这是键基数上限的主导因素。

计数键的真实构成是 `bind|siteID|归一化 Host|clientIP` 四段（`phases.go:63-70`），旧文档所写的「IP + Host」已不成立；bot 行为分在此基础上追加 `|bot` 后缀（`phases.go:501-512`）。

### 窗口边界与脚本语义

滑动窗口的区间定义完全由脚本决定：`min_ts = now - window`，随后 `ZREMRANGEBYSCORE key -inf min_ts`。分数等于 `min_ts` 的成员会被删除，因此窗口是左开右闭区间 `(now-window, now]`。

| 指令 | 语义 | 在三条脚本中的出现 | 缺失后果 |
|------|------|--------------------|----------|
| `ZREMRANGEBYSCORE key -inf (now-window)` | 修剪窗口外成员 | 三条均有（`:84`、`:99`、`:110`） | 集合无界增长，计数永久偏大 |
| `ZCARD key` | 取当前窗口内事件数 | `:85`、`:102`、`:112` | 无法判定 |
| `ZADD key now now:rand` | 写入本次事件 | `:87`（条件）、`:100`（无条件） | 事件不计入 |
| `EXPIRE key (window+1)` | 续期整键 | `:88`、`:101`、`:111` | 空闲键永不回收 |
| `return 1 / 0` | 判定结果 | `:89`、`:91` | 上层无法区分 |

比较口径的差异是这套实现里最容易踩的一点：`Allow` 走 `count < limit` 才写入，故一个窗口内恰好通过 `limit` 个请求；`IsOverLimit` 走 `count > maxReqs` 才为真，故需先累积到 `maxReqs + 1` 个事件。两条路径相差一个事件。

```mermaid

    空集合 --> 未满 : ZADD 首个成员，count = 1
    未满 --> 未满 : count 小于 limit，继续 ZADD
    未满 --> 满载 : count 达到 limit
    满载 --> 满载 : ZREMRANGEBYSCORE 未剪掉成员，判定为拒绝
    满载 --> 未满 : 窗口滚动，过期成员被剪掉
    满载 --> 只读超限 : IsOverLimit 分支，count 大于 max 不自增
    只读超限 --> 未满 : 修剪后回落到阈值内
    未满 --> 空集合 : TTL 到期整键消失
    满载 --> 空集合 : TTL 到期整键消失
```

### 成员唯一性与碰撞风险

`ZADD` 的成员名是 `now .. ':' .. math.random(1, 1000000)`。同一毫秒内两次取到相同随机数时，成员名重复，`ZADD` 只更新分数而不新增成员，于是两个事件被计成一个。

| 同毫秒事件数 | 至少一次碰撞的近似概率 | 对判定的影响 |
|:------------:|:----------------------:|--------------|
| 10 | 约 0.005% | 可忽略 |
| 100 | 约 0.5% | 偶发少计一次 |
| 1000 | 约 39% | 显著少计，实际放过量高于配额 |
| 大于 1414 | 概率过半 | 随机空间 1e6 成为硬上界 |

这是设计上的取舍：随机后缀保证成员在跨毫秒场景下必然唯一，代价是同毫秒高并发时窗口会略微放松。对判定精度的要求若高于此，应缩短窗口或降低配额，使同毫秒事件数落回百位以内。

### TTL 单位不一致与键滞留

三条脚本都以 `redis.call('EXPIRE', key, window + 1)` 续期，而 `window` 传入的是毫秒值（`redis.go:132` 计算 `windowMs := windowS * 1000` 后作为 `ARGV[2]`）。`EXPIRE` 的单位是秒，于是实际 TTL 是「窗口毫秒数 + 1 秒」。

| 配置窗口 | 期望 TTL | 实际 TTL | 偏差倍数 |
|:--------:|:--------:|:--------:|:--------:|
| 10 秒 | 11 秒 | 10001 秒（约 2.78 小时） | 约 910 倍 |
| 60 秒 | 61 秒 | 60001 秒（约 16.67 小时） | 约 984 倍 |
| 300 秒 | 301 秒 | 300001 秒（约 3.47 天） | 约 997 倍 |

后果不是判定错误——修剪逻辑保证计数正确——而是内存滞留：一个键在最后一次写入后的整个 TTL 周期内都不会消失，即便该客户端早已停止访问。键基数因此取决于「TTL 周期内出现过的不同四元组数」，而不是「当前活跃客户端数」。默认请求窗口 60 秒（`protection.go:161`）意味着近 17 小时的滞留窗口。

### 时钟漂移

`now` 取自 WAF 节点的 `time.Now().UnixMilli()`（`redis.go:131`、`:157`、`:184`），Redis 自身的 `TIME` 从未被调用。这意味着窗口的时间轴由客户端节点定义，多节点部署时各节点写入的分数处于同一个 ZSET 中，却来自不同时钟。

| 场景 | 直接后果 | 对限流的影响 | 缓解 |
|------|----------|--------------|------|
| 节点 A 快 5 秒 | A 写入未来分数成员 | B 的 `now - window` 剪不掉它，窗口被拉长，判定偏严 | NTP 强制同步 |
| 节点 B 慢 5 秒 | B 的修剪下界偏早 | 有效成员被提前删除，判定偏松 | 同上 |
| 节点间偏差与窗口同量级 | 窗口边界随机漂移 | 配额越接近窗口长度，误差占比越大 | 放宽窗口或统一时钟源 |
| 节点时钟回拨 | 分数出现倒退成员 | 旧成员长期滞留直到被 TTL 回收 | 禁用闰秒回拨策略 |

由于三条脚本都不做单调性检查，任何时钟异常都表现为「计数偏移」而不是报错，因此不会触发失败放行路径，也就不会出现在 Redis 侧的监控里。排查时应优先比对节点与 Redis 服务器的时间差。

### 键基数与内存上界

ZSET 的规模上界由「哪条路径在写入」决定，两者差别极大。

| 路径 | 写入条件 | 单键规模上界 | 说明 |
|------|----------|--------------|------|
| `Allow` | 仅当 `count < limit` 时 `ZADD` | 不超过配额本身 | 满载后不再写入，集合被配额钳住 |
| `Increment` | 无条件 `ZADD` | 窗口内的真实事件数 | 与配额无关，可远超配额 |
| `IsOverLimit` | 不写入 | 只剪不增 | 只读 |

据此可给出估算口径（非实测值，按成员名与分数的典型 Redis 编码开销估算）：

| 场景 | 参数 | 单键估算 | 键数 | 总量估算 |
|------|------|----------|------|----------|
| 请求限流满载 | 配额 300 | 约 300 成员 | 活跃四元组数 | 成员数线性于配额 |
| 行为分高流量 | 窗口 60 秒、单键 100 QPS | 约 6000 成员 | 活跃四元组数 | 明显高于限流路径 |
| 键滞留 | 窗口 60 秒，TTL 约 16.7 小时 | 冻结当时的成员数 | TTL 周期内出现过的四元组 | 主导因素 |

控制内存的三个变量因此是：配额（钳住 `Allow` 路径）、窗口长度（同时决定修剪半径与 TTL 滞留）、以及键的四元组基数（`bind`、`siteID`、Host、IP 的笛卡尔组合）。降低 `siteID` 与 `bind` 维度不能省内存，因为那是隔离语义所需；真正有效的是缩短窗口、控制暴露面使无效 Host 不产生新键，以及在 IP 维度前做聚合。

### 与本地固定窗口的精度对照

| 维度 | 本地固定窗口 | Redis 滑动窗口 |
|------|--------------|----------------|
| 窗口对齐 | 整数秒，边界突变 | 毫秒滚动，无突变 |
| 最坏放过量 | 约 2 倍配额（相邻两窗） | 约配额 + 同毫秒碰撞误差 |
| 判定开销 | 一次锁 + 一次原子自增 | 一次 50ms 上限的往返 |

| 内存归属 | 本进程堆 | Redis 实例 |

## 性能考虑

| 问题 | 优化手段 | 效果与代价 |
|------|----------|------------|
| 每请求一次网络往返 | 单条 Lua 完成修剪、计数、写入、续期 | 往返从多次降到一次；尾延迟受 RTT 支配 |
| Redis 抖动拖垮主链路 | 50ms 上下文超时，超时即放行 | 可用性优先；代价是故障期间等于不限流 |
| ZSET 无界增长 | 每次调用先 `ZREMRANGEBYSCORE` | 集合规模被窗口与配额双重约束 |
| 空闲键长期滞留 | `EXPIRE` 续期 | 因单位不一致而远超预期，见「TTL 单位不一致」 |
| 热点键集中单分片 | 键含 `bind`/`siteID`/Host/IP 四段 | 天然分散；极端单 IP 刷全站仍会集中 |
| 脚本重复传输 | 脚本以包级变量一次性构造 | 由客户端负责缓存与回退，进程内只编译一次 |

选型建议以判定开销为主轴：单节点或同机房多节点优先本地固定窗口；确需跨节点共享额度时才引入 Redis，并把窗口设为不小于 10 秒，以免 50ms 超时在跨地域链路上频繁触发。

## 故障排查指南

| 症状 | 可能根因 | 排查动作 | 处置 |
|------|----------|----------|------|
| 配额很小却几乎不拦 | Redis 报错触发失败放行 | 比对 Redis 可用性与延迟 | 修复链路或改用本地窗口 |
| 打开 Redis 后限流明显变松 | 50ms 超时在跨地域链路上频繁命中 | 测 RTT，观察 P99 | 就近部署或缩短判定频次 |
| ZSET 键数量异常庞大 | TTL 单位不一致叠加高键基数 | `SCAN` 统计 `openwaf:request:rl:` 前缀 | 缩短窗口，收敛暴露面 |
| 实际放过量高于配额 | 同毫秒成员碰撞 | 检查单键 QPS 是否达千级 | 缩短窗口或降低配额 |
| 多节点判定不一致 | 节点间时钟漂移 | 比对各节点与 Redis 时间 | 统一 NTP |
| 切换 Redis 后短时流量突增 | `Swap` 后视图归零，旧键要等修剪 | 观察切换时刻 | 预期行为，错峰操作 |
| 行为分始终为 0 | `Increment` 报错返回 0，或 `rateMax` 非正 | 查 `phases.go:501-510` 前置条件 | 修正配额参数 |

`Scan` 之类的运维命令只用于观察，不要在限流路径上执行；`KEYS` 在生产实例上会阻塞。失败放行不产生日志，因此定位必须依赖 Redis 侧监控（延迟、拒绝连接、`EVALSHA` 错误计数）而非应用日志。

## 结论

`RedisRateLimiter` 用三条单键 Lua 脚本把滑动窗口压缩成一次往返，精度、可用性与实现复杂度之间取了明确的优先序：可用性最高，其次是跨节点一致性，最后才是判定精度。这一取舍集中体现在三处——报错一律放行、50ms 上限、成员随机后缀可能少计——以及一处客观缺陷：`EXPIRE` 拿到的是毫秒数值却按秒解释，使空闲键滞留时间被放大约千倍。把它当作「Redis 可用时的增强项」来部署，而不是当作强约束的额度控制器，才与该实现的实际能力相符。
