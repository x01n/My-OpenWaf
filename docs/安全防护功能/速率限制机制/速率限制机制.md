## 简介

本篇是「速率限制机制」域的总览，负责把分散在三篇子文档中的事实收敛为一份可对账的索引：

- 两套限流算法：本地固定窗口（`RateLimiter`）与 Redis 滑动窗口（`RedisRateLimiter`），由 `DynamicRateLimiter` 统一包装成可在运行时互换的后端。
- 三条计数链路：请求频率限制（引擎 `rate_limit` 阶段）、错误频率限制（数据面响应后旁路计数）、bot 行为分（复用请求限流后端但使用独立键后缀）。
- 一条与限流器无关的频次通道：CC 自定义规则编译出的 `cc_rate` 复合匹配器，自带内存窗口状态，不经 `RateLimiterBackend`。
- Redis 是**可选**依赖：客户端由 `redis.OptionalClient` 构造，地址为空或连通性探测失败时返回 `nil`，限流后端自动退化为本地实现，不存在「必须部署 Redis」的前提。
- 限流键的真实构成是 `bind|siteID|归一化 Host|clientIP` 四段，旧文档所写的「IP + Host」已不成立。
- 站点级限流字段是三态语义：`rate_limit_enabled` 为 `*bool`，`nil` 表示继承全局，非 `nil` 才允许覆盖窗口与配额。

需要特别澄清的命名冲突：`internal/waf/dynamic` 包是**动态混淆 / 响应信封加密**子系统，与「动态限流」无关；本域所说的运行时可替换后端位于 `internal/waf/ratelimit/dynamic.go`。

### 组件清单

| 组件 | 算法 | 状态载体 | 是否依赖 Redis | 可空 | 位置 |

### 后端契约

`RateLimiterBackend` 是本地与 Redis 两套实现共享的抽象，方法集固定为六个：`Enabled`、`Reconfigure`、`Allow`、`Increment`、`IsOverLimit`、`Close`（`ratelimit.go:10-17`）。两个具体实现另有 `SetEnabled`，该方法**不在接口内**，热重载路径不会调用它，只经 `Reconfigure` 一次性提交窗口、配额与开关三项。

## 详细组件分析

### 两种算法对照与选型判据

| 算法 | 状态存储 | 键构成 | 精度 | 降级行为 | 适用场景 |
|------|----------|--------|------|----------|----------|
| 本地固定窗口 | 进程内 map，值含 `atomic.Int64` 与到期秒 | `bind\|siteID\|host\|clientIP` | 窗口边界最坏可放过约 2 倍配额 | 无降级概念，本身就是降级目标；`nil` 接收者放行 | 单节点、无 Redis、可容忍边界突发 |
| Redis 滑动窗口 | ZSET，成员为「毫秒时间戳:随机数」，分数为毫秒时间戳 | 同上，外加 `openwaf:request:rl:` 前缀 | 逐请求滚动，无桶边界 | Redis 报错或 50ms 超时即放行（fail-open） | 多节点共享同一份额度 |
| CC `cc_rate` 匹配器 | 进程内 `ccRateSharedState`，按规则状态键分桶 | 与限流键同源（`ccRateKey`） | 固定窗口，但命中后可追加封禁时长 | 无外部依赖，不受 Redis 影响 | 按条件维度（路径、UA、头）精细限流 |

选型判据按下表顺序判定，任一条件命中即定型，不再评估后续条件：

| 判据顺序 | 条件 | 结论 |
|:--------:|------|------|
| 1 | 快照中存在多实例部署且需要共享配额 | 配置 Redis 地址，走滑动窗口 |
| 2 | 未配置 Redis 或连通性探测失败 | 自动本地固定窗口，无需改代码 |
| 3 | 需要按路径/UA/请求头等条件维度限流 | 用 CC 规则 `cc_rate`，与全局限流并存 |
| 4 | 只想压低错误率并快速拦截高错误来源 | 叠加错误率限流，独立后端与独立前缀 |

### 限流键的真实构成

`RateLimitKey` 依次拼接四段，段间以竖线分隔：监听器绑定地址、站点 ID、归一化后的 Host、客户端 IP 字符串（`phases.go:63-70`）。Host 归一化复用站点解析的同一函数，做小写化、去首尾空白与端口剥离（`snapshot.go:409-435`）。

| 键段 | 取值来源 | 为空时的键表现 | 隔离维度 | 引入动机 |
|------|----------|----------------|----------|----------|
| `bind` | `pipeline.RequestCtx.Bind` | 空串，键以竖线开头 | 监听端口/协议 | 同站点在 :80 与 :443 各有一份额度 |
| `siteID` | 站点主键 | `0` | 站点 | 通配兜底站点与显式 host 站点不得互挤配额 |
| 归一化 Host | `NormalizeMatchHost(ctx.Host)` | 空串 | 域名 | 大小写与端口差异不得拆桶 |
| `clientIP` | `RequestCtx.ClientIP` | 空串 | 客户端 | `nil` IP 走空串而非 panic |
| `|bot` 后缀 | `botBehaviorKeySuffix`（`phases.go:512`） | 不追加 | 行为分独立窗口 | 避免与 `Allow` 的计数重复 |

### 与 CC 规则频次限制的边界

CC 规则在快照构建期被编译为 `cc_rate` 复合匹配器，携带 `window`、`threshold`、`duration`、`duration_unit` 与派生的 `duration_seconds`（`build.go:1085-1091`）。它拥有独立的进程内状态 `ccRateSharedState`，与 `RateLimiterBackend` 无关，因此关闭全局限流不会影响 CC 规则计数。

`duration_unit` 的缺省口径是一处需要明示的陷阱：三处判定都接受空串，而空串按「分钟」换算，不是「秒」。

```json
[
  {
    "name": "高频路径拦截",
    "enabled": true,
    "action": "rate_limit",
    "conditions": [{ "target": "url_path", "operator": "prefix", "value": "/api/search" }],
    "window": 60,
    "threshold": 30,
    "duration": 5,
    "duration_unit": ""
  }
]
```

上述载荷的封禁时长是 300 秒而非 5 秒：`validCCDurationUnit` 与 `validCompoundDurationUnit` 均把空串列为合法值（`helpers.go:252-258`、`validate.go:114-121`），而 `ccDurationSeconds` 的 `""` 分支与 `default` 分支同样乘以 60（`matcher.go:1844-1855`）；快照侧 `normalizedCCDurationUnit` 的默认返回值也是 `minutes`（`build.go:1015-1024`）。要得到秒级封禁必须显式写 `"seconds"`。

## 性能考虑

| 问题 | 优化手段 | 效果与代价 |
|------|----------|------------|
| Redis 滑动窗口的 ZSET 随配额线性增长 | 每次脚本执行前 `ZREMRANGEBYSCORE` 修剪窗口外成员 | 内存上界约为「配额 × 成员大小」；高配额站点应缩短窗口而非放大配额 |
| 每次判定一次 Redis 往返 | 单条 Lua 完成修剪、计数、写入、续期，一次往返 | 网络往返从多次降为 1 次；代价是 50ms 超时后即放行 |
| 本地窗口键数随 IP 基数膨胀 | 30 秒周期清理到期窗口，映射清空后重建 | 内存与 CPU 折中；清理粒度粗于窗口粒度 |
| `Allow` 与 bot `Increment` 争用同一映射 | bot 使用 `|bot` 后缀独立键，且各自单次加锁后立即原子自增 | 锁临界区只覆盖窗口查找/创建 |
| 后端切换导致计数丢失 | 仅在客户端真实变化时 `Swap`，否则用 `Reconfigure` 原地改参 | `Reconfigure` 保留既有窗口，`Swap` 不保留 |
| 边界突发放过约 2 倍配额 | 需要平滑时改用 Redis 滑动窗口 | 精度换一次网络往返 |

数据面指标可用来验证限流效果：`Metrics` 提供请求总量、2xx/4xx/5xx 分档、WAF 拦截与观察计数，以及 10 秒环形缓冲的 QPS 估算（`metrics.go:14-28`、`64-77`、`112`）。`/metrics` 暴露在管理端口，不属于数据面。

| 配额明明很小却几乎不拦 | 键含 `bind` 与 `siteID`，同一 IP 经不同监听器或站点落在不同桶 | 用同一 `bind`、同一站点复测 | 按站点收敛配额 |
| 阈值实际减半 | bot 行为分与限流共用同一键 | 确认 bot 键带 `|bot` 后缀 | 属设计约束，勿改后缀 |
| 打开 Redis 后限流变松 | 单次调用 50ms 超时即放行 | 观察 Redis 延迟与慢日志 | 缩短 RTT 或回本地窗口 |
| 保存限流配置返回 400 | 窗口或配额为负，或启用时为零 | 对比 `validateRateLimitConfig` 三条判据 | 填正值 |
| 站点填了窗口但没生效 | 覆盖以 `rate_limit_enabled` 非 `nil` 为前提，且值需大于 0 | 检查站点三态是否为「继承」 | 显式覆盖启用 |
| 切换 Redis 后短时流量突增 | `Swap` 丢弃旧后端计数 | 观察切换时间点 | 预期行为，必要时错峰切换 |

## 结论

本域的实现把「限流算法」与「状态存储」解耦成六个方法的接口，再由装配层按 Redis 是否真实可用择优注入，因此 Redis 是增强项而非前提。三种计数通道各有归属：全局限流走引擎阶段，错误率限流走数据面旁路，CC 频次走规则匹配器自有状态，三者键语义同源但状态互不干扰。文档层面最容易出错的两点是限流键的四段构成与站点三态覆盖的前置条件，本篇已按代码逐处对齐；`duration_unit` 空串按分钟换算属于现存语义，任何改写都应显式写单位。
