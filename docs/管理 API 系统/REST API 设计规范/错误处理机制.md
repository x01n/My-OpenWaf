## 简介

本篇描述控制面错误如何产生、如何表达、如何被记录与如何恢复。控制面**没有专用错误类型体系**：所有错误都以单层 JSON 对象 `{"error": "<文本>"}` 表达，靠 HTTP 状态码区分语义，靠可选上下文字段（`retry_after_secs`、`remaining_attempts`）补充判定依据。

因此本篇的重点不是"有哪些错误类"，而是"哪些分支产出哪个状态码与哪段文本、日志里能看到什么、失败后系统怎么退"。载荷字段格式见[请求响应格式规范](请求响应格式规范.md)，端点条目见[API 端点参考](API 端点参考.md)。

控制面错误分支可穷举为五类，每类的判定位置与产出固定。

| 类别 | 判定位置 | 状态码 | 文本样例 |

| 授权不足 | `RequireRole` | 403 | `access denied: insufficient permissions` |

| 下游失败 | 处理器业务分支 | 500 | `token storage failed` |

### 内部判定码与响应码的分离

控制面错误使用标准 HTTP 码；数据面判定使用 1xxx 内部码，二者互不替换。内部码只进日志与指标，**不会发送给客户端**。

| 内部码 | 动作 | 描述 | 对应 HTTP |
|:------:|------|------|:---------:|
| 1000 | `drop` | TCP 立即断开，不发响应 | 无 |
| 1001 | `intercept` | WAF 拦截 | 403 |
| 1002 | `rate_limit` | 速率限制 | 429 |
| 1003 | `challenge` | JS 挑战 | 403 |
| 1004 | `captcha_challenge` | 图形验证码 | 403 |
| 1005 | `shield_challenge` | 5 秒盾 | 403 |
| 1006 | `chain_challenge` | 链式验证 | 403 |
| 1007 | `redirect` | 安全重定向 | 302 |
| 1008 | `observe` | 仅观察，放行 | 无 |
| 1009 | — | IP 信誉拦截 | 403 |
| 1010 | — | 防重放拦截 | 403 |
| 1011 | — | 机器人检测拦截 | 403 |
| 1012 | — | 维护模式 | 503 |
| 1013 | — | 响应升级 | 视配置 |
| 1014 | — | 文件上传拦截 | 403 |

### 错误日志与请求关联

`AccessLog` 为每条请求生成 UUID 并写入响应头 `X-Request-ID` 与上下文 `request_id`，响应后输出一条结构化日志，字段集合固定。

| 日志字段 | 类型 | 来源 | 用途 |
|----------|------|------|------|
| `request_id` | string | `uuid.NewString()` | 跨端关联主键 |
| `method` | string | 请求方法 | 定位动作类型 |
| `path` | string | 请求路径 | 定位端点 |
| `status` | int | 响应状态码 | 判定失败层 |
| `latency` | Duration | `time.Since(start)` | 性能与超时分析 |
| `auth` | any | 上下文 `auth_method` | 区分 jwt / api_key |
| `section` | string | `logger.New("admin")` | 模块归属 |

日志消息固定为 `request`，级别为 `Info`；失败响应不额外提高级别，判定依据全在 `status` 字段。登录尝试另有一张审计表，字段为 `username`、`ip`、`success`、`user_agent`、`created_at`，成功与失败都记录，且**不记录口令**。

### 错误恢复策略

恢复机制集中在认证链，遵循两条原则：**可退避的不改判语义**、**撤销必须整链**。

| 场景 | 策略 | 实现 | 副作用 |
|------|------|------|--------|
| 黑名单加载失败 | 1 秒退避重试，期间 `503` | `ensureBlacklistReady` | 不会永久拒绝认证 |
| 刷新仓储不可用 | 返回 `503` 而非 `401` | `auth.go:156-159` | 客户端保留当前访问令牌 |
| 刷新令牌并发轮换 | `Rotate` 条件更新失败即 `401` | `refresh_token.go:88-118` | 不清除共享 Cookie |
| 账号被删除时刷新 | 撤销整条轮换链 + 清 Cookie + `401` | `auth.go:175-181` | 后继令牌一并失效 |
| 登出 | 撤销整链，再按 Authorization 拉黑访问 JTI | `auth.go:243-290` | 撤销失败返回 `500` |
| 强制下线 | 移除会话 + 拉黑 + 撤销链（旧会话按账号全量撤销） | `auth_session.go:55-87` | 每步失败都有独立文案 |

### 调用侧错误处理约定

| 情形 | 调用侧动作 | 抛出的 `ApiError` |
|------|------------|-------------------|
| 本地令牌已被其他标签页更新 | 直接用新令牌重试 | 不抛 |
| 刷新成功且令牌一致 | 用新令牌重试一次 | 不抛 |
| 刷新成功但令牌已被替换 | 不重试业务请求 | `401 会话已变更，请重试` |
| 刷新返回未授权 | 清令牌并跳转 `/login` | `401 会话已过期，请重新登录` + `refresh_status` |
| 刷新服务不可用 | 保留原始 `401` 语义 | 原始状态码 + `refresh_status: unavailable` |
| 其他非 2xx | 取 `error` 字段 | 原状态码 + 原载荷 |
| 响应无 `error` 字段 | 兜底文案 | `请求失败: {status}` |
| 204/205 | 跳过 JSON 解析 | 不抛 |

## 性能考虑

错误路径本身不引入额外开销：状态码与文案在处理器分支内一次写入，`AccessLog` 仅在响应后输出一条日志。吊销类操作把多个写库步骤串成一次请求内完成，代价是失败时无法回滚，因此采用"首个错误上报、后续步骤继续执行"的口径，保证吊销覆盖面最大化而不是快速失败。

`CleanExpired(64)` 挂在登录与刷新成功路径上顺带执行，避免独立定时任务；批量上限固定 64，防止一次请求触发大范围删除。

## 结论

控制面错误处理的优点是**表达统一**（单层 `error` + 标准 HTTP 码）、**认证侧文案固定**（不泄露账号存在性）、**吊销语义完备**（整链撤销覆盖登出、强退、改密、删号四条路径），以及**认证依赖故障可退避而不失守**。

两点客观缺口：资源类 500 直接把仓库错误原文返回客户端；访问日志对所有状态码统一用 `Info` 级别，错误与成功在级别上不可区分，只能靠 `status` 字段过滤。前者属输出面收紧问题，后者属可观测性粒度问题，均需按当前需求决定是否处理。
