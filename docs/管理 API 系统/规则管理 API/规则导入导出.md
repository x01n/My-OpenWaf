## 简介

本篇只讲**规则的搬运**：把一组自定义规则从数据库里取出来（导出）、把一组规则写回数据库（导入），以及跨环境同步时两者如何配对。

三条实测边界决定了本篇的写法：

- **导出是全局的，不是按策略的**。`ExportRules` 调 `repo.List(0, 10000)`，一次拿完所有策略的规则（rule.go:396-405），导出文件名里的策略号只是前端标签（page.tsx:135）。
- **导入是整批事务，任一条失败即全批不落库**。校验在前、写入在后，且写入是一次 `BatchCreate` 事务（rule.go:426-455）。
- **单条导入上限 1000**。`maxImportedRules = 1000`（rule.go:20），超限直接 400，且被拒的批次不得触发 reload（rule_import_limit_test.go:41-59）。

CVE 与 OWASP 两类规则**没有专用导入导出端点**，只能通过 admin 的配置备份链路 `GET /api/v1/backup/export` / `POST /api/v1/backup/import` 整体搬运（router.go:381-388）。

### 导入侧的 GORM 默认值顶替

单条创建与批量导入对「显式零值」的处理并不对称，这是导入最容易踩的静默改写：

| 路径 | 绑定前 | 写入 | 结果 |
|---|---|---|---|
| `POST /rules` | `ApplyModelDefaults` 先填模型默认值（`admin/rule/rule.go:103`） | `CreateWithZeroDefaults` 回写被顶替的零值（`repository/rule.go:91-98`） | 显式 `false`/`0` 如实落库 |
| `POST /rules/import` | 无 | 裸 `tx.Create(&items)`（`repository/rule.go:24-28`） | GORM 把带 `default` 标签的零值当「未设置」并写入默认值 |

实测（本地 `gorm v1.31.2` + `Rule` 同标签模型，`priority:0`、`enabled:false` 批量插入）：结构体与库行都变成 `priority=100`、`enabled=true`，且 `zero_defaults.go:70-77` 的注释明确把这列为事故源。因此导入想表达「停用」或「抢在默认优先级之前」必须显式避开零值：`enabled` 想为假就先导入再单条更新，`priority` 想为 0 就改用 1。本篇只登记，不改代码。

### 校验失败行为表

导入的处理顺序是固定的七段（五段校验 + 一段写入 + 一段重载），每段的失败形态不同：

| 序号 | 校验 | 失败响应 | 响应额外字段 | 是否已写库 | 是否 reload |
|:---:|---|:---:|---|:---:|:---:|
| 1 | 请求体 JSON 绑定 | 400 | `error` 为绑定原文 | 否 | 否 |
| 2 | `rules` 非空、条数 ≤1000 | 400 | `no rules provided` / `too many rules (max 1000)` | 否 | 否 |
| 3 | 逐条策略存在 | 400 或 500 | 带 `index`；查询故障走 500 | 否 | 否 |
| 4 | 逐条 phase/pattern/action 归一 | 400 | 带 `index` 与中文原因 | 否 | 否 |
| 5 | 优先级冲突（批内 + 库存） | 400 或 500 | 仅 `error`：批内冲突在文案里给出两个下标，库存冲突给出冲突规则 ID | 否 | 否 |
| 6 | `BatchCreate` 事务 | 500 | `{error, imported:0, total:n}` | 回滚，零写入 | 否 |
| 7 | reload 失败 | 500 | `{error, imported:n, total:n}` | **是，已写入** | 已尝试 |

第 7 行是最需要警惕的：规则已经落库但快照未重建，返回值同时给出 `imported` 与 `total` 表明「已全部写入」，此时应修因后再 `POST /api/v1/reload`，不要重复导入。

## 性能考虑

- **1000 条上限来自数据库而非协议**：`BatchCreate` 走 `tx.Create(&items)`，绑定变量数随条数线性增长，SQLite 变量上限 2077 使 2100 条必失败，因此上限取 1000（rule_import_limit_test.go:9-16 的注释与断言）。
- **逐条 `PolicyExists` 是 N 次查询**：导入 1000 条即 1000 次 COUNT，前端分批不会减少总量，只会增加请求数。
- **导出用 10000 行上限换一次往返**：规则数超过 1 万时导出会静默截断，需改用备份端点。
- **优先级冲突检查在写入前完成**：批内用 map、库存用一次查询/条（rule.go:367-393），失败即零写入，避免「半批回滚」成本。
- **建议**：跨环境同步按策略拆分文件，单批控制在 200 条以内，导入前先跑一次 `/rules/validate`（见 [规则验证与测试.md](file://docs/管理%20API%20系统/规则管理%20API/规则验证与测试.md)）。

## 结论

规则的导入导出在实现上是「一条全表读 + 一条整批事务写」，简单但没有缓冲：导出忽略策略边界，导入忽略客户端传来的主键，中间所有语义差异都压在校验层。

- **成果**：本篇把五段校验、16 个字段的导入映射、备份侧 5 个规则切片整理成可核对表格，并用实测补了一条前端→后端契约断点（空串时间戳导致导入必失败，且现有测试无覆盖）。
- **原则落点**：KISS 体现为复用单条创建的 `normalizePersistedRuleConfig`，导入没有第二套校验实现；DRY 同样落在这一次复用上；SRP 让 `ExportRules` 只做读、`ImportRules` 只做校验与批写、reload 由注入闭包负责；YAGNI 表现为没有「增量导入」「按名去重」「导入预演」这类未实现能力——需要时应用 `POST /rules/validate` 逐条预检。
- **下一步**：若要修断点，最小改动是在前端 `handleImport` 里删除时间戳字段而不是改为空串；本篇不改代码，只在故障排查与问题登记中留痕。

### 跨环境同步流程

1. 源环境 `GET /api/v1/rules/export`，保存为 `owaf-rules-{policyId}.json`
2. 用 `jq` 删除 `id`、`created_at`、`updated_at`，并把 `policy_id` 改成目标环境的策略号
3. 目标环境先确认策略存在（`GET /api/v1/policies`）
4. `POST /api/v1/rules/import`，单批 ≤1000 条
5. 用 `GET /api/v1/sites/:id/rules` 复核目标站点生效策略下的规则
6. 若规则用了 30 项白名单之外的 kind，先按验证与测试篇的差集自检再决定是否替换
