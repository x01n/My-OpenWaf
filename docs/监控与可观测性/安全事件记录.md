## 简介
本文件面向安全事件记录系统，围绕事件采集、脱敏、异步批量写入、查询与统计、假阳性反馈与保留清理给出可核对的技术说明。

设计约束有三条来自实测：
- 数据平面热路径只做一次非阻塞通道发送，落库由单个 goroutine 在一个事务里完成，从根本上消除 SQLite 写锁竞争 [unified_writer.go:18-24](file://internal/observability/unified_writer.go#L18-L24)。
- 请求头、请求体、响应头、查询串与匹配片段都属于审计字段，写入前一律脱敏并截断，敏感键整体遮蔽，绝不落 `Authorization`、`Cookie`、`Set-Cookie`、API key 等原值 [access_log.go:173-180](file://internal/dataplane/access_log.go#L173-L180)、[sanitize.go:13-15](file://internal/dataplane/logredact/sanitize.go#L13-L15)。
- 事件不落主库而是落日志库 `rt.LogDB`，与配置库分库迁移 [server.go:354](file://internal/app/server.go#L354)、[migrate.go:126-139](file://internal/store/migrate.go#L126-L139)。

## 核心组件

### 统一写入器（UnifiedWriter）
- 四通道汇聚：安全事件与访问日志共用 `EventBufferSize`（默认 16384），丢弃事件与机器人评分共用 `DropBufferSize`（默认 8192）；批阈值默认 256，flush 周期默认 3 秒，单次取数上限 `drainLimit = 4 × BatchSize` [unified_writer.go:124-129](file://internal/observability/unified_writer.go#L124-L129)、[unified_writer.go:405-410](file://internal/observability/unified_writer.go#L405-L410)。
- 硬上限钳制：通道容量 1M、批大小 10000、flush 间隔 60s、慢速宽限 5m；越界回退默认或截断并打 WARN，不静默改写 [unified_writer.go:111-119](file://internal/observability/unified_writer.go#L110-L118)、[unified_writer.go:228-246](file://internal/observability/unified_writer.go#L217-L246)。
- 队列满语义：默认不是立即丢弃，而是「持续为满 30s 之内阻塞等待」，超过宽限或已关闸才计入丢弃；`SlowLogGraceDisabled` 才回到历史丢弃语义 [unified_writer.go:155-208](file://internal/observability/unified_writer.go#L155-L208)。
- 单事务落库：四类记录同一个 `db.Transaction`，每类各持一个 SAVEPOINT，某类失败只回滚到自身保存点；sqlite 方言走长期语句，其余方言回退 `CreateInBatches` [unified_writer.go:929-1005](file://internal/observability/unified_writer.go#L929-L1005)。
- Redis 双写：在落库前先推 Redis 列表 `openwaf:security_events` / `openwaf:access_logs`（LTRIM 到 99999）与 `openwaf:drop_events` / `openwaf:bot_scores`（49999），统一 7 天 TTL，单次调用 5 秒超时 [unified_writer.go:1094-1152](file://internal/observability/unified_writer.go#L1094-L1152)。
- 关停：先置 `closed` 闸门并关 `stopCh`，再在 8 秒排空预算 + 5 秒宽限内循环排空；超预算记录计入丢弃并打错误日志 [unified_writer.go:340-351](file://internal/observability/unified_writer.go#L340-L351)、[unified_writer.go:702-742](file://internal/observability/unified_writer.go#L702-L742)。
- 提交后按类型失效控制面 COUNT 缓存前缀（安全事件是 `se_count:v2`）[unified_writer.go:962-985](file://internal/observability/unified_writer.go#L962-L985)。

### 通用写队列（WriteQueue）
- 任务形态是 `func(tx *gorm.DB) error`，`Submit` 非阻塞、`SubmitWait` 阻塞等结果、`SubmitPriority` 入队并立即触发 flush，队列为 nil 时走 `runSynchronously` [write_queue.go:300-425](file://internal/observability/write_queue.go#L300-L425)。
- 默认容量 256、批大小 64、ticker 50ms；上限 1M 条 / 10000 批 [write_queue.go:104-131](file://internal/observability/write_queue.go#L104-L131)。
- 丢弃分两种原因计数：`full`（队列满）与 `closed`（已开始关停），告警按 10 秒节流 [write_queue.go:67](file://internal/observability/write_queue.go#L67)、[write_queue.go:236-262](file://internal/observability/write_queue.go#L236-L262)。
- `runWriteTransaction` 把驱动 panic 转成 error，单个写任务不会打断整个队列 [write_queue.go:264-287](file://internal/observability/write_queue.go#L264-L287)。

## 性能考虑
- 事务合并：四类记录共用一个事务，SQLite 写锁竞争从「每类一次」降到「每批一次」；sqlite 方言再经长期语句省掉重复 Prepare [unified_writer.go:929-1005](file://internal/observability/unified_writer.go#L929-L1005)、[sqlite_bulk_flusher.go:1-40](file://internal/observability/sqlite_bulk_flusher.go#L1-L40)。
- 批阈值 256 是实测调参结果，由 64 上调；`drainLimit = 4 × 256` 限制单事务体积 [unified_writer.go:122-128](file://internal/observability/unified_writer.go#L119-L125)、[unified_writer.go:405-410](file://internal/observability/unified_writer.go#L405-L410)。
- 背压取舍：默认 30 秒慢速宽限而不是立即丢弃，因为在 128 并发、400 万行日志库的实测中立即丢弃会丢掉约 51% 的访问日志；宽限只在数据库长期落后时生效 [unified_writer.go:155-177](file://internal/observability/unified_writer.go#L155-L177)。
- 读侧缓存：5 秒 COUNT 缓存覆盖 `security_events`/`access_logs`/`drop_events`，大结果集再叠一层 Redis 热缓存 [server.go:317-326](file://internal/app/server.go#L317-L326)、[security_event.go:109-140](file://internal/store/repository/security_event.go#L109-L140)。

## 结论
安全事件记录用「非阻塞入队 + 单事务批量落库 + 双写 Redis」把采集成本压离热路径，同时以逐字段脱敏与列裁剪保证审计可用性与体积可控；查询侧用精简列、5 秒计数缓存与 Redis 热缓存分层，写入侧用批阈值与宽限参数平衡延迟与丢弃。

三点务必如实理解：事件详情只在终止动作或 4xx/5xx 时采集；时间线只统计终止动作；清理周期是 24 小时而非每小时，且保留天数为 0 表示永久保留。建议在生产环境为 `openwaf_writer_dropped_total` 设告警，并把假阳性反馈闭环纳入规则调优流程。
