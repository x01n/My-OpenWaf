## 简介
事件归档系统负责可观测性数据的生命周期收尾：按保留期删除过期记录、在删除后做数据库维护、并保证删除动作不拖垮读写。

三条必须澄清的实测事实，旧文档普遍写错：
- 清理周期是 **24 小时**，由 `defaultArchiverIntervalSeconds = int64(24 * time.Hour / time.Second)` 定义，不是每小时 [archiver.go:56-57](file://internal/observability/archiver.go#L56-L57)。
- 归档器**启动时不预跑清理**：`loop` 用 `time.NewTimer` 等待第一个周期到期才执行「刷新配置 → 清理 → 库维护」三步，因此新进程上线后最早 24 小时才回收空间 [archiver.go:219-242](file://internal/observability/archiver.go#L219-L242)。
- 保留天数 `0` 的语义是**永久保留**，负值会被回退成 0 并打 WARN，而不是「立即清空」 [archiver.go:22-24](file://internal/observability/archiver.go#L22-L24)、[archiver.go:94-104](file://internal/observability/archiver.go#L94-L104)。

归档器不搬数据到冷存储，只做「删除 + 维护」，因此容量规划必须以保留天数为唯一旋钮。

### 清理与库维护
`cleanup` 对四类数据分别判 `days > 0` 后才构造 cutoff 并删除，四类互相独立，单类失败只记错误不中断其余类 [archiver.go:332-401](file://internal/observability/archiver.go#L332-L401)。威胁情报同步日志刻意复用 `DropEventDays`，注释明确理由是「同类运维辅助日志」 [archiver.go:186-193](file://internal/observability/archiver.go#L186-L193)、[archiver.go:387-400](file://internal/observability/archiver.go#L387-L400)。

### 分批删除的仓储实现
三个主表的 `DeleteOlderThan` 形态一致：以 `id IN (SELECT id ... LIMIT 5000)` 分批删，累计行数，不足一批即退出；安全事件与访问日志每批之间睡 50ms，访问日志还在进入循环前先失效指纹缓存与 COUNT 缓存 [security_event.go:410-432](file://internal/store/repository/security_event.go#L410-L432)、[access_log.go:856-880](file://internal/store/repository/access_log.go#L856-L880)、[drop_event.go:167-190](file://internal/store/repository/drop_event.go#L167-L190)。

`runArchiverDelete` 把仓储 panic 转成 error，避免单表异常杀死整个归档循环 [archiver.go:137-144](file://internal/observability/archiver.go#L137-L144)。

### 归档循环状态机

## 性能考虑
- 分批 + 睡眠：5000 行一批、批间 50ms，把长事务拆成短事务，给写入侧的批事务留出锁窗口 [security_event.go:410-432](file://internal/store/repository/security_event.go#L410-L432)。
- 不做每日 VACUUM：注释明确「被删除的页仍可被 SQLite 复用」，无条件 `VACUUM` 会带来整库重写成本，因此改用两次 `wal_checkpoint`，其中 `TRUNCATE` 专门回收长尾 WAL [archiver.go:452-470](file://internal/observability/archiver.go#L452-L470)。
- 维护有超时：30 秒 `context` 上限，驱动不响应时不会阻塞进程关停 [archiver.go:66-68](file://internal/observability/archiver.go#L66-L68)。
- panic 隔离：删除与维护都包了 `recover`，单表异常不影响循环存活 [archiver.go:137-144](file://internal/observability/archiver.go#L137-L144)、[archiver.go:413-417](file://internal/observability/archiver.go#L413-L417)。
- 周期与保留期联动：周期越长，删除后的空间释放越滞后；周期越短，扫描与 `ANALYZE` 开销越频繁。24 小时是当前折中，可通过 `db_optimize_interval_hours` 调整 [archiver.go:56-57](file://internal/observability/archiver.go#L56-L57)、[archiver.go:313-329](file://internal/observability/archiver.go#L313-L329)。

## 结论
事件归档系统是一个刻意保持简单的收尾组件：一个协程、一个定时器、四类删除目标、三段方言维护命令，配置只从 `system_settings` 读，删除只按 `created_at` 判。24 小时周期与 5000 行分批是在「及时回收」与「不干扰读写」之间的明确取舍，`PRAGMA` 双步 checkpoint 而非每日 VACUUM 也是对 SQLite 特性的针对性选择。

需要留意的三处事实边界：启动后第一个周期不会预清理，保留天数为 0 表示永久保留，`bot_score_logs` 与 `stats_retention_days` 目前不构成有效保留闭环。建议把保留天数与 `db_optimize_interval_hours` 纳入部署清单，并用删除日志的行数作为容量核对的唯一依据。
