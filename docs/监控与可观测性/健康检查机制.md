## 简介

My-OpenWaf 在**管理端口**（默认 `:9443`，明文 HTTP）上提供三个探针：存活 `/healthz`、就绪 `/readyz`、状态 `/status`。健康判定与生命周期管理解耦：`Checker` 只负责读状态并回码，`lifecycle.Manager` 负责多服务器的启动、就绪等待与优雅关闭，`TokenManager` 负责认证黑名单是否就绪。

关键事实（必须与运行码一致）：

- `/readyz` 就绪条件是四者同时成立——**快照非 nil ∧ `lm.Ready()` ∧ `tokenMgr.Ready()` ∧ 数据库 Ping**（`health.go:32-44` 经 `server.go:629` 注入的 `ready` 回调组合而成）。不是「仅快照 + DB」两项。
- `/healthz` 的 `Alive()` **恒返回 true**（`health.go:29`），即存活探针只要进程能响应即 200，不做任何下游检查。
- `/metrics`、`/readyz`、`/healthz`、`/status` 都挂在 `adminSrv`（`server.go:1053-1056`），属控制面端口，不在数据面监听器上。
- Redis 不参与就绪判定：可选依赖，不可用时进程优雅降级而非 `not ready`（`runtime.go:99-116`）。

探针编排、指标与事件等域级内容见 [监控与可观测性](监控与可观测性.md)；指标名口径见 [性能指标收集](性能指标收集.md)。

### 启动到就绪：状态流转

进程从冷启动到可接流量经历「启动中 → 就绪」，运行期可在「就绪 ↔ 未就绪」间迁移，收到信号后进入「关闭」。`Alive` 是贯穿全程的独立位（除进程退出外恒真）。

```mermaid
stateDiagram-v2
state "启动中" as boot
state "未就绪" as notready
state "就绪" as ready
state "关闭" as shutdown
[*] --> boot: Run 开库 迁移 种子
boot --> notready: 快照未加载 或 server 未 Running
boot --> ready: 快照 ∧ lm.Ready ∧ tokenMgr.Ready ∧ Ping
notready --> ready: 四条件全部恢复
ready --> notready: 快照缺失 或 DB Ping 失败 或 某 server 掉线
ready --> shutdown: 收到 SIGINT 或 SIGTERM
notready --> shutdown: 收到信号
shutdown --> [*]: Shutdown 完成 默认 10s 超时
note right of ready: readyz=200 可接流量
note right of notready: readyz=503 被摘流
```

### 生命周期与优雅关闭

`Start`/`StartOne` 在后台 goroutine 调 `Spin()` 后用 `waitReady` 轮询：5 秒截止、5 毫秒 tick；若服务器在变就绪前退出，`Err()` 返回「hertz server stopped before becoming ready」（`lifecycle.go:205-227`、`49-59`）。热重载调谐用 `StartOne`/`Remove`，`Remove` 的关闭超时是更短的 500ms（`lifecycle.go:21`、`155`），而进程级 `Shutdown` 沿用 `defaultShutdownTimeout = 10s`（`lifecycle.go:18`、`250`）。`WaitForSignal` 仅监听 `SIGINT`/`SIGTERM`，收到后统一 `Shutdown` 并等待，超时则告警「shutdown deadline exceeded」（`lifecycle.go:290-298`、`282-286`）。

## 性能考虑

- 就绪判定全为内存读 + 一次 `Ping`，无锁阻塞：`Holder.Load` 是 `atomic.Pointer` 读（`snapshot.go:489`），`Manager.Ready` 持互斥锁仅遍历小 map。
- `waitReady` 用 5ms ticker 轮询而非忙等，最长 5s 截止，避免空转（`lifecycle.go:210-213`）。
- `Shutdown` 并发关闭全部服务器，10s 截止，缩短停机；`Remove` 用 500ms 快超时避免拖慢热重载（`lifecycle.go:18`、`21`）。
- `/healthz` 不调任何下游，适合高频存活探测而不产生数据库压力。

## 故障排查指南

三个探针均在管理端口 `:9443`，明文 HTTP，无鉴权。命令可直接执行：

```bash
# 1) 存活探针：进程可达即 200
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:9443/healthz
# 预期：200

# 2) 就绪探针：看状态码与体
curl -s http://127.0.0.1:9443/readyz
# 预期：就绪时 {"status":"ready"}（200）；否则 {"status":"not ready"}（503）

# 3) 定位就绪失败原因：/status 的 ready 与 /readyz 同判定，revision=0 说明快照未加载
curl -s http://127.0.0.1:9443/status
# 预期：JSON 含 alive/ready/revision/sites/listeners/goroutines/heap_alloc 等

# 4) 确认管理端口在监听（默认 :9443）
(ss -ltnp 2>/dev/null || netstat -ltnp 2>/dev/null) | grep ':9443'

# 5) DB 故障时 /readyz 转 503：先验证库可达再恢复
curl -s -o /dev/null -w "readyz=%{http_code}\n" http://127.0.0.1:9443/readyz
# 预期：库正常时 200；库不可用时 503
```

- `/readyz` 持续 503：按短路顺序排查——先看 `/status.revision` 是否为 0（快照未加载，检查 `ReloadSnapshot` 与键基配置 `runtime.go:215-217`），再看是否某数据面 server 未 `IsRunning`（`lm.Ready` 会因此为 false），最后查数据库 `Ping`（DSN/网络）。
- `/healthz` 一直 200 但 `/readyz` 503：正常——存活与就绪语义不同，前者不检查下游（`health.go:29`）。
- Redis 挂了却仍 `ready`：符合设计，Redis 不在就绪条件内（`runtime.go:109-115`）。
- 关闭卡住到 10s：`Shutdown` 超时仅告警不强杀（`lifecycle.go:284-286`），需查是否有服务器阻塞在长请求上。

## 结论

健康检查机制以「存活恒真、就绪四条件、状态只读」清晰分层：`Checker` 把 `snapshot.Holder`、`lifecycle.Manager`、`TokenManager` 与数据库 `Ping` 组合为就绪判据，`server.go:629` 是这套组合的唯一装配点；`lifecycle.Manager` 用 `waitReady` 保证启动后才报就绪、用并发 `Shutdown` 与 10s 截止保证优雅关闭。Redis 被刻意排除在就绪之外，保证可选依赖不可用时仍能服务。探针全部落在控制面端口，与数据面转发解耦。

## 附录

### 探针与周期建议

- 探针周期由外部编排（K8s/SLB）自行配置，代码不内置定时轮询：`Ready()` 仅在每次请求时即时计算。
- 存活探测可高频（不触库）；就绪探测应低频一些，因为每次都做一次 `Ping`（`health.go:39-43`）。
- 优雅关闭窗口：进程级 10s、热重载移除 500ms、就绪等待最长 5s（`lifecycle.go:18`、`21`、`210`），外部 terminationGracePeriod 应不小于 10s。
