## 简介

My-OpenWaf 是自托管的反向代理型 WAF，单二进制交付，核心特性可归纳为四条主线：

- **双平面架构**：控制面（管理 API + 内嵌 Next.js 面板，默认 `:9443`）与数据面（按站点 `bind` 聚合的多监听 + HTTP/3）彻底解耦，配置经不可变快照原子替换后热生效。
- **11 阶段检测引擎**：请求上下文依次穿过 `ip_reputation → anti_replay → acl → lua_pre → owasp_default → cve → bot → browser_sign → rate_limit → signature → custom`，终止动作短路后续阶段。
- **对抗纵深**：OWASP 361 条内置注册表（`owasp_rule_catalogs` 目录 553 条、18 个类别）、CVE 三类语言检测器、Bot 两阶段加权打分、JA3/JA4/ClientHello 指纹、验证码与 5 秒盾与链式挑战、浏览器签名、PoW + VMP 混淆 JS 分片、TCP drop、威胁情报、IP 信誉自动封禁、反重放。
- **可运营性**：快照原子热重载 + Redis 跨实例同步、Lua 与 QuickJS 双插件引擎、国密 SM2/SM3/SM4-GCM 挑战信封、图像转换与动态保护、自实现 `/metrics` 与统一异步写库。

本篇定位是**特性地图**：给出每个特性的实现位置、开关来源、依赖子系统与已知限制。逐子系统的设计细节属于[系统架构设计](../系统架构设计/系统架构设计.md)、[WAF 引擎系统](../WAF%20引擎系统/WAF%20引擎系统.md)与[安全防护功能](../安全防护功能/安全防护功能.md)的职责范围，本篇不复制其表格，只做索引与结论汇总。

## 项目结构

仓库按「领域目录 + 分层子包」组织，后端非测试 Go 代码实测 349 文件 / 115,733 行，前端 173 个 ts/tsx 文件，测试 532 个 `_test.go`。

```text

internal/app/            控制面/数据面接线、HTTP/3 计划、TLS 指纹监听
internal/core/           配置、运行时、引擎、流水线、规则 DSL、阶段实现
internal/dataplane/      站点匹配、代理/质询/阻断、SSE、WebSocket、TLS 指纹窥探
```

## 性能考虑

- **先强后弱**：`ip_reputation` 与 `anti_replay` 入链首位，名单命中直接终止，昂贵正则不启动。
- **无锁读**：规则编译与阶段链缓存都用 `atomic.Pointer` 发布不可变快照，写时复制加互斥锁串行化（engine.go:98-103、441-545），热路径不出现读写锁争用。
- **按族剪枝**：OWASP 与 CVE 在正则之前做单次字节掩码扫描与 Aho-Corasick 指示器门，未置位的桶整族跳过。
- **条件入链**：未启用的阶段不入链，避免为「大概率为空」的阶段付出分支成本。
- **异步落库**：安全事件与访问日志由 `UnifiedWriter` 单协程批量写入（批阈值 256），主库与日志库分文件避免 SQLite 写锁竞争。
- **体检测边界**：请求体默认只检查前 48 KiB，抽取深度 10、单值 100、multipart 20 段 × 4096。
- 效果与压测口径见[缓存与性能优化](../系统架构设计/缓存与性能优化.md)，本篇不重复其数值表。

## 故障排查指南

| 症状 | 可能原因 | 排查动作 | 处置方案 |
|------|----------|----------|----------|
| 改了保护配置但流量行为未变 | 代次未递增或快照 CAS 失败 | 查 `ConfigRevision` 与 reload 日志 | 重新提交更新；确认无并发覆盖 |
| 另一实例未同步 | Redis 未配置或 Pub/Sub 2s 超时 | 查 `openwaf:config:reload` 是否可达 | 配 `MY_OPENWAF_REDIS_ADDR`，或逐实例手动重载 |
| Bot 分数长期为 0 | 行为模块依赖限流窗口 | 看 `RequestRateLimitEnabled` 是否开启 | 启用请求限速或接受纯静态分 |
| JA3/JA4 为空 | 启用了 `MY_OPENWAF_H2WS_PEEKER_OFF` 逃生门 | 确认环境变量未置 `1` | 取消该测试专用变量 |
| 挑战反复回到未验证 | 客户端禁用 JS 或 PoW 超时 | 看 `shield_timeout_secs` 与分片加载 | 降低难度或改用纯验证码 |

## 结论

特性地图的结论有三点。第一，所有防护特性都挂在同一条 11 阶段链上，阶段是否入链完全由站点保护配置决定，因此「特性开关」在实现层面就是「阶段装配条件」，不存在第二配置源。第二，控制面与数据面之间只通过不可变快照与代次号耦合，这使热重载、跨实例同步与无锁读三个特性共享同一套底层不变式。第三，对抗类特性（指纹、挑战、混淆、国密）依赖外部库但降级路径明确，缺失依赖只会削弱判定强度，不会中断转发。

优势集中在覆盖面与可运营性；短板是特性数量带来的配置面复杂度——站点级三态字段与全局默认需要成对理解，新增保护字段必须按 `internal/store` → Admin handler → 前端类型 → 页面表单 → 默认值 → 验证命令的链路同步，否则会出现前端可见但后端不生效的偏差。
