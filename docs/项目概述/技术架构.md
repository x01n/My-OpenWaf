## 简介

本篇是**面向概览的技术栈与分层选型说明**，回答三个问题：系统分成哪几层、每层用什么、以及为什么这样选。组件级拓扑、依赖边、数据转换与状态迁移的权威描述在[系统架构设计](../系统架构设计/系统架构设计.md)及其 6 篇子文档中，本篇不复制其表格，只在需要处指向对应文档。

My-OpenWaf 的分层不是按技术堆叠（MVC 式），而是按**变更频率与执行位置**切分：控制面在低频写路径上，数据面在高频读路径上，二者之间用「不可变快照 + 代次号」这一条契约隔离。这条契约决定了后续几乎所有技术选型——为什么是 `atomic.Pointer` 而不是读写锁、为什么是 SQLite 单文件双库、为什么规则链要按站点缓存、为什么 PoW 要用 Rust 编译 WASM。

## 项目结构

三个可独立构建的技术栈共存于一个仓库：Go 后端（349 个非测试文件 / 115,733 行）、TypeScript-React 前端（173 个 ts/tsx）、Rust-WASM 挑战求解器（`wasm-pow-solver/` 11 个 rs 模块）。三者的产物最终合并为**单个 Go 二进制**：前端静态导出被复制进 `internal/core/adminweb/dist` 由 `embed` 打包，WASM 与 glue JS 被复制进 `internal/waf/challenge/powdata` 同样由 `embed` 打包。

## 详细组件分析

### 分层契约：快照与代次

层间只有一条数据契约：`Snapshot` 是不可变的，运行态通过 `Holder` 的原子指针发布新版本。`StoreIfNewer`（snapshot.go:474）用 CAS 循环保证「只有更高代次才能替换」，低代次写入直接被拒——这是热重载与跨实例同步能够安全并存的基础。请求路径只有一次 `Load()`，因此不存在读写锁争用。


### 传输层选型：Hertz + quic-go + 自管连接池

| 决策点 | 选用 | 备选 | 取舍理由 | 代价 |
|--------|------|------|----------|------|
| HTTP 服务框架 | Hertz v0.10.6 | `net/http`、gin | 控制面与数据面统一生态，原始 URI 路径可控，便于与上游逐字节一致 | 需要 fork 版 http2（`x01n/http2`）实现 RFC 8441 |
| HTTP/3 | quic-go v0.63.0 自建 `HTTP3Server` | 等框架内置 | 需按站点 bind 聚合 H3 计划并通告 Alt-Svc（http3.go:858） | 0-RTT 重放风险，默认不强制开启（:884） |
| TLS 指纹 | uTLS v1.8.2 + go-ja4 v1.0.0 | 纯标准库 `crypto/tls` | 标准库不暴露 ClientHello 扩展序，无法算 JA3/JA4 | 需自建窥探监听；测试逃生门会置空指纹 |
| 上游连接池 | 自管 `transport` 三类池 | 单一 `http.Transport` | 主池 256/32/30s（transport.go:157-161）、h2c 单例 512/128/90s、探活 128/32/90s 各有不同 SLA | 池语义分散，需按入口 `ResolveUpstreamBase` 统一 |
| 持久化 | GORM + 三方言，SQLite 优先 | 单方言裸驱动 | 自托管默认可用零依赖单文件；生产可切 MySQL/PG | SQLite 需 WAL + 双库分文件规避写锁（gorm.go:89/94） |
| Redis | rueidis v1.0.78 | go-redis | 单命令 50ms 超时的轻量客户端，限流 fail-open 语义直接 | 无重连；空实例走 5s 熔断 |
| 进程内缓存 | ristretto v0.2.0 | 手写 LRU | 快照层的 TinyLFU 容量控制 | 参数属快照层，不适用于规则缓存 |
| 指标导出 | 自实现文本拼装 | `prometheus/client_golang` | 指标族完全自定义，避免引入注册表与直方图成本 | 需自证 exposition 格式正确性 |
| 前端形态 | Next.js `output: "export"` | SSR 服务 | 静态产物 embed 进单二进制，无额外运行时 | 16 下不能用 redirects/cookies/Server Actions |
| PoW 求解 | Rust → WASM | 纯 JS | 浏览器侧算力不可控，WASM 收敛执行时间并便于混淆 | 需 `make optimize` 重建；glue 混淆后须 `FORCE_GLUE=1` |

## 性能考虑

- **两级无锁缓存**：规则编译缓存键 `{siteID, policyID}`（engine.go:34-37），阶段链缓存键 `{policyID, siteID, antiReplayEnabled}` 并附四项判据（:60-64、:461），读写模式统一为 `atomic.Pointer` 无锁读 + 写锁串行化后整体发布，不是 RWMutex。
- **对象池**：`RequestCtx` 走 `sync.Pool`（pool.go:20-37），进管道前 `ResetMutationCaches` 清零派生值，避免热路径分配。
- **条件入链**：阶段未启用即不入链，链容量按 11 预分配（engine.go:467）。
- **写侧收敛**：安全事件与访问日志由 `UnifiedWriter` 单协程批量落库；主库与日志库分文件避免 SQLite 写锁互扰。
- **协议成本**：h1/h2/h3 共用同一份站点路由键；WS 与 SSE 不进 `http.Transport` 连接池，避免池语义污染。
- 具体基准数值见[缓存与性能优化](../系统架构设计/缓存与性能优化.md)，本篇不重复。

## 结论

分层的唯一目的是让「高频读」与「低频写」不互相拖累：控制面可以任意扩展端点与表单，只要它仍只产出一次代次递增；数据面可以增加检测阶段，只要它仍只实现 `Phase` 并条件入链。技术栈选型沿同一逻辑收敛——单二进制交付排除了 SSR 与外部运行时，Go 侧统一 Hertz 生态覆盖 h1/h2/h3，浏览器侧用 Rust/WASM 换取不可控环境下的稳定算力，持久化用 SQLite 默认 + 双库分离规避写锁并保持三方言可切。

代价同样明确：特性面广导致配置字段与快照契约的同步成本高（新增保护字段必须贯通模型、Admin、前端类型、表单、默认值与验证命令）；QuickJS 依赖 CGO 与构建 tag；`/metrics` 自实现意味着 exposition 正确性需自行保证。

下一步值得推进的方向是继续压缩「第二配置源」风险：让阶段链装配条件、前端表单字段与 `check:*` 契约脚本三者共用单一事实表，并补上当前无人比对的 kind 白名单差集。
